# reversa-spec-sdd, Spec-Driven Development in Reversa

This skill runs the complete SDD process inside the Code New Project Agents pipeline: **decompose → draft → evaluate → iterate** until each spec is ready for the forward cycle.

The skill is a vendored version of the global `sdd-spec`, adapted to the Reversa context: it reads `prd.md` as the primary source, writes to `_reversa_sdd/sdd/`, marks everything with the 🟡 marker and ends by handing off to `/reversa-forward`.

## Why SDD?

Specs written before the code save time because they:

- Make ambiguities visible before they turn into bugs
- Align expectations between whoever asks and whoever implements
- Serve as a permanent reference for tests, reviews and onboarding
- Let LLMs implement with far more precision

The methodology here is **Pragmatic RFC plus LLM-First**: structured like an RFC (Problem / Goals / Design / Edge Cases), but optimized to be consumed by humans and AI agents alike.

## Before you start

1. Read `.reversa/state.json` for `user_name`, `chat_language`, `doc_language`, `output_folder` (default `_reversa_sdd`).
2. Check the precondition: **`<output_folder>/prd.md` must exist**. If absent, stop with a clear message:
   > "I couldn't find `<output_folder>/prd.md`. Run `/reversa-drafter` first, or invoke `/reversa-new` to run the full pipeline."
3. Make sure the `<output_folder>/sdd/` folder exists. Create it if it does not.

## Default output path

Each generated spec goes to:

```
<output_folder>/sdd/<component-kebab-case>.md
```

For example: `_reversa_sdd/sdd/user-authentication.md`, `_reversa_sdd/sdd/payment-checkout.md`.

The components are decomposed from `prd.md` in the first phase.

## The 🟡 marker is mandatory

Every item in the specs generated by `reversa-spec-sdd` must use the **🟡 PLANNED** marker (a variant of the 🟡 INFERRED used in other Reversa contexts). The 🟢 CONFIRMED marker is reserved for facts extracted from existing code by the Discovery Team — an inherited rule to avoid confusing "a fact about the legacy system" with "a forward hypothesis".

Every requirement, behavior, edge case and acceptance criterion in the specs must start with 🟡.

## Workflow

### Phase 0, Decomposition into components

Read `<output_folder>/prd.md` in full. From the "Scope", "Target personas" and "Acceptance criteria" sections, propose a decomposition of the product into logical components. Each component should represent a cohesive unit that will become its own SDD spec.

Present the decomposition to the user:

> "From the PRD, I identified these logical components:
>
>   1. **<component 1>**: <one-sentence description>
>   2. **<component 2>**: <one-sentence description>
>   3. **<component N>**: ...
>
> Do you agree with this decomposition? Would you like to add, remove or rename any of them?"

Wait for an answer. Iterate until it is confirmed (at most 2 adjustments). For each confirmed component, normalize the name to ASCII kebab-case.

### Phase 1, Per-component interview (optional)

For each component, decide whether the information in `prd.md` is already enough:

- **Enough:** go straight to Phase 2.
- **Missing:** ask at most 3 focused questions, covering whichever of the points below are absent:
  1. **That component's specific problem:** "What is `<component>`'s role in the product?"
  2. **Success:** "How will you know this component worked? What can the user do?"
  3. **Scope:** "What is explicitly OUT of this component's scope?"
  4. **Edge cases:** "Can you already anticipate hard cases or error situations in this component?"

Total limit: 3 questions per component, choosing the most critical ones.

### Phase 2, Drafting the spec

Use the template in `references/spec_template.md` as the basis. Fill in **every** section:

- **Functional requirements:** in the form `FR-01`, `FR-02`. Each testable in isolation. The 🟡 marker is mandatory.
- **Behaviors:** describe what happens, not how to implement it. The spec defines the **what**, not the **how**.
- **Zero ambiguity:** if you are unsure, mark it with `⚠️ OPEN:` and add it to the Open Questions list.
- **LLM-readiness:** write it as though a developer or an LLM will implement it without asking anything.
- **The 🟡 marker on every item in the spec**, including FRs, edge cases and criteria.

Use `<doc_language>` for the specs' content.

### Phase 3, Automatic quality evaluation

After drafting each spec, run the scorer.

**Python detection:** try `python --version` or `python3 --version` via the shell.

- **If Python is available:**

  ```
  python scripts/spec_scorer.py --spec <output_folder>/sdd/<component>.md
  ```

  Use the script's literal output.

- **If Python is not available (manual mode):** apply the procedure in the "Scoring on engines without Python" section below.

The scoring returns:

- A **total score** (0 to 100) with a per-dimension breakdown
- **Critical gaps** that need resolving
- **Suggestions** ordered by impact

Dimensions evaluated (see `references/evaluation_rubric.md` for details):

| Dimension | Weight | What it evaluates |
|---|---|---|
| Completeness | 30% | Every section filled in, requirements covered |
| Testability | 25% | Verifiable requirements, clear acceptance criteria |
| Clarity | 20% | No ambiguities, precise language |
| Scope | 15% | Non-goals defined, clear boundaries |
| Edge Cases | 10% | Error cases and system limits covered |

### Phase 4, Iteration

Based on the score:

1. Score **≥ 80**: the spec is ready. Persist it and move on to the next component.
2. Score **60 to 79**: fix the obvious gaps automatically, then confirm with the user whether anything critical is missing. Re-score.
3. Score **< 60**: go back to Phase 1 with questions focused on the gaps. Re-score.

Limit: **3 iterations per component**. After 3 attempts, persist with the current score and add a `## Quality gaps` section to the file.

On each iteration, show the delta: "went from 54 to 71, 2 critical gaps remain".

### Phase 5, Persistence and handoff

For each finished component:

1. Write `<output_folder>/sdd/<component-kebab-case>.md` with an atomic write (tempfile plus rename), UTF-8 without BOM.
2. Include the **evaluation report** (score + gaps + suggestions) at the end of the file.
3. If the file already exists, ask the user whether to overwrite it.

Once **all** the specs are generated, show a consolidated report:

> "`<user_name>`, SDD generation complete. Specs created in `<output_folder>/sdd/`:
>
> | Component | Path | Score | Iterations |
> |---|---|---|---|
> | <comp1> | <output_folder>/sdd/<comp1>.md | 87 | 1 |
> | <comp2> | <output_folder>/sdd/<comp2>.md | 73 | 2 |
> | <comp3> | <output_folder>/sdd/<comp3>.md | 68 | 3 (with open gaps) |
>
> Every item is marked with the 🟡 (planned) marker.
>
> Next step: run `/reversa-forward`, which will consume these specs and start the evolution cycle through to the code.
>
> Type **CONTINUE** to start `/reversa-forward`, or pause here."

Never proceed automatically.

## Scoring on engines without Python

When `python --version` and `python3 --version` both fail, switch to manual mode:

1. **Read `references/evaluation_rubric.md`** for each dimension's criteria.
2. For each of the 5 dimensions, evaluate the spec mentally and assign a score from 0 to 100, justifying it in 1 to 2 sentences:

   - **Completeness (30%):** are all 9 mandatory sections filled in? Do the FRs cover the declared scope?
   - **Testability (25%):** are the FRs verifiable in isolation? Do the acceptance criteria use a Given/When/Then form or equivalent?
   - **Clarity (20%):** are there vague phrases (intuitive, fast, easy)? Are there contradictions?
   - **Scope (15%):** are the non-goals declared explicitly? Are the boundaries clear?
   - **Edge cases (10%):** are at least 3 error/boundary cases covered?

3. **Compute the weighted score:**

   ```
   score = (Completeness * 0.30) + (Testability * 0.25) + (Clarity * 0.20)
         + (Scope * 0.15) + (Edge Cases * 0.10)
   ```

4. **List the gaps** in order of severity (blockers, important, improvements).

5. **Render the output** in the same format as the script:

   ```
   ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
   TOTAL SCORE: <NN>/100
   ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

   Breakdown:
     Completeness:  <NN>/100 (weight 30%)
     Testability:   <NN>/100 (weight 25%)
     Clarity:       <NN>/100 (weight 20%)
     Scope:         <NN>/100 (weight 15%)
     Edge Cases:    <NN>/100 (weight 10%)

   Critical gaps:
     - <gap 1>
     - <gap 2>

   Suggestions (by impact):
     1. <suggestion>
     2. <suggestion>
   ```

The manual-mode result should be equivalent to the script's for the same spec.

## Mode: evaluating an existing spec

If the user invokes `/reversa-spec-sdd` outside the `/reversa-new` pipeline, with a spec already written for evaluation:

1. Ask for the file's path.
2. Run the scoring (script or manual).
3. Present the score with a detailed per-dimension analysis.
4. List the gaps in order of severity.
5. Ask whether they want you to fix the points raised.

This mode does not need a `prd.md` and does not enter the pipeline. It is a standalone utility inherited from the original skill.

## Signs of a bad spec (avoid these)

- Requirements that cannot be tested ("the system must be intuitive")
- A missing or vague scope section ("we'll see what makes sense")
- Mixing technical implementation design with expected behavior
- Contradictory requirements that are not flagged
- No acceptance criteria defined
- Error edge cases completely absent

## Signs of a good spec (aim for these)

- Any developer can implement it without asking questions
- Any QA can write tests from it
- The non-goals are as clear as the goals
- Error cases have a defined behavior
- Every requirement has a unique, traceable ID
