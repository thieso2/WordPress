# 3D Architecture

Creates 3D visualizations of **software architecture** using Three.js. It always generates **standalone HTML** (a single, self-contained file) with an interactive 3D scene, camera controls (mouse, touch, keyboard), a parameter sidebar and a button to export the viewport as a PNG.

The skill covers five visual modes well established in software visualization, each with a dedicated reference in `references/`:

| Mode | When to use it | Reference |
|------|----------------|-----------|
| **Code City** | An overview of each file's size/complexity, the "code city" pattern | `references/CODE_CITY.md` |
| **Dependency Graph 3D** | A dependency graph with repulsive force, nodes in 3D | `references/DEPENDENCY_GRAPH_3D.md` |
| **Layer Stack** | Architectural layers (UI / Domain / Infra) stacked with flow arrows | `references/LAYER_STACK.md` |
| **Call Graph 3D** | A call tree explorable in depth | `references/CALL_GRAPH_3D.md` |
| **Architecture Tour** | An animated camera moving through the scene with a narrative overlay | `references/ARCH_TOUR.md` |

Shared Three.js, lighting, controls and performance patterns live in `references/THREE_PATTERNS.md`. Error scenarios and their handling are in `references/ERRORS.md`.

## Workflow

### 1. Receiving the data

The data may come from:

- **Inline JSON**: the user provides `modules.json` (a list of modules) and/or `deps.json` (a dependency graph).
- **A file path**: the user points at JSON files in `_reversa_docs/assets/data/` (generated by the `/reversa-documentation` agent).
- **Asking the user**: if the skill is invoked with no data, ask for the path or ask them to paste it inline.

**The expected `modules.json` schema**:

```json
[
  {
    "name": "src/auth/login.ts",
    "folder": "src/auth",
    "loc": 142,
    "complexity": 8,
    "type": "code"
  }
]
```

**The expected `deps.json` schema** (directed):

```json
{
  "nodes": [{ "id": "src/auth/login.ts" }, { "id": "src/auth/jwt.ts" }],
  "edges": [{ "from": "src/auth/login.ts", "to": "src/auth/jwt.ts", "weight": 1 }]
}
```

### 2. Choosing the mode

If the user specified a mode, use it. If not, **suggest 2 or 3 options** based on the data:

| Data type | Recommended modes |
|-----------|-------------------|
| `modules.json` with LOC + complexity | Code City (the default), Layer Stack if there are clear folders/layers |
| `deps.json` with many edges | Dependency Graph 3D, or Code City coloring the hot path |
| An execution trace or call graph | Call Graph 3D |
| An explicit request for a presentation | Architecture Tour combining two of the above |

When the node count goes above **500**, apply **folder grouping** automatically and tell the user (record the decision in the footer of the generated HTML).

### 3. Generating the code

Consult `references/THREE_PATTERNS.md` for the base setup (renderer, scene, camera, lighting, OrbitControls). Consult the chosen mode's specific reference for the layout algorithm and the materials.

**Fundamental rules**:

1. **Standalone HTML**: a single `.html` file with everything embedded (CSS, JS, data inline in `<script id="data">`). When run by the Reversa Docs Team, the data comes from `window.RV_DATA.modules` and `window.RV_DATA.deps` (loaded by the `assets/js/data.js` the Publisher generates) and `<script id="data">` is empty or absent. Final pages **never** `fetch()` local files (that breaks via `file://`).
2. **Local Three.js**: use `<script src="assets/vendor/three.min.js"></script>` pointing at the file the Publisher downloaded (the version pinned in `agents/reversa-docs-publisher/references/vendor-pins.yaml`, currently `three@0.147.0` IIFE). When invoked standalone outside the Docs team, accept a CDN as a fallback (`https://unpkg.com/three@0.147.0/build/three.min.js`), but **never** mix versions.
3. **Local OrbitControls**: use `<script src="assets/vendor/OrbitControls.js"></script>` (also IIFE, compatible with `three@0.147`). Do not use `examples/jsm/...` until the skill migrates to importmap + ESM.
4. **Renderer**: a WebGLRenderer with antialiasing and the device's pixelRatio.
5. **Lighting**: a HemisphereLight + a DirectionalLight with soft shadows. For the Code City, an extra AmbientLight to fill in.
6. **Camera**: a PerspectiveCamera, its initial position looking at the scene's center from above and slightly angled. The distance derived from the scene's size.
7. **Performance**: use an `InstancedMesh` when there are more than 200 elements of the same type. A hard limit of 5,000 buildings in the Code City without grouping.
8. **Responsiveness**: a resize handler resizes the renderer and adjusts the camera's aspect ratio.
9. **Sidebar**: on the right, with sliders/checkboxes/buttons in a vertical layout. Each control has a stable ID for `localStorage`.
10. **Export PNG**: a button captures the canvas via `renderer.domElement.toBlob()`.

    <script src="assets/vendor/three.min.js"></script>
    <script src="assets/vendor/OrbitControls.js"></script>
    <script src="assets/js/data.js"></script>
    <style>
        body { margin: 0; overflow: hidden; font-family: system-ui, sans-serif; }
        #scene { position: fixed; inset: 0; }
        #sidebar { position: fixed; top: 0; right: 0; width: 280px; height: 100vh; padding: 16px; background: rgba(15,15,20,0.85); color: #eaeaea; overflow-y: auto; }

    </style>

<body data-style="exploratory">
    <div id="loader">Loading 3D scene...</div>
    <canvas id="scene"></canvas>
    <aside id="sidebar">
        <h3>Controls</h3>
        <!-- SIDEBAR_CONTROLS -->
        <button id="reset">Reset</button>
        <button id="export-png">Export PNG</button>
    </aside>
    <script id="data" type="application/json"><!-- DATA_JSON --></script>
    <script>
        // The OrbitControls IIFE exposes THREE.OrbitControls globally.
        // 1. Load the data from window.RV_DATA when running in the Docs team,
        //    or from <script id="data"> in standalone mode.
        // 2. Set up the scene, camera, renderer and lighting

### 5. Saving and delivering

The output is always standalone HTML. Save it at the path the orchestrating agent gives (usually `_reversa_docs/architecture.html`).

When invoked outside the `/reversa-documentation` context, ask for a destination path or use `<mode>-<timestamp>.html` in the current directory.

## Quality guidelines

- **An intuitive camera**: the initial position shows the whole scene; OrbitControls with damping for smooth movement.
- **Cohesive materials**: a limited palette (5 to 8 colors at most); saturated colors indicate an attribute (e.g. red for the hot path, blue for lightweight modules).
- **Readable labels**: use CSS2DRenderer or sprites; labels only appear on hover or past a zoom threshold, so they do not clutter the view.
- **A visible loader**: the scene starts with a "Loading 3D scene..." overlay that disappears when the first frame's `requestAnimationFrame` completes.
- **Graceful fallback**: if Three.js does not load (no internet), show the message "This visualization needs the Three.js library to load. Connect to the internet and reload."
- **Basic accessibility**: keyboard navigation for the sidebar's buttons; a visible focus ring.
- **Language**: comments and visible text follow the installation's language. No em dashes.

## Code guidelines

- **Modularity**: separate the scene's creation, the geometry's construction and the interaction handling into clearly named functions.
- **No dependencies beyond Three.js and OrbitControls (local, in `assets/vendor/`)**: do not import GSAP, dat.GUI or any other lib without a clear need.
- **Named constants at the top**: colors, sizes and thresholds in a visible configuration block.
- **Dispose**: when switching modes or regenerating, call `geometry.dispose()` and `material.dispose()` to avoid leaks.
- **A performance check**: before rendering, count the nodes; if there are > 5,000 without an instanced mesh, abort and show a warning.

## Error handling

Consult `references/ERRORS.md` for the common scenarios (an unreachable CDN, malformed JSON, an empty project, WebGL unsupported, etc.).
