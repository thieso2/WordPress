# Bug Register (Reversa Bugs)

> Generated by Reversa on {{DATE}}. This file is the contract for this project's bug register.
> Source of truth: each `<context>/bugs/<ID>/bug.md`. Everything in `generated/` is a regenerable projection.

## Project configuration

```yaml
closure_policy: {{CLOSURE_POLICY}}   # local-software | package | production-service
control_mode: gated                  # supervised | gated | autonomous
```

- `closure_policy` defines what "resolved" requires:
  - `local-software`: regression tests passing + a spec verdict
  - `package`: the above + a merge + a published fixed version (+ any required backports)
  - `production-service`: the above + delivery + an observation window with no recurrence
- `control_mode: gated` (default): reading, isolated reproduction and diagnosis flow without approval;
  a gate is mandatory to apply tests, apply a change set, change the effective spec, use an external
  harness with access to the project, and for any destructive operation.

## Structure

Bugs are grouped by **context** (feature, module or use case, in the language of whoever reports them). Each context is an aggregating folder holding EVERYTHING for that area: bugs, inspections and views. The folder is created on demand, when the first problem in the area is reported; nothing is created empty.

```text
_reversa_bugs/
├── README.md                    this contract
├── taxonomy.yaml                controlled vocabulary of area/module/feature
└── <context>/                   e.g. credit-system/, shopping-cart/
    ├── bugs/BUG-<date>-<suffix>-<slug>/   the bug's single folder (IMMUTABLE address, never moves)
    │   ├── bug.md               canonical record
    │   ├── evidence/  ├── debate/  └── fix/
    ├── inspections/<sweep>/     reports from the context's fine-tooth-comb inspection
    └── generated/               the context's views, regenerated by /reversa-debugger-graph
```

## Life cycle

`status`: `open` → `active` → `resolved`. `phase` details the step within `active`
(mitigating, reproducing, diagnosing, testing, patching, delivering, observing, awaiting-human).
Being blocked is a condition (`blocking:`), never a status. Every closure has a `resolution_kind`.

**Completion lock:** once the closure policy is satisfied, the bug gets a `DONE.md` in its folder and becomes
READ-ONLY for every agent. Reopening: remove the lock deliberately, or record a new bug with
`regression-of`. The list of locked bugs appears in the context's `graph.html` (a derived view,
never hand-edited).

## Traceability rule

Every bug MUST identify:

1. The spec section that defines the expected behavior (effective spec = original + addenda in effect).
   Without a spec, the bug carries the `spec-gap` label and the gap is handled before resolution.
2. The affected code (where it shows up) and, after investigation, the root cause (where it originated), with an
   epistemic state and evidence.
3. The reproduction and regression tests.

A bug CANNOT be `resolved: fixed` with an empty `traceability.specs`, `root_cause` (confirmed) or
`regression_tests`.

## Agent protocol

1. Recording (`/reversa-debugger`) NEVER fixes. Fixing (`/reversa-debugger-fix`) goes through two approval
   gates with diffs (the tests that fail; the change set that makes the tests pass).
2. The original spec is NEVER edited. A spec change becomes a versioned, immutable addendum in
   `<output_folder>/addenda/bug-<ID>-vNNN.md`, with the human decision recorded.
3. The code diff and the spec diff/addendum are recorded TOGETHER in the bug's Resolution.
4. Bugs with `visibility: restricted` stay out of the views, and nothing exploitable goes to an external harness.
5. Relationships and root causes have an epistemic state: a hypothesis is not a fact.

## Conventions

- Canonical ID: `BUG-<YYYYMMDD>-<suffix>` (merge-safe). `display_number` is a human-friendly alias.
- Always reference by ID; the views resolve the path.
- Evidence goes in `evidence/`, never as giant logs inside the Markdown.
- Full schema: see `bug-schema` in the Reversa documentation (agents/reversa-debugger/references/).
