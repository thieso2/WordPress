## Identified Design Decisions

| Decision | Evidence in the code | Confidence |
|----------|----------------------|------------|
| Tests are partitioned so that expensive checks (loopback HTTP, remote version checks) run asynchronously via JavaScript after page load | `wp-admin/includes/class-wp-site-health.php` | 🟢 |
| Tests are either direct (run synchronously during page load) or async (fetched by JavaScript), so slow tests do not block the page | `wp-admin/includes/class-wp-site-health.php` | 🟢 |
| Test statuses are good, recommended and critical | `wp-admin/includes/class-wp-site-health.php` | 🟢 |
| WP_Site_Health is instantiated during boot specifically so its cron events can fire | `wp-settings.php:760` | 🟢 |
| The loopback test is how a site detects that WP-Cron cannot self-invoke | `wp-admin/includes/class-wp-site-health.php` | 🟢 |
| Results are also exposed through the site-health REST controller | `wp-includes/rest-api/endpoints/class-wp-rest-site-health-controller.php` | 🟢 |

## Risks and Gaps

- 🟢 **F-SH-01** — Site Health is the only place core systematically checks its own operating assumptions: that cron can spawn, that HTTPS works, that the REST API is reachable.
- 🟡 **F-SH-02** — Instantiating a diagnostic class on every request purely to keep a cron event registered is a small but real site-wide cost paid for an admin feature.
