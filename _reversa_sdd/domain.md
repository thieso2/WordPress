## 1. What WordPress actually is

The code answers this more clearly than any documentation:

**WordPress is an extensibility platform that ships with a blogging application.**

The evidence is structural, not rhetorical:

| Observation | Module |
|-------------|--------|
| 565 actions + 1,638 filters wrap nearly every value core computes | `hooks-plugin-api` |
| 35 core security functions are wholly replaceable by any plugin | `authentication-and-sessions` |
| 5 drop-ins can replace the database, object cache, page cache, error handler and network bootstrap | `bootstrap-and-load` |
| Every SQL statement passes through a filter before execution | `database-wpdb` |
| 9,112 lines exist purely so 20-year-old code keeps working | `deprecated-compat` |
| 16 unrelated entity types share one table because registering a post type is cheaper than adding one | `posts-and-post-types` |

The blogging features are the *demonstration*. The hook system is the product.

**Consequence for specification:** no WordPress behavior can be specified in isolation. Every
statement of the form "WordPress does X" is really "WordPress does X unless a filter says
otherwise" (F-HOOK-06).

## 2. Glossary

### Content

| Term | Meaning | Confidence |
|------|---------|-----------|
| **Post** | A row in `wp_posts`. Not necessarily a blog post — one of 16 built-in types. | 🟢 |
| **Post type** | A string in `post_type` plus a `WP_Post_Type` registration that declares capabilities, supports, REST exposure and rewrite behavior. | 🟢 |
| **Post status** | One of 11 values. **Derived from `post_date_gmt` at write time**, not caller-controlled (BR-POST-01). | 🟢 |
| **Meta** | A key/value row attached to a post, comment, term, user or blog. Protected when the key starts with `_`. | 🟢 |
| **Revision** | A `revision` post whose `post_parent` is the original. | 🟢 |
| **Attachment** | A `post` row of type `attachment` describing an uploaded file; the file itself lives on disk. | 🟢 |
| **Block** | A unit of content delimited by HTML comments in `post_content`. Static (saved markup) or dynamic (`render_callback`). | 🟢 |
| **Pattern** | A reusable arrangement of blocks. | 🟢 |
| **Freeform** | Content authored before blocks, wrapped in a `core/freeform` block. | 🟢 |

### Classification

| Term | Meaning | Confidence |
|------|---------|-----------|
| **Term** | A word — a row in `wp_terms`. Has no taxonomy of its own. | 🟢 |
| **Taxonomy** | A named classification scheme (`category`, `post_tag`, …). | 🟢 |
| **term_taxonomy_id (tt_id)** | The identifier that actually links objects to terms. **Not `term_id`** (BR-TAX-01). | 🟢 |
| **Hierarchical taxonomy** | One whose terms have parents (categories). Counts roll up at read time (BR-TAX-11). | 🟢 |

### Identity

| Term | Meaning | Confidence |
|------|---------|-----------|
| **Role** | A named bundle of capabilities, stored per user in `usermeta` as `{$prefix}capabilities`. | 🟢 |
| **Capability** | A boolean permission. 50 primitives in the default roles. | 🟢 |
| **Meta capability** | An object-specific question (`edit_post`, `delete_page`) resolved by `map_meta_cap()` into primitives at call time. Never stored. | 🟢 |
| **`do_not_allow`** | The deny primitive. Unset before evaluation, so requiring it can never be satisfied (BR-CAP-02). | 🟢 |
| **Super Admin** | Multisite-only; bypasses every capability check except `do_not_allow`. | 🟢 |
| **Nonce** | A time-windowed HMAC bound to user, action and session token. **Not a nonce** — deterministic for 12 hours (F-AUTH-03). | 🟢 |

### Runtime

| Term | Meaning | Confidence |
|------|---------|-----------|
| **The Loop** | Iteration over `$wp_query->posts`, priming caches on the first `the_post()`. | 🟢 |
| **Hook** | An action or a filter. They are the same mechanism; `do_action()` is `apply_filters()` with the return discarded (F-HOOK-01). | 🟢 |
| **Pluggable function** | One of 35 functions in `pluggable.php` that a plugin may redefine outright. | 🟢 |
| **Drop-in** | A file in `wp-content/` that replaces a core subsystem by filename: `db.php`, `object-cache.php`, `advanced-cache.php`, `sunrise.php`, `fatal-error-handler.php`. | 🟢 |
| **Transient** | An option with an expiry — or an object-cache entry if a persistent cache exists (BR-OPT-10). | 🟢 |
| **Autoload** | A 6-valued enum on `options` controlling whether a value loads on every request. | 🟢 |
| **WP-Cron** | A queue in the `cron` option, drained by visitor traffic. Not a daemon (F-CRON-01). | 🟢 |
| **Recovery mode** | A degraded state where a fataling plugin or theme is skipped and the admin gets a signed access link. | 🟢 |
| **Ability** | A namespaced, schema-described, permission-gated operation invocable by REST or by an AI model. | 🟢 |

## 3. Cross-cutting domain rules

These are rules the Archaeologist found in more than one module — the ones that define how
WordPress behaves as a whole.

### DR-01 · Everything is filterable, therefore nothing is final 🟢

1,638 filters and 565 actions. `apply_filters('query', $sql)` means even SQL is negotiable
(BR-DB-05). `user_has_cap` means even authorization is negotiable (F-CAP-01). A specification of
WordPress that omits the hook surface describes a different system.

### DR-02 · Input arrives slashed 🟢

`wp_magic_quotes()` (`wp-settings.php:636`) rebuilds `$_REQUEST` and re-slashes every superglobal.
`wp_unslash()` is required before use; `wp_slash()` before calling functions that expect slashed
input. Enforced by nothing (F-FMT-05).

### DR-03 · Escape at output, sanitize at input, and never confuse them 🟢

Sanitizing (`sanitize_text_field`) cleans data for storage. Escaping (`esc_html`, `esc_attr`,
`esc_url`) prepares data for a specific output context. The escaper is chosen by destination, not by
source. Convention only, enforced by review.

### DR-04 · Optional extensions always have a pure-PHP fallback 🟢

`sodium` → `sodium_compat`; `zip` → `PclZip`; `curl` → streams; `imagick` → GD; `mbstring` →
`compat.php`. WordPress assumes it cannot control its hosting environment, and this assumption
shapes the boot sequence, the media pipeline and the update system.

### DR-05 · Cost is deferred until someone asks 🟢

Term counts defer (BR-TAX-09), comment counts defer (BR-CMT-13), transients expire lazily
(BR-OPT-09), meta caches prime on first loop iteration (BR-QUERY-10), rewrite flushes defer to
`wp_loaded` (BR-RW-07), cron runs on visitor traffic (F-CRON-01). Nothing happens on a schedule;
everything happens because a request triggered it.

### DR-06 · State is global and process-wide 🟢

`$wpdb`, `$wp_query`, `$wp_rewrite`, `$wp_roles`, `$wp_locale`, `$wp_filter`,
`WP_Block_Supports::$block_to_render`, `$super_admins`. Created during boot, mutated throughout the
request. `switch_to_blog()` mutates several at once and must be unwound manually (F-MS-02).

### DR-07 · Compensating transactions instead of database transactions 🟢

`wpdb` exposes no transaction API (F-DB-06). So: `wp_insert_term()` inserts, detects a duplicate,
and deletes its own rows (F-TAX-02); `add_metadata()` checks-then-inserts with no unique index
(F-META-02); `wp_unique_post_slug()` loops with one query per attempt (F-POST-03). Every
"uniqueness guarantee" in WordPress is advisory.

### DR-08 · Failure degrades rather than stops 🟢

A fatal plugin is paused, not fixed (BR-BOOT-05). An unverifiable update signature is "unsupported",
not "invalid" (BR-FS-07). A missing block renders a placeholder (BR-BLIB-04). A deleted menu target
is tombstoned (BR-MENU-05). A malformed block parses as freeform (BR-BLK-05). Availability is
consistently chosen over correctness.

### DR-09 · Two of everything, and both are supported 🟢

REST **and** XML-RPC. Classic scripts **and** script modules. `WP_Error` **and** `WP_Exception`.
Widgets **and** blocks **and** the Customizer **and** the Site Editor. `.mo` **and** `.l10n.php`.
phpass **and** bcrypt **and** `$wp` bcrypt. Nothing is removed, so every generation accumulates.

### DR-10 · Security defaults are inconsistent across subsystems 🟢

| Subsystem | Default | Rule |
|-----------|---------|------|
| REST route with no `permission_callback` | **public** | BR-REST-05 |
| REST `permission_callback` returning `null` | **denied** | BR-REST-04 |
| `map_meta_cap()` emitting no capabilities | **allowed** | BR-CAP-05 |
| `delete_post` with no object argument | **denied** | BR-CAP-10 |
| Admin-Ajax `nopriv` handler | **public, no gate** | BR-ADM-07 |
| Ability with no explicit opt-in | **private, not in REST** | BR-AI-04 |

Six authorization surfaces, five different defaults. This is the single most important finding for
anyone auditing or specifying WordPress security.

## 4. Business rules by domain

The Archaeologist recorded **431 rules** across 44 modules in `code-analysis.md`. The ones with
cross-module consequences:

### Content lifecycle

| Rule | Statement |
|------|-----------|
| BR-POST-01/02 | Status is computed from the date with a 60-second threshold. A caller cannot force `publish` with a future date. |
| BR-POST-04 | Drafts store `0000-00-00 00:00:00`, which is **why** BR-DB-10 strips `NO_ZERO_DATE` from MySQL's SQL mode. |
| BR-POST-10 | `guid` is seeded from the permalink on first publish and never updated. |
| BR-POST-11 | Every status transition unconditionally clears the scheduled-publish cron event. |
| BR-POST-06/07 | Slug uniqueness has three different scopes, and reserved words (feed slugs, `embed`, pagination numbers, date-archive segments) force a suffix. |

### Moderation

| Rule | Statement |
|------|-----------|
| BR-CMT-05 | The post author and any user with `moderate_comments` skip **all** moderation. |
| BR-CMT-06 | `comment_moderation = '1'` holds everything and short-circuits every other rule. |
| BR-CMT-08 | Moderation keywords match as substrings across author, email, URL, content, IP **and user agent**. |
| BR-CMT-10 | The disallowed list overrides the approval decision *after* it is made; `trash` or `spam` depends on `EMPTY_TRASH_DAYS`. |
| BR-CMT-04 | **Core enforces no rate limit.** `wp_check_comment_flood()` runs a query and asks a filter that defaults to `false`. |

### Authorization

| Rule | Statement |
|------|-----------|
| BR-CAP-01 | `has_cap()` requires **all** mapped capabilities, not any. |
| BR-CAP-03 | Super admins bypass everything except `do_not_allow`. |
| BR-CAP-14 | The `$super_admins` PHP global outranks the database option. |
| BR-REST-05 | A REST route without `permission_callback` is public; core warns but serves. |

### Data integrity

| Rule | Statement |
|------|-----------|
| BR-DB-06 | A write containing text the column's charset cannot represent is **rejected**, not truncated. |
| BR-DB-12 | `update()`/`delete()` support only equality joined by `AND`. |
| BR-TAX-05 | Duplicate terms are resolved by deleting the newly inserted rows; the older row always wins. |
| BR-META-03 | `$unique = true` is a `SELECT COUNT(*)` with no unique index behind it. |

## 6. Findings

| # | Finding | Confidence |
|---|---------|-----------|
| F-DOM-01 | WordPress's domain is not publishing; it is extensibility. The publishing features are the reference implementation of the extension model. | 🟢 |
| F-DOM-02 | Six authorization surfaces with five different defaults (DR-10) is the highest-value observation in this analysis for security work. | 🟢 |
| F-DOM-03 | Constraints in one module are causally locked to constraints in another (`NO_ZERO_DATE` ↔ draft dates; `pagination_base` ↔ legal post slugs). These couplings are invisible from either module alone. | 🟢 |
| F-DOM-04 | Every uniqueness guarantee is advisory because there are no transactions and almost no unique indexes. | 🟢 |
| F-DOM-05 | The AI/Abilities subsystem inverts nearly every core default — mandatory namespaces, no overwrite, private by default, validated output. It reads as a deliberate correction. | 🟢 |
| F-DOM-06 | Nothing is ever removed. The system's complexity is monotonically increasing by design, and that design is why it survived 22 years. | 🟢 |
