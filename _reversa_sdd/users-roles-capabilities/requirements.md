## Overview

The authorization model. Roles are named bundles of capabilities, capabilities are booleans, and a meta-capability layer translates object-specific questions into concrete capability checks. This is WordPress's entire access control. 🟢

**Complexity:** `high` · **Business rules extracted:** 15 · **Public functions catalogued:** 14 · **Extension points:** 7

**Depended on by 13 module(s):** `admin-application`, `ai-abilities-connectors`, `authentication-and-sessions`, `comments`, `customizer`, `internationalization`, `kses-security`, `multisite`, `posts-and-post-types`, `query-and-loop`, `rest-api`, `sitemaps`, `xmlrpc`

## Responsibilities

- **meta capability mapping** — An ~870-line switch translating object-specific meta capabilities (edit_post, delete_post, edit_user, remove_user) into lists of primitive capabilities based on the object's author, status and type 🟢
- **five-stage capability check** — map_meta_cap first, super-admin bypass second, user_has_cap filter third, do_not_allow removal fourth, then require ALL mapped caps 🟢
- **dynamic capability grants** — Three core callbacks on user_has_cap compute environment-dependent capabilities rather than storing them 🟢
- **incremental role definition** — populate_roles() calls eight version-named functions (_160 through _300), layering each historical WordPress version's capability additions 🟢
