## Main Flow

1. **meta capability mapping** — An ~870-line switch translating object-specific meta capabilities (edit_post, delete_post, edit_user, remove_user) into lists of primitive capabilities based on the object's author, status and type.
   Source: `wp-includes/capabilities.php:45` 🟢
2. **five-stage capability check** — map_meta_cap first, super-admin bypass second, user_has_cap filter third, do_not_allow removal fourth, then require ALL mapped caps.
   Source: `wp-includes/class-wp-user.php:787` 🟢
3. **dynamic capability grants** — Three core callbacks on user_has_cap compute environment-dependent capabilities rather than storing them.
   Source: `wp-includes/capabilities.php:1309` 🟢
4. **incremental role definition** — populate_roles() calls eight version-named functions (_160 through _300), layering each historical WordPress version's capability additions.
   Source: `wp-admin/includes/schema.php:719` 🟢

## Alternative Flows

- **BR-CAP-02:** do_not_allow is unset from the user's capability set before evaluation, so a requirement for it can never be satisfied. It is the deny primitive. 🟢
- **BR-CAP-03:** A multisite super admin passes every check unless the mapped capability list contains do_not_allow. 🟢
- **BR-CAP-09:** A user may not remove themselves in multisite unless they are a super admin. 🟢
- **BR-CAP-10:** delete_post / delete_page without a post argument emits _doing_it_wrong() and returns do_not_allow: fail closed. 🟢
- **BR-CAP-12:** install_languages, resume_plugin, resume_theme and view_site_health_checks are granted dynamically by user_has_cap callbacks, never stored. 🟢

## Risks and Gaps

- 🟢 **F-CAP-01** — The user_has_cap filter can rewrite the entire capability array on any check, so every authorization decision in WordPress is overridable by any plugin in one line.
- 🟢 **F-CAP-02** — map_meta_cap() is an ~870-line switch that is the sole source of truth for object-level permissions, with no formal specification: the code is the policy.
- 🟢 **F-CAP-03** — 'Empty caps array means allowed' is a dangerous default for a permission system; a map_meta_cap case that falls through without emitting a capability grants access silently.
- 🟡 **F-CAP-04** — The 6.1 hardening of delete_post to fail closed when the object argument is missing implies earlier versions failed open in that path.
- 🟢 **F-CAP-05** — level_0 through level_10 capabilities persist in every role two decades after deprecation, and plugins still test them.
- 🟢 **F-CAP-06** — Roles are stored as user meta with no referential integrity to their definitions; deleting a role leaves users holding a name that resolves to nothing.
- 🟢 **F-CAP-07** — Role definitions are spread across eight populate_roles_*() functions ordered by historical version; there is no single place stating what an Editor can do.
- 🟢 **F-CAP-08** — $super_admins as a PHP global outranking the database option means a compromised wp-config.php or any early-loading plugin can grant itself total control.
