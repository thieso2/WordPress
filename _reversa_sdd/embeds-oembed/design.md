## Main Flow

1. **provider registry match** — 59 pattern => [endpoint, is_regex] pairs matched with preg_match; sanitize_provider() validates each entry.
   Source: `wp-includes/class-wp-oembed.php:285` 🟢
2. **link-rel discovery fallback** — HTTP GET the target URL and scrape <link rel="alternate" type="application/json+oembed"> or its XML variant. A server-side request to a user-supplied URL.
   Source: `wp-includes/class-wp-oembed.php:493` 🟢
3. **format negotiation** — _fetch_with_format('json') then fall back to 'xml'.
   Source: `wp-includes/class-wp-oembed.php:586` 🟢
4. **type-dispatched rendering** — photo renders a validated img tag; video and rich inject provider html; link renders an anchor.
   Source: `wp-includes/class-wp-oembed.php:750` 🟢

## Risks and Gaps

- 🟢 **F-EMB-01** — Discovery makes a server-side HTTP request to a user-supplied URL; its safety depends entirely on the HTTP API's SSRF guards, not on anything in this module.
- 🟢 **F-EMB-02** — rich and video responses inject third-party HTML into the page. The trust boundary is the provider allowlist, so the 59-entry registry rather than sanitization is the actual security control.
- 🟢 **F-EMB-03** — Explicitly disabling XXE in _parse_xml() is one of the few places core defends against a parser-level attack.
- 🟡 **F-EMB-04** — Using a post type as the embed cache means embed data participates in post queries, revisions and exports.
