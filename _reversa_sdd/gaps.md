## Critical — decided, work outstanding

### G-02 · Authorization defaults must be made fail-closed 🔴

**Decision (Q4): deny by default is the house style.** The Abilities API is the reference.

Three surfaces **deviate** and are now identified as debt rather than as ambiguity:

| Surface | Current default | Required |
|---------|----------------|----------|
| REST route with no `permission_callback` | **public** — core warns via `_doing_it_wrong()` and serves anyway (BR-REST-05) | denied |
| `map_meta_cap()` emitting an empty capability array | **allowed** — `array_all()` over `[]` is `true` (BR-CAP-05) | denied |
| Admin-Ajax `wp_ajax_nopriv_*` | **public, no declarative gate at all** (BR-ADM-07) | a gate must exist |

Three surfaces already conform: Ability default-private (BR-AI-04), REST callback returning `null`
(BR-REST-04), `delete_post` without an object (BR-CAP-10, hardened in 6.1).

**Why this is the highest-value item:** any new surface inherits whichever precedent its author
copies. Admin-Ajax is the only one with no mechanism to fix, which is why it is the most common
source of WordPress privilege-escalation CVEs (F-ADM-01).

**Tracked as:** `architecture.md` §6 TD-01 and TD-02 · `permissions.md` §7.

### G-03 · KSES must migrate off regex HTML parsing 🔴

**Decision (Q5): it should be migrated.**

ADR-009 records that the HTML API was built *because* regex HTML manipulation caused a long tail of
correctness and security bugs. Three consumers remain unmigrated:

| Target | Size | Risk |
|--------|------|------|
| `kses.php` — the security-critical allowlist and last line of defense for untrusted markup | ~3,200 lines | **highest**; it is the guard itself |
| `wpautop()` | in `formatting.php` | runs on **every rendered post** |
| `wptexturize()` | in `formatting.php` | runs on **every rendered post** |

KSES is the priority: it is the only one of the three whose failure mode is a security bypass rather
than malformed output.

**Tracked as:** `architecture.md` §6 TD-04 and TD-08.

## Accepted risk

### G-01 · XML-RPC remains enabled 🟡

**Decision (Q3): keep it enabled.** Recorded as deliberate.

The decision does not change the behaviour, so the exposure is recorded unchanged:

- 78 methods; four of the six families serve clients that no longer exist (F-XR-01).
- **Credentials on every call** — no session, no token (BR-XR-03).
- **No core rate limit** — the canonical brute-force target (F-XR-02).
- `pingback.ping` performs an **unauthenticated server-side fetch of a caller-supplied URL**
  (F-XR-03).
- **Zero dependents** — nothing in WordPress requires it (F-SIM-04).

**Mitigations that preserve the decision:** rate-limit `xmlrpc.php` at the web server or WAF, and
disable pingback methods specifically via the `xmlrpc_methods` filter. Neither requires disabling
the endpoint.

### Q7 + Q8 together

These two answers interact, and the combination is stronger than either alone:

> A persistent object cache gives the `doing_cron` lock **cross-process semantics**, and a system
> crontab removes the **traffic dependency**. Together they resolve both F-CRON-01 and F-CRON-02 —
> the two most serious properties of the cron module — in the target deployment.
