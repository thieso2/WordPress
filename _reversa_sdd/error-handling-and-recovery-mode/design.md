## Main Flow

1. **detect-attribute-pause-recover loop** — register_shutdown_function catches the fatal, the error's file path maps to a plugin or theme, the extension is stored as paused, an email with a signed link is sent, and the boot sequence skips the paused extension on subsequent requests.
   Source: `wp-includes/class-wp-recovery-mode.php:168` 🟢
2. **lockout-proof TTL constraint** — get_link_ttl() returns max(filtered_ttl, rate_limit) so a misconfigured filter cannot make links expire faster than replacements can be sent.
   Source: `wp-includes/class-wp-recovery-mode.php:317` 🟢

## Alternative Flows

- **BR-ERR-01:** WP_Error holds multiple codes each with multiple messages; get_error_message() returns only the first. 🟢
- **BR-ERR-02:** Only E_ERROR, E_PARSE, E_USER_ERROR, E_COMPILE_ERROR and E_RECOVERABLE_ERROR trigger the fatal error handler; warnings and notices do not. 🟢
- **BR-ERR-08:** The recovery link TTL is max(filtered_ttl, rate_limit), so the link can never expire before another email may be sent. 🟢
- **BR-ERR-09:** The recovery cookie is httponly, secure when is_ssl(), and set on both COOKIEPATH and SITECOOKIEPATH. 🟢

## Risks and Gaps

- 🟢 **F-ERR-01** — The full loop (detect, attribute, pause, skip, notify, recover) is genuinely well engineered and unusual in a CMS, converting a white screen of death into a degraded but usable site.
- 🟢 **F-ERR-02** — max(ttl, rate_limit) is a small guard preventing an administrator lockout that no amount of filter misconfiguration can produce: defensive design against the extension API rather than against users.
- 🟡 **F-ERR-03** — Extension attribution is by file path, so an error thrown inside core but caused by a plugin's data is attributed to core and the wrong extension is paused.
- 🟢 **F-ERR-04** — WP_Error and WP_Exception coexist with no migration deadline; two error models are in simultaneous use across the codebase.
- 🟢 **F-ERR-05** — Fatal-error handling is itself a drop-in, so a site can replace the mechanism that catches its own fatal errors.
