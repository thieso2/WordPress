## Main Flow

1. **locale precedence chain** — pre_determine_locale filter, then login-screen wp_lang (the only user-supplied source, sanitized), then user locale for admin and ?_locale=user JSON, then installation language, then the site option.
   Source: `wp-includes/l10n.php:124` 🟢
2. **stack-based locale switching** — switch_to_locale pushes and reloads all textdomains; restore_previous_locale pops and reloads again.
   Source: `wp-includes/l10n.php:1899` 🟢

## Alternative Flows

## Risks and Gaps

- 🟢 **F-I18N-01** — The login-screen locale is the only user-controlled locale input and it becomes part of a filesystem path, making sanitize_locale_name() a path-traversal boundary rather than a formatting nicety.
- 🟢 **F-I18N-02** — Using the English source string as the key means fixing a typo in an English string orphans every translation of it.
- 🟢 **F-I18N-03** — The .l10n.php format is a performance answer to .mo parsing: a PHP array that opcache can retain across requests.
- 🟡 **F-I18N-04** — Locale switching reloads all textdomains, so switching in a loop (for example a per-recipient email loop) pays a full reload per iteration.
