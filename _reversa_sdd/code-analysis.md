## How to read this document

WordPress has no dependency-injection container, no ORM and no service layer. Its architecture is
three mechanisms applied everywhere:

1. **Global functions over global state** — `$wpdb`, `$wp_query`, `$wp_rewrite`, `$wp_roles`,
   `$wp_the_query`, `$wp_locale`, `$wp_object_cache` are process-wide singletons created during boot.
2. **The hook system** — 565 actions and 1,638 filters. Almost every meaningful value passes through
   `apply_filters()` before use, which means *core behavior is not final*. Any specification of a
   WordPress function that omits its filters describes only the default case.
3. **Progressive enhancement over a hostile environment** — every optional PHP extension has a
   pure-PHP fallback, because WordPress cannot assume anything about its host.

Each module below is documented as: **purpose → control flow → algorithms → data structures →
configuration → extension points → business rules → findings**.

Vendored third-party libraries are documented in `dependencies.md`, not here.

# Tier A — Core kernel

## A1. `bootstrap-and-load`

**Purpose.** Turn a bare PHP request into a fully initialized WordPress runtime: locate configuration,
verify the host can run WordPress, define constants, connect the database, start the object cache,
load plugins and the theme, and hand control to the request handler.

### Algorithms 🟢

**Config discovery (`wp-load.php`)** — a two-location search with a deliberate guard:

```
if   ABSPATH/wp-config.php exists          → use it
elif dirname(ABSPATH)/wp-config.php exists
     AND dirname(ABSPATH)/wp-settings.php does NOT exist   → use it
else → redirect to wp-admin/setup-config.php
```

The second branch supports moving `wp-config.php` one directory above the web root. The
`! file_exists(../wp-settings.php)` guard exists so that a WordPress installed inside another
WordPress does not steal its parent's configuration. 🟢

**Maintenance mode (`wp_is_maintenance_mode()`, `load.php:437`)** — four sequential escapes:

1. No `.maintenance` file, or `wp_installing()` → not in maintenance.
2. `$upgrading` timestamp **older than 10 minutes** → maintenance considered over (self-healing:
   a crashed upgrade cannot lock the site permanently).
3. Fatal-error scraping in progress and `md5($upgrading) === $_REQUEST['wp_scrape_key']` and
   `(int) $_REQUEST['wp_scrape_nonce'] === $upgrading` → bypass.
4. `apply_filters( 'enable_maintenance_mode', true, $upgrading )` returns false → bypass.

**Environment type (`wp_get_environment_type()`, `load.php:250`)** — resolved once and memoized in a
static. Precedence: `getenv('WP_ENVIRONMENT_TYPE')` → `WP_ENVIRONMENT_TYPE` constant → `'production'`.
Any value outside the whitelist falls back to `'production'`. **Fail-safe by design:** a typo yields
production behavior, never development behavior. 🟢

Valid environments: `local`, `development`, `staging`, `production`.
`WP_ENVIRONMENT_TYPES` is deprecated and emits `_deprecated_argument()`.

**Development mode (`wp_get_development_mode()`, `load.php:322`)** — same memoize-and-whitelist shape.
Valid modes: `core`, `plugin`, `theme`, `all`. Invalid → `''` (off). `wp_is_development_mode('theme')`
returns true when the mode is `theme` **or** `all`. Used to bypass caches during development.

**Plugin loading with paused-extension filtering** — `wp_get_active_and_valid_plugins()` reads the
`active_plugins` option, validates each file, then `wp_skip_paused_plugins()` removes any plugin
recorded as fatal in recovery-mode storage. The same pattern applies to themes
(`wp_get_active_and_valid_themes()` / `wp_skip_paused_themes()`). A plugin that fatals is
**automatically excluded from the next request** rather than bricking the site. 🟢

### Findings

| # | Finding | Confidence |
|---|---------|-----------|
| F-BOOT-01 | Boot order is a **public contract**. 311 `require`s in a fixed sequence with six named checkpoints — plugins depend on the exact position of each. This cannot be refactored without breaking the ecosystem. | 🟢 |
| F-BOOT-02 | There is no autoloader for core. Every class is explicitly required at boot, so **every request pays the cost of the whole codebase** regardless of what it needs. `SHORTINIT` is the only mitigation. | 🟢 |
| F-BOOT-03 | Four drop-in files (`advanced-cache.php`, `object-cache.php`, `db.php`, `sunrise.php`) can replace core subsystems wholesale. They are loaded by filename convention with no interface validation. | 🟢 |
| F-BOOT-04 | Recovery mode is armed before the DB connects, making it structurally capable of surviving almost any failure — a notable robustness property. | 🟢 |
| F-BOOT-05 | `wp_magic_quotes()` still runs at line 636, rebuilding `$_REQUEST` from `$_GET + $_POST` and re-slashing superglobals. All WordPress input arrives **slashed**, and `wp_unslash()` must be called before use. This is a pervasive, easily-missed correctness trap. | 🟢 |

## A2. `hooks-plugin-api`

**Purpose.** The extension mechanism the entire system is built on. Every other module in this
document exposes its behavior through it. 565 unique actions and 1,638 unique filters pass through
this engine.

**Primary files:** `wp-includes/plugin.php`, `wp-includes/class-wp-hook.php`,
`wp-includes/default-filters.php`, `wp-includes/class-wp-filter-sentinel.php`

### The core distinction 🟢

Actions and filters are **the same mechanism**. `do_action()` is `apply_filters()` with the return
value discarded:

```php
public function do_action( $args ) {
    $this->doing_action = true;
    $this->apply_filters( '', $args );
    if ( ! $this->nesting_level ) {
        $this->doing_action = false;
    }
}
```
— `class-wp-hook.php:375`

The only behavioral difference is the `$doing_action` flag, which controls whether `$args[0]` is
overwritten with the running value between callbacks. In a filter each callback receives the
*previous callback's return value*; in an action each receives the *original* first argument.

### Data structures 🟢

`WP_Hook implements Iterator, ArrayAccess`:

| Property | Visibility | Purpose |
|----------|-----------|---------|
| `$callbacks` | public | `array<int priority, array<string idx, array{function, accepted_args}>>` |
| `$priorities` | protected | cached `array_keys($callbacks)` |
| `$iterations` | private | per-nesting-level snapshot of the priority list |
| `$current_priority` | private | per-nesting-level current priority |
| `$nesting_level` | private | recursion depth counter |
| `$doing_action` | private | action vs. filter semantics flag |

Globals: `$wp_filter` (`array<string hook, WP_Hook>`), `$wp_actions`, `$wp_filters` (call counters),
`$wp_current_filter` (a stack).

### Algorithms 🟢

**Callback identity — `_wp_filter_build_unique_id()` (`plugin.php:1002`)**

Every callback is keyed by a string derived from its type:

| Callback type | Generated key |
|---------------|---------------|
| `string` (function name) | the string itself |
| `object` (invokable/closure) | `(string) spl_object_id($callback)` |
| `[object, 'method']` | `spl_object_id($obj) . $method` |
| `['Class', 'method']` | `'Class::method'` |
| anything else | `null` → **silently not registered** |

This is why **closures are effectively impossible to `remove_filter()`**: you need the identical
object instance to regenerate its `spl_object_id`. A widely-encountered practical limitation. 🟢

`spl_object_id` is also reused after garbage collection, so two different objects can theoretically
collide across a request. 🟡 INFERRED — no guard is present in the code.

**Registration — `WP_Hook::add_filter()` (`class-wp-hook.php:91`)**

1. `null` priority coerced to `0`.
2. Build the unique id; **`null` → return silently, no error, no warning.**
3. Record `$priority_existed`.
4. Store `$callbacks[$priority][$idx] = ['function' =>, 'accepted_args' => (int)]`.
5. If the priority is new and more than one priority exists, `ksort($callbacks, SORT_NUMERIC)`.
6. Refresh `$priorities`.
7. **If `$nesting_level > 0`, call `resort_active_iterations()`** — a hook added *while that same
   hook is running* is spliced into the live iteration.

**Live re-sorting — `resort_active_iterations()` (`class-wp-hook.php:130`)**

The most intricate logic in the module. For each active nesting level it rebuilds the iteration
array and repositions the internal array pointer so that:

- a new priority **lower** than the current one is prepended and skipped (it will not run —
  its moment has passed);
- a new priority **equal** to the one currently executing, when that priority did not previously
  exist, has the pointer walked back so the callback still runs in this pass;
- a new priority **higher** than the current one is picked up naturally later in the loop.

This is what makes `add_filter()` from inside a filter callback behave predictably. It relies
entirely on PHP's internal array pointer (`current()`, `next()`, `prev()`, `end()`, `reset()`).

**Execution — `WP_Hook::apply_filters()` (`class-wp-hook.php:328`)**

```
if no callbacks           → return $value unchanged
nesting_level++           (supports recursive dispatch)
iterations[level] = priorities   (snapshot)
do {
    priority = current(iterations[level])
    foreach callbacks[priority] as cb {
        if not doing_action: args[0] = value      ← filter chaining
        if accepted_args == 0:      value = call_user_func(cb)
        elif accepted_args >= n:    value = call_user_func_array(cb, args)
        else:                       value = call_user_func_array(cb, array_slice(args, 0, accepted_args))
    }
} while ( next(iterations[level]) !== false )
nesting_level--
return value
```

The three-branch `accepted_args` dispatch is a deliberate micro-optimization: `array_slice()` is
avoided when the callback accepts at least as many arguments as were passed.

**The `all` hook (`plugin.php:174`, `972`)**

Before every single `apply_filters()` / `do_action()`, core checks `isset($wp_filter['all'])`. If a
callback is registered on `'all'`, `_wp_call_all_hook()` fires it with the hook name and every
argument. This is a global interception point over all 2,203 unique hooks — powerful for debugging,
and a significant performance cost when used. 🟢

**`plugin_basename()` (`plugin.php:776`)** — normalizes a plugin file path to a
`folder/file.php` identifier. It walks `$wp_plugin_paths` in reverse-sorted order to resolve
symlinked plugin directories back to their canonical name, then strips `WP_PLUGIN_DIR` or
`WPMU_PLUGIN_DIR`. The `arsort()` ensures the longest (most specific) path matches first. 🟢

### Business rules 🟢

| # | Rule | Location |
|---|------|----------|
| BR-HOOK-01 | Default priority is `10`; lower runs earlier. `null` priority becomes `0`. | `class-wp-hook.php:91` |
| BR-HOOK-02 | Default `accepted_args` is `1`. A callback declared with fewer parameters than passed receives a sliced argument list; declaring more than `accepted_args` yields missing-argument errors. | `class-wp-hook.php:328` |
| BR-HOOK-03 | A callback whose unique id cannot be built is **silently dropped** — no exception, no notice. | `class-wp-hook.php:96` |
| BR-HOOK-04 | Within one priority, callbacks run in **registration order** (PHP array insertion order). | `class-wp-hook.php:345` |
| BR-HOOK-05 | Re-registering the same callback at the same priority **overwrites** rather than duplicating (same unique id). | `class-wp-hook.php:103` |
| BR-HOOK-06 | Registering a hook while it is executing re-sorts the live iteration; equal-priority additions still run in that pass, lower-priority ones do not. | `class-wp-hook.php:130` |
| BR-HOOK-07 | In an action, every callback receives the original arguments. In a filter, each receives the previous callback's return value as `$args[0]`. | `class-wp-hook.php:349` |
| BR-HOOK-08 | A filter callback that returns nothing returns `null`, which becomes the filtered value — a common source of silent data loss. | `class-wp-hook.php:353` |
| BR-HOOK-09 | `register_uninstall_hook()` rejects instance-method callbacks via `_doing_it_wrong()`, because the callback is serialized into the `uninstall_plugins` option. | `plugin.php:934` |
| BR-HOOK-10 | `'all'` callbacks fire before every hook dispatch in the system. | `plugin.php:182` |
| BR-HOOK-11 | `apply_filters_deprecated()` only emits its notice when a callback is actually registered, so unused deprecated hooks stay silent. | `plugin.php:723` |
| BR-HOOK-12 | `has_filter()` returns the integer priority when a specific callback is found — falsy-comparison against `0` priority is a known trap. | `class-wp-hook.php:252` |

### Findings

| # | Finding | Confidence |
|---|---------|-----------|
| F-HOOK-01 | Actions and filters share one implementation; the distinction is a single boolean. Documenting them as separate concepts is a convention, not an architecture. | 🟢 |
| F-HOOK-02 | Closures cannot practically be removed once registered, because their key is `spl_object_id()`. This is a structural limitation with no workaround in core. | 🟢 |
| F-HOOK-03 | `resort_active_iterations()` depends entirely on PHP's internal array pointer semantics. It is the most fragile code in the kernel and has no test coverage available in this tree. | 🟢 |
| F-HOOK-04 | Silent failure on unbuildable callback ids means a typo'd `add_filter()` produces no diagnostic at all. | 🟢 |
| F-HOOK-05 | The `'all'` hook check runs on every one of the ~3,371 dispatch sites, even when unused — two `isset()` calls per dispatch. | 🟢 |
| F-HOOK-06 | Because 1,638 filters wrap core values, **no core function's return value can be specified without also specifying its filters**. This is the single most important constraint on writing accurate WordPress specs. | 🟢 |
| F-HOOK-07 | `spl_object_id` reuse after GC could theoretically collide two callbacks within a request. No guard exists. | 🟡 |

## A3. `database-wpdb`

**Purpose.** The entire data access layer. One 4,200-line class, no ORM, no query builder, no
prepared-statement objects. Every other module reaches the database through the global `$wpdb`.

**Primary files:** `wp-includes/class-wpdb.php` (~4,230 lines), `wp-includes/wp-db.php` (BC shim)

### Data structures 🟢

`wpdb` is a single class holding connection state, table-name properties and query results.

`wp_posts` or `wp_3_posts` depending on the active blog:

| `$global_tables` (network-wide) | `users`, `usermeta` |

**Result / state properties:** `$last_query`, `$last_result`, `$last_error`, `$num_queries`,

`$reconnect_retries = 5`.

### Algorithms 🟢

#### `prepare()` — the security boundary (`class-wpdb.php:1458`)

This is not a real prepared statement. It is an `sprintf()`-derived interpolator, and its correctness
is what stands between WordPress and SQL injection. The algorithm:

1. `null` query → return `null`.
2. No `%` in the query → early return.
3. Strip pre-existing quoting: `'%s'` → `%s`, `"%s"` → `%s`. **Quotes are added by `prepare()`, never
   by the caller.**
4. Escape unrecognized percents via
   `preg_replace("/%(?:%|$|(?!($allowed_format)?[sdfFi]))/", '%%\1', $query)`.
5. `preg_split()` on `/(^|[^%]|(?:%%)+)(%(allowed_format)?[sdfFi])/` with `PREG_SPLIT_DELIM_CAPTURE`,
   producing a 3-element stride per placeholder. `placeholder_count = (count - 1) / 3`.
6. Detect array-passed args (`vsprintf` style) and flatten.
7. Walk placeholders in stride-3, classifying each:
   - `%f` → rewritten to `%F` to force **locale-unaware** float formatting (a comma decimal
     separator would break SQL);
   - `%i` → rewritten to `` `%s` `` and its arg index recorded in `$arg_identifiers` (identifier
     quoting, added in 6.2);
   - `%s` → arg index recorded in `$arg_strings`;
   - `%d`, `%F` → neither list (numeric, unquoted).
8. **Conflict check:** `array_intersect($arg_identifiers, $arg_strings)`. If an argument is used as
   both an identifier and a value, re-parse to build a readable conflict list, emit
   `_doing_it_wrong()` and **return `null`**.
9. **Arity check:** `count($args) !== $placeholder_count` → `_doing_it_wrong()`. If too few args and
   there are no numbered placeholders (or fewer args than the highest numbered one), return `''` —
   an empty query, which `query()` then refuses.
10. Escape the argument values and interpolate.

**Placeholder escaping (`placeholder_escape()`, line 2413)** — a defense against second-order
injection. A random, per-request sentinel is generated once:

```php
$salt = defined('AUTH_SALT') && AUTH_SALT ? AUTH_SALT : (string) rand();
$placeholder = '{' . hash_hmac('sha256', uniqid($salt, true), $salt) . '}';
```

Every literal `%` in a prepared value is replaced with this sentinel, and a `query` filter at
priority `0` (`remove_placeholder_escape`) converts it back immediately before execution. This means
a user-supplied `%s` inside a value **cannot** be re-interpreted as a placeholder by a later
`prepare()` call. 🟢

The `rand()` fallback when `AUTH_SALT` is undefined is weak, but the sentinel only needs to be
unguessable within a single request. 🟡

#### `query()` — the execution gate (`class-wpdb.php:2214`)

```
if !ready                                  → return false
query = apply_filters('query', $query)     ← every SQL statement is filterable
if !query                                  → insert_id = 0; return false
flush()
if check_current_query AND !check_ascii(query):
    stripped = strip_invalid_text_from_query(query)
    if stripped !== query:
        last_error = 'query contains invalid data'
        return false                       ← the query is REFUSED, not truncated
_do_query(query)
if dbh empty OR mysqli_errno == 2006 (server gone away):
    if check_connection(): _do_query(query)     ← retried once
    else: return false
last_error = mysqli_error(dbh)
if last_error:
    if insert_id AND query is INSERT/REPLACE: insert_id = 0
    print_error(); return false
if query is CREATE|ALTER|TRUNCATE|DROP  → return the raw result
...
```

Note the `query` filter: **every SQL statement WordPress executes passes through a filter first.**
That is an extraordinary extension point and an equally extraordinary attack surface.

#### Charset negotiation (`determine_charset()`, line 881)

A cascade that silently upgrades the caller's request:

| Input | Result |
|-------|--------|
| `utf8` | → `utf8mb4` (real 4-byte UTF-8; `utf8` in MySQL is 3-byte) |
| `utf8mb4` + no collate, or `utf8_general_ci` | → `utf8mb4_unicode_ci` |
| `utf8mb4` + other `utf8_*` collate | → `str_replace('utf8_', 'utf8mb4_', $collate)` |
| collate is `utf8mb4_unicode_ci` and server has `utf8mb4_520` | → `utf8mb4_unicode_520_ci` |

**BR:** WordPress never stores 3-byte `utf8` when 4-byte is available. This is why emoji support
required a database-level migration.

#### Invalid-text stripping (`strip_invalid_text()`, line 3624)

Before any write, `process_field_charsets()` and `process_field_lengths()` inspect the target
column's real charset and byte length (via `get_col_charset()` / `get_col_length()`, both memoized in
`$col_meta` / `$table_charset`). Values that cannot be represented in the column's charset cause the
query to be **rejected**, not silently mangled. `check_ascii()` is a fast path that skips all of this
for pure-ASCII queries.

#### SQL mode sanitization (`set_sql_mode()`, line 949)

On connect, WordPress reads `@@SESSION.sql_mode` and **removes** any of:

`NO_ZERO_DATE`, `ONLY_FULL_GROUP_BY`, `STRICT_TRANS_TABLES`, `STRICT_ALL_TABLES`, `TRADITIONAL`, `ANSI`

WordPress deliberately runs MySQL in a permissive mode. `0000-00-00 00:00:00` is a legitimate
WordPress date value (used for "not yet published"), which `NO_ZERO_DATE` would reject. 🟢

#### Reconnection (`check_connection()`, line 2124)

`DO 1` as a liveness probe. On failure, **5 retries with `sleep(1)` between each** — up to 5 seconds
of blocking. Then: if `template_redirect` has already fired (output has begun), return `false`
quietly; otherwise render a full HTML error page and `bail()`.

### Write API 🟢

| Method | Behavior |
|--------|----------|
| `insert($table, $data, $format = null)` | `INSERT`; returns rows affected or `false` |
| `replace($table, $data, $format = null)` | `REPLACE INTO` |
| `update($table, $data, $where, $format, $where_format)` | `UPDATE` with `AND`-joined `WHERE` |
| `delete($table, $where, $where_format)` | `DELETE` with `AND`-joined `WHERE` |
| `_insert_replace_helper()` | shared implementation for insert/replace |

All four run `process_fields()` → `process_field_formats()` → `process_field_charsets()` →
`process_field_lengths()`. When `$format` is omitted, the format is looked up in `$field_types`,
defaulting to `%s`. **There is no `OR` support and no operator support** in `$where` — only
equality joined by `AND`. Anything more complex requires hand-written SQL.

### Read API 🟢

| Method | Returns |
|--------|---------|
| `get_var($query, $x = 0, $y = 0)` | single scalar |
| `get_row($query, $output = OBJECT, $y = 0)` | one row as `OBJECT`, `ARRAY_A` or `ARRAY_N` |
| `get_col($query, $x = 0)` | one column as a flat array |
| `get_results($query, $output = OBJECT)` | all rows |

### Business rules 🟢

| # | Rule | Location |
|---|------|----------|
| BR-DB-01 | `prepare()` adds its own quoting; callers must **not** wrap `%s` in quotes. Existing quotes are stripped. | `class-wpdb.php:1497` |
| BR-DB-02 | An argument used as both `%i` (identifier) and `%s` (value) is a hard error → `_doing_it_wrong()` + `null`. | `class-wpdb.php:1643` |

### Findings

| # | Finding | Confidence |
|---|---------|-----------|
| F-DB-01 | `prepare()` is string interpolation, not a server-side prepared statement. Every SQL-injection defense in WordPress rests on this one regex-driven function. | 🟢 |
| F-DB-02 | The `query` filter lets any plugin rewrite every SQL statement in the system. Immense power, and a complete bypass of every guard above it. | 🟢 |
| F-DB-03 | `$allow_unsafe_unquoted_parameters` remains `true` for backward compatibility, preserving the historically unsafe `%1$s`-as-identifier pattern. The class's own docblock calls it risky. | 🟢 |
| F-DB-04 | `strip_invalid_text_*` issues extra `SHOW FULL COLUMNS` queries per table on first use, memoized per request. Correctness bought with round-trips. | 🟢 |
| F-DB-05 | 5×1 s reconnect sleeps inside a web request is a latency cliff under DB stress: requests queue rather than fail fast. | 🟢 |
| F-DB-06 | No transaction API. `wpdb` exposes no `begin`/`commit`/`rollback`; multi-table operations (e.g. deleting a post and its meta) are not atomic. | 🟢 |

## A4. `options-and-transients`

**Purpose.** WordPress's key-value store. Site configuration, plugin settings, cached remote data and
expiring values all live in one table, `wp_options`, addressed by name. This module is read on
**every single request** (via `wp_load_alloptions()`), which makes its caching behavior the single
largest lever on WordPress performance.

**Primary files:** `wp-includes/option.php` (~3,300 lines)

### Data model 🟢

`wp_options` — four columns: `option_id`, `option_name` (unique), `option_value` (LONGTEXT),
`autoload`.

The `autoload` column is **not a boolean**. It is an enum of six string values, introduced to let
WordPress distinguish an explicit human decision from an automatic one:

| Value | Meaning | Autoloaded? |
|-------|---------|-------------|
| `on` | explicitly enabled by the caller | ✅ |
| `off` | explicitly disabled by the caller | ❌ |
| `auto-on` | automatically enabled by heuristic | ✅ |
| `auto-off` | automatically disabled by heuristic | ❌ |
| `auto` | no decision made | ✅ |
| `yes` | legacy (pre-6.6) | ✅ |
| `no` | legacy (pre-6.6) | ❌ |

`wp_autoload_values_to_autoload()` (line 3259) defines the autoloading set as
`['yes', 'on', 'auto-on', 'auto']`, filterable — but the filter result is
`array_intersect()`ed with the original list, so **a filter can only remove values, never add
new ones**. A deliberate guard against invalid enum values entering the query. 🟢

### Algorithms 🟢

#### `get_option()` (`option.php:78`) — a five-level cascade

```
trim option name;  empty → false
deprecated key (blacklist_keys → disallowed_keys,
                comment_whitelist → comment_previously_approved)
    → _deprecated_argument(), recurse on the new name
① pre_option_{$option} filter, then pre_option filter
    → if !== false, RETURN (full short-circuit, DB never touched)
if WP_SETUP_CONFIG defined → false
$passed_default = func_num_args() > 1     ← distinguishes "default false" from "no default"
② alloptions cache (one bulk-loaded array)
③ notoptions cache — a set of names known NOT to exist
    → hit means RETURN default_option_{$option} filter, no DB query
④ per-option object cache
⑤ SELECT option_value FROM wp_options WHERE option_name = %s LIMIT 1
    → miss: record in notoptions, RETURN default_option_{$option} filter
special-case: option 'home' with an empty value falls back to get_option('siteurl')
```

Two details worth noting:

- **`get_row()` is used instead of `get_var()`** with an explicit comment: *"because of funkiness
  with 0, false, null values"*. `get_var()` cannot distinguish "no row" from "a row containing an
  empty string". 🟢
- **The `notoptions` negative cache** is what stops a missing option from generating a query on
  every request. It is a documented performance-critical structure.

#### `wp_load_alloptions()` (`option.php:600`)

Loads **every** row where `autoload IN ('yes','on','auto-on','auto')` in one query and caches the
result as a single `alloptions` array. This is why option reads are usually free — and why a single
oversized autoloaded option degrades every request on the site.

#### Automatic autoload sizing (`option.php:1306`, `1353`)

```
wp_determine_option_autoload_value($option, $value, $serialized, $autoload):
    bool $autoload              → 'on' / 'off'
    'on' | 'yes'                → 'on'
    'off' | 'no'                → 'off'
    otherwise:
        $autoload = apply_filters('wp_default_autoload_value', null, …)
        bool result             → 'auto-on' / 'auto-off'
        else                    → 'auto'
```

Core registers `wp_filter_default_autoload_value_via_option_size()` on that filter:

```
$max = (int) apply_filters('wp_max_autoloaded_option_size', 150000, $option);
if ( strlen($serialized_value) > $max ) return false;   → 'auto-off'
```

**BR: an option whose serialized value exceeds 150,000 bytes is automatically excluded from
autoloading.** A self-defense mechanism against the most common WordPress performance failure. 🟢

#### `update_option()` (`option.php:846`)

```
trim; empty → false
deprecated key remap
wp_protect_special_option($option)     ← 'alloptions' / 'notoptions' → wp_die()
clone if object                        ← prevents caller mutation leaking
$value = sanitize_option($option, $value)
$old_value = get_option($option)
pre_update_option_{$option} filter, then pre_update_option filter
if $value === $old_value
   OR maybe_serialize($value) === maybe_serialize($old_value)
        → RETURN FALSE                 ← "no change" is reported as failure
if default_option_{$option} filter === $old_value
        → delegate to add_option()     ← the option did not really exist
do_action('update_option', …)
if $autoload === null:
    read the current raw autoload; only re-evaluate if it is 'auto-on'|'auto-off'|'auto'
    (an explicit 'on'/'off' set by a human is never overridden)
$wpdb->update(...)
clear from notoptions; refresh alloptions or the per-option cache
do_action("update_option_{$option}", …), do_action('updated_option', …)
```

#### Transients (`option.php:1380`–`1698`)

Transients are options with an expiry, stored as **two rows**:

- `_transient_{$name}` — the value
- `_transient_timeout_{$name}` — the Unix expiry timestamp

**Storage strategy depends on whether a persistent object cache exists:**

| Condition | Storage |
|-----------|---------|
| `wp_using_ext_object_cache()` or `wp_installing()` | object cache only, with a native TTL. **No DB rows at all.** |
| otherwise | the two `wp_options` rows |

**Expiry is lazy, not scheduled.** `get_transient()` reads the timeout option and, if
`$timeout < time()`, deletes **both** rows and returns `false`. An expired transient that is never
read again is never cleaned up by this path — `delete_expired_transients()` (line 1638) exists as a
scheduled sweep for exactly that reason.

**Autoload interaction:** in `set_transient()`, a transient with **no expiration is autoloaded**
(`$autoload = true`), while one **with an expiration is not** (`$autoload = false`). The reasoning is
visible in `get_transient()`: *"If option is not in alloptions, it is not autoloaded and thus has a
timeout"* — presence in `alloptions` is used as a proxy for "this transient never expires", saving a
lookup. A subtle coupling between two caching layers. 🟢

There is also a repair path: if the value row exists but its timeout row is missing, `set_transient()`
deletes and re-adds both, rather than leaving an immortal transient.

#### Network options (`option.php:2001`–`2510`)

`get_network_option()` / `add_` / `update_` / `delete_` mirror the single-site API against
`wp_sitemeta` when multisite is active, and fall through to the regular options table when it is not.
Site transients (`get_site_transient()` etc.) mirror transients the same way.

#### Settings registry (`option.php:2996`)

`register_setting($group, $name, $args)` records a setting in `$wp_registered_settings` with
`type`, `description`, `sanitize_callback`, `show_in_rest` and `default`. `filter_default_option()`
(line 3239) hooks `default_option_{$name}` so a registered default is returned automatically when the
option is absent. This is the bridge between the options table, the Settings API and the REST
`/wp/v2/settings` endpoint.

### Business rules 🟢

| # | Rule | Location |
|---|------|----------|
| BR-OPT-01 | Option names are trimmed; an empty name returns `false`. | `option.php:80` |
| BR-OPT-02 | `blacklist_keys` and `comment_whitelist` are transparently remapped to `disallowed_keys` / `comment_previously_approved` with a deprecation notice. | `option.php:86` |
| BR-OPT-03 | `alloptions` and `notoptions` are protected names; writing to them calls `wp_die()`. | `option.php:565` |

| BR-OPT-06 | An option whose serialized value exceeds 150,000 bytes (filterable) is automatically set to `auto-off`. | `option.php:1353` |

| BR-OPT-14 | The `wp_autoload_values_to_autoload` filter can only remove values from the valid set, never add new ones. | `option.php:3259` |

### Extension points 🟢

`pre_option_{$option}`, `pre_option`, `option_{$option}`, `default_option_{$option}`,
`pre_update_option_{$option}`, `pre_update_option`, `update_option`, `update_option_{$option}`,
`updated_option`, `add_option`, `added_option`, `delete_option`, `deleted_option`,
`wp_default_autoload_value`, `wp_max_autoloaded_option_size`, `wp_autoload_values_to_autoload`,
`alloptions`, plus the transient family: `pre_transient_{$t}`, `transient_{$t}`,
`pre_set_transient_{$t}`, `expiration_of_transient_{$t}`, `set_transient_{$t}`, `setted_transient`,
`delete_transient_{$t}`, `deleted_transient`, and their `site_` equivalents.

### Findings

| # | Finding | Confidence |
|---|---------|-----------|
| F-OPT-01 | `wp_options` is the single most contended table in WordPress: configuration, plugin settings, transient cache and expiry timestamps all share one key-value table with one unique index. | 🟢 |
| F-OPT-02 | `autoload` being a 6-valued enum rather than a boolean is a recent and instructive design choice: it preserves the distinction between a human decision and a heuristic one, so the heuristic never overrides intent. | 🟢 |
| F-OPT-03 | `update_option()` returning `false` for "unchanged" is a persistent source of caller bugs; there is no way to distinguish it from a write failure. | 🟢 |
| F-OPT-04 | Transients silently change storage backend based on the presence of a persistent object cache. Behavior that is correct in production (Redis) and different in a default install is a real testing hazard. | 🟢 |
| F-OPT-05 | Transient expiry has no guaranteed upper bound. Without traffic to trigger the read path or the cron sweep, expired rows persist indefinitely. | 🟢 |
| F-OPT-06 | The autoload-size heuristic (150 KB) is a mitigation, not a fix: hundreds of options just under the limit still bloat every request. | 🟡 |
| F-OPT-07 | `pre_option_{$option}` allows a plugin to fully replace any option read without touching the database — the cleanest override point in core, and one that makes any option's value unspecifiable in isolation. | 🟢 |

## A5. `cache-and-object-cache`

**Purpose.** A request-scoped in-memory cache, designed to be transparently replaced by a persistent
one. The default implementation **does not persist across requests** — a fact that determines the
behavior of large parts of WordPress.

**Primary files:** `wp-includes/cache.php` (procedural API),
`wp-includes/class-wp-object-cache.php` (default implementation),
`wp-includes/cache-compat.php` (polyfills for drop-ins missing newer methods)

### The critical property 🟢

`WP_Object_Cache` is a PHP array. `$cache[$group][$key]`. Nothing more.

```php
private $cache = array();
```

When `wp-content/object-cache.php` exists, `wp_start_object_cache()` loads it instead and
`wp_using_ext_object_cache()` returns `true`. **Every caching decision in WordPress branches on
that boolean**, most visibly in the transient layer (see A4).

### Data structures 🟢

| Property | Purpose |
|----------|---------|
| `$cache` | `array<group, array<key, mixed>>` |
| `$cache_hits`, `$cache_misses` | counters for `stats()` |
| `$global_groups` | groups **not** prefixed with the blog id |
| `$blog_prefix` | `"{$blog_id}:"` under multisite |
| `$multisite` | bool |

**Key namespacing:** under multisite, a key in a non-global group is silently rewritten to
`"{$blog_prefix}{$key}"`. Global groups escape this. This is the entire multisite cache isolation
mechanism — no separate cache instances, just a key prefix. 🟢

**Core global groups** (`load.php:901`) — 22 of them:

`blog-details`, `blog-id-cache`, `blog-lookup`, `blog_meta`, `global-posts`, `image_editor`,
`networks`, `network-queries`, `sites`, `site-details`, `site-options`, `site-queries`,
`site-transient`, `theme_files`, `translation_files`, `rss`, `users`, `user-queries`, `user_meta`,
`useremail`, `userlogins`, `userslugs`

**Non-persistent groups** (`load.php:928`): `counts`, `plugins`, `theme_json` — a persistent backend
is asked *not* to store these, because they are cheap to recompute and expensive to invalidate.
`themes` is added later by `WP_Theme` (`class-wp-theme.php:259`).

### Algorithms 🟢

**Key validation (`is_valid_key()`, line 140)** — accepts `int` or non-empty trimmed `string`.
Anything else triggers `_doing_it_wrong()` (since 6.1) and returns `false`. Note it uses
`debug_backtrace(DEBUG_BACKTRACE_IGNORE_ARGS, 2)[1]['function']` to name the *calling* cache method
in the message.

**Existence (`_exists()`, line 178)**

```php
return isset( $this->cache[$group] )
    && ( isset( $this->cache[$group][$key] )
      || array_key_exists( $key, $this->cache[$group] ) );
```

The `array_key_exists()` second arm exists because `isset()` returns `false` for a stored `null`.
Without it, caching `null` would be indistinguishable from a cache miss. 🟢

**Object cloning on both boundaries** — `set()` clones objects on the way in, `get()` clones them on
the way out. Two clones per object round-trip. This guarantees that mutating a value returned from
the cache cannot corrupt the cached copy — necessary because the "cache" is a live PHP array in the
same process. A persistent backend serializes instead and gets the same isolation for free. 🟢

**`$expire` is ignored** by the default implementation. It is accepted in every signature and
discarded, because a request-scoped cache never outlives its TTL. Only a persistent drop-in honors it.

**`wp_cache_supports()` (`cache.php:314`)** — a feature-detection shim returning `true` for
`add_multiple`, `set_multiple`, `get_multiple`, `delete_multiple`, `flush_runtime`, `flush_group`
and `false` for anything else. Callers must feature-detect because a drop-in written against an
older WordPress may lack these methods.

### Business rules 🟢

| # | Rule | Location |
|---|------|----------|
| BR-CACHE-01 | The default object cache is request-scoped only; nothing survives the response. | `class-wp-object-cache.php:33` |
| BR-CACHE-02 | Under multisite, keys in non-global groups are prefixed with `"{$blog_id}:"`. Global groups are not. | `class-wp-object-cache.php:311` |
| BR-CACHE-03 | An invalid key (not int, not non-empty string) fails with `_doing_it_wrong()` and returns `false`. | `class-wp-object-cache.php:140` |
| BR-CACHE-04 | A cached `null` is a genuine hit, distinguished from a miss by `array_key_exists()`. | `class-wp-object-cache.php:178` |
| BR-CACHE-05 | Objects are cloned on `set()` and again on `get()`. | `class-wp-object-cache.php:314, 380` |
| BR-CACHE-06 | `$expire` is accepted and ignored by the default implementation. | `class-wp-object-cache.php:301` |
| BR-CACHE-07 | `add()` respects `wp_suspend_cache_addition()`; `set()` does not. | `class-wp-object-cache.php:199` |
| BR-CACHE-08 | An empty `$group` becomes `'default'`. | `class-wp-object-cache.php:306` |
| BR-CACHE-09 | `counts`, `plugins`, `theme_json` and `themes` are declared non-persistent. | `wp-includes/load.php:928` |

|---|---------|-----------|
| F-CACHE-01 | The default cache being non-persistent means **most WordPress installs run with no real caching**. Performance characteristics observed on a default install do not transfer to one with Redis or Memcached. | 🟢 |
| F-CACHE-02 | The `object-cache.php` drop-in is an implicit interface with no formal contract. `cache-compat.php` exists specifically to polyfill drop-ins that predate newer methods. | 🟢 |
| F-CACHE-03 | Cache correctness for `false` and `null` values depends on callers using `$found` and on `_exists()`'s `array_key_exists()` arm. Callers that check `if ( false === $value )` re-query on every legitimately-`false` cached value. | 🟢 |
| F-CACHE-04 | Multisite cache isolation is a string prefix, so a drop-in that ignores `switch_to_blog()` leaks data across sites. | 🟢 |

## A6. `metadata`

**Purpose.** The generic attribute system. One implementation serves posts, comments, terms, users
and blogs, driven entirely by a `$meta_type` string that resolves to a table name.

**Primary files:** `wp-includes/meta.php` (~1,850 lines),
`wp-includes/class-wp-metadata-lazyloader.php`, `wp-includes/class-wp-meta-query.php`

### The type-to-table mapping 🟢

```php
function _get_meta_table( $type ) {
    global $wpdb;
    $table_name = $type . 'meta';
    if ( empty( $wpdb->$table_name ) ) return false;
    return $wpdb->$table_name;
}
```

`'post'` → `$wpdb->postmeta`, `'user'` → `$wpdb->usermeta`, `'comment'` → `$wpdb->commentmeta`,
`'term'` → `$wpdb->termmeta`, `'blog'` → `$wpdb->blogmeta`. The object-id column is derived as
`sanitize_key($meta_type . '_id')`.

**This is string-driven dispatch onto SQL identifiers.** `sanitize_key()` and the `$wpdb->$table_name`
property lookup are the only things preventing an arbitrary `$meta_type` from reaching the query.
A `$meta_type` with no matching `wpdb` property returns `false` and the operation aborts — the guard
holds, but it is a whitelist by property existence rather than an explicit list. 🟢

**Table shape** (identical for all five): `meta_id` (`umeta_id` for users), `{type}_id`, `meta_key`,
`meta_value` (LONGTEXT). No type column, no index on `meta_value`.

### Algorithms 🟢

**`add_metadata()` (`meta.php:40`)**

```
validate: meta_type, meta_key, numeric object_id → else false
object_id = absint(); 0 → false
table = _get_meta_table(); false → false
meta_subtype = get_object_subtype($meta_type, $object_id)
meta_key   = wp_unslash($meta_key)          ← input arrives slashed (see F-BOOT-05)
meta_value = wp_unslash($meta_value)
meta_value = sanitize_meta($meta_key, $meta_value, $meta_type, $meta_subtype)
$check = apply_filters("add_{$meta_type}_metadata", null, …)
   → if !== null, RETURN it (full short-circuit)
if $unique:
    SELECT COUNT(*) FROM $table WHERE meta_key = %s AND $column = %d
    → non-zero, RETURN FALSE                ← check-then-insert, NOT atomic
meta_value = maybe_serialize($meta_value)
do_action("add_{$meta_type}_meta", …)
$wpdb->insert(...)
invalidate cache; do_action("added_{$meta_type}_meta", …)
```

**The `$unique` check is a race.** `SELECT COUNT(*)` followed by `INSERT` with no unique index on
`(object_id, meta_key)` means two concurrent requests can both pass the check and both insert. There
is no database-level constraint to catch it. 🟢

**`get_metadata_raw()` (`meta.php:628`)**

```
$check = apply_filters("get_{$meta_type}_metadata", null, …)
   → if !== null: return $single && is_array($check) ? $check[0] : $check
$meta_cache = wp_cache_get($object_id, "{$meta_type}_meta")
   → miss: update_meta_cache($meta_type, [$object_id])
if !$meta_key: return the whole meta_cache
if isset($meta_cache[$meta_key]):
    $single ? maybe_unserialize($meta_cache[$meta_key][0])
            : array_map('maybe_unserialize', $meta_cache[$meta_key])
return null
```

Note the cache stores **all** meta for an object as one entry. Reading one meta key loads every meta
row for that object. For a post with hundreds of meta rows, `get_post_meta($id, 'small_key', true)`
pulls the entire set into memory.

**`update_meta_cache()` (`meta.php:1137`)** — the bulk primer:

1. Coerce `$object_ids` to ints (with a `preg_replace('|[^0-9,]|', '', …)` sanitize when passed as a
   string).
2. `update_{$meta_type}_metadata_cache` filter can short-circuit.
3. `wp_cache_get_multiple()` to find which ids are already cached.
4. For the remainder: one query, `WHERE {$column} IN ({$id_list}) ORDER BY meta_id ASC`
   (`umeta_id` for users).
5. Group by object id and meta key into `array<id, array<key, value[]>>`.

This is the N+1 defense: `WP_Query` primes the meta cache for every post in the loop with **one**
query.

**`get_metadata()` vs `get_metadata_raw()` vs `get_metadata_default()`** — a three-function split
added so that a registered default (`register_meta(..., ['default' => …])`) can be returned when no
row exists, without the raw reader having to know about the registry. `filter_default_metadata()`
(line 1584) bridges them via the `get_{$meta_type}_metadata` filter.

**`is_protected_meta()` (`meta.php:1312`)**

```php
$sanitized_key = preg_replace( "/[^\x20-\x7E\p{L}]/", '', $meta_key );
$protected     = strlen($sanitized_key) > 0 && '_' === $sanitized_key[0];
return apply_filters( 'is_protected_meta', $protected, $meta_key, $meta_type );
```

A key is protected when, **after stripping every character that is not printable ASCII or a Unicode
letter**, it starts with `_`. The strip exists so that a key like `"\0_wp_secret"` or
`"​_wp_secret"` (zero-width space) cannot smuggle a protected key past the check by prefixing an
invisible character. Protected meta is hidden from the custom-fields UI and from REST. 🟢

**`sanitize_meta()` (`meta.php:1342`)** — dispatches to the most specific registered filter:
`sanitize_{$object_type}_meta_{$meta_key}_for_{$object_subtype}` if one exists, otherwise
`sanitize_{$object_type}_meta_{$meta_key}`.

**`register_meta()` (`meta.php:1435`)** — registers `type`, `description`, `single`,
`default`, `sanitize_callback`, `auth_callback`, `show_in_rest`, and optionally an
`object_subtype`. This is what exposes a meta key to the REST API and gives it a typed default.

**Lazy loading (`class-wp-metadata-lazyloader.php`)** — queues term and comment meta to be primed on
first access rather than eagerly, via `wp_metadata_lazyloader()`.

### Business rules 🟢

| # | Rule | Location |
|---|------|----------|
| BR-META-01 | `$meta_type` resolves to `"{$type}meta"` on `$wpdb`; an unknown type returns `false` and aborts. | `meta.php:1290` |
| BR-META-02 | Meta keys and values are `wp_unslash()`ed on write — input arrives slashed. | `meta.php:57` |
| BR-META-03 | `$unique = true` is enforced by `SELECT COUNT(*)` before insert, with **no unique index**. Concurrent writers can both succeed. | `meta.php:65` |
| BR-META-04 | A meta key is protected when its key, stripped of non-printable and non-letter characters, begins with `_`. | `meta.php:1312` |
| BR-META-05 | All meta for an object is cached as a single entry; reading one key loads them all. | `meta.php:645` |
| BR-META-06 | `$single = true` returns `$values[0]`; `false` returns the full array. A missing key returns `''` under `$single`, `[]` otherwise (via `get_metadata()`). | `meta.php:601` |
| BR-META-07 | Every meta value passes `sanitize_meta()`, dispatching to the subtype-specific filter when one is registered. | `meta.php:59` |
| BR-META-08 | Values are `maybe_serialize()`d on write and `maybe_unserialize()`d on read — arrays and objects round-trip transparently. | `meta.php:74` |
| BR-META-09 | `add_{$meta_type}_metadata` / `get_…` / `update_…` / `delete_…` filters returning non-`null` fully replace the operation. | `meta.php:61, 636` |

|---|---------|-----------|

| F-META-02 | No unique index backs `$unique = true`. The guarantee is advisory, and duplicate meta rows are a known real-world outcome. | 🟢 |
| F-META-03 | `meta_value` is `LONGTEXT` with no index. Every `meta_query` filter is a full scan or a join on `meta_key` only — the root cause of most slow WordPress queries. | 🟢 |
| F-META-04 | Whole-object meta caching turns any single-key read into a full meta load, which is a win in loops and a loss for objects with large meta sets. | 🟢 |
| F-META-05 | The `_`-prefix protection convention is enforced only in UI and REST layers, never at the storage layer. Protected meta is a display convention, not an access control. | 🟢 |
| F-META-06 | The character-stripping in `is_protected_meta()` is a deliberate anti-smuggling measure, indicating this check has been attacked before. | 🟡 |

### The 11 built-in post statuses 🟢

`publish`, `future`, `draft`, `pending`, `private`, `trash`, `auto-draft`, `inherit`,
`request-pending`, `request-confirmed`, `request-failed`

- `inherit` — used by attachments and revisions; the effective status is the parent's.
- `auto-draft` — a post row created before the user has typed anything; garbage-collected after 7 days.
- `future` — scheduled; see the transition rules below.

### Algorithms 🟢

#### Status/date coupling in `wp_insert_post()` (`post.php:4598`)

The single most consequential rule in the module. After resolving dates:

```
if ( 'publish' === $post_status ) {
    if ( strtotime($post_date_gmt) - strtotime($now) >= MINUTE_IN_SECONDS )
        $post_status = 'future';          ← publishing with a future date SCHEDULES it
} elseif ( 'future' === $post_status ) {
    if ( strtotime($post_date_gmt) - strtotime($now) < MINUTE_IN_SECONDS )
        $post_status = 'publish';         ← a scheduled post whose time arrived PUBLISHES
}
```

**Status is derived from the date, not independent of it.** The 60-second threshold means a post
dated 30 seconds in the future publishes immediately. Callers cannot force `publish` with a future
date, nor `future` with a past one. 🟢

Other insert-time rules visible in the same function:

- An `attachment` whose status is not `inherit`, `private`, `trash` or `auto-draft` is rejected.
- `post_date_gmt` is left as `0000-00-00 00:00:00` for drafts — which is why `NO_ZERO_DATE` had to be
  stripped from the SQL mode (see BR-DB-10). The two rules are causally linked.
- Slugs are **not** generated for `draft`, `pending` or `auto-draft`.

#### `wp_unique_post_slug()` (`post.php:5560`) — three distinct uniqueness scopes

An early exit first: `draft`, `pending`, `auto-draft`, revisions with `inherit`, and `user_request`
all return the slug untouched (no uniqueness enforced).

Then one of three strategies:

| Post type | Uniqueness scope | Query |
|-----------|-----------------|-------|
| `attachment` | **across all post types** | `WHERE post_name = %s AND ID != %d` |
| hierarchical (`page`, …) | within `(type, parent)`, plus attachments | `WHERE post_name = %s AND post_type IN (%s,'attachment') AND ID != %d AND post_parent = %d` |
| flat (`post`, CPTs) | within the post type | `WHERE post_name = %s AND post_type = %s AND ID != %d` |

`nav_menu_item` returns early — menu items never need unique slugs.

**Reserved-slug collisions** are also rejected, forcing a suffix:

- any registered feed slug (`$wp_rewrite->feeds`)
- the literal `embed`
- for hierarchical types, `^(pagination_base)?\d+$` — a page named `2` would collide with
  `/parent/2/` pagination
- for flat types, slugs that would conflict with **date archives** (a post named `2024` under
  `/%year%/` permalinks)

Resolution is a `do … while` loop appending `-2`, `-3`, … with `_truncate_post_slug($slug, 200 - strlen($suffix) - 1)`
so the result never exceeds 200 bytes. **One query per iteration** — a slug with 50 existing variants
costs 50 queries. 🟢

#### Status transitions (`post.php:5912`, `8154`)

`wp_transition_post_status()` fires exactly two hooks:

```php
do_action( 'transition_post_status', $new_status, $old_status, $post );
do_action( "{$old_status}_to_{$new_status}", $post );
```

The dynamic second hook is why `draft_to_publish`, `publish_to_trash`, `new_to_publish` etc. exist
without being individually declared anywhere. Any status pair generates a valid hook name.

`_transition_post_status()` is core's own callback and performs the side effects:

1. On any transition **into** `publish` from a non-publish status with an empty GUID: write
   `get_permalink()` into the `guid` column. (The GUID is a permanent identifier, not a URL — but it
   is initialized *from* the permalink, which is why changing permalink structure does not change
   existing GUIDs.)
2. If either side is `publish`: invalidate `lastpostmodified` / `lastpostdate` caches for all three
   timezones (`server`, `gmt`, `blog`) plus the per-post-type variant.
3. On any status change: invalidate the post-count caches (`counts` group — declared non-persistent,
   see BR-CACHE-09).
4. **Unconditionally** `wp_clear_scheduled_hook('publish_future_post', [$post->ID])` — with the
   explicit comment *"in case the post status bounced from future to draft"*. A scheduled publish is
   cancelled on every transition, then re-scheduled if the new status is still `future`.

## B2. `query-and-loop`

**Purpose.** Turn a URL into a set of posts. `WP` parses the request into query variables,
`WP_Query` compiles those into SQL, and "The Loop" iterates the result. This is WordPress's
front controller, router and ORM query layer combined.

**Primary files:** `wp-includes/class-wp.php`, `wp-includes/class-wp-query.php` (~4,900 lines),
`wp-includes/query.php`, `wp-includes/class-wp-meta-query.php`, `wp-includes/class-wp-tax-query.php`,
`wp-includes/class-wp-date-query.php`

### The request pipeline 🟢

`WP::main()` (`class-wp.php:818`) is remarkably short for what it does:

```php
public function main( $query_args = '' ) {
    $this->init();                          // set up the current user
    $parsed = $this->parse_request( $query_args );
    if ( $parsed ) {
        $this->query_posts();               // $wp_the_query->query( $this->query_vars )
        $this->handle_404();
        $this->register_globals();          // $posts, $post, $wp_query into globals
    }
    $this->send_headers();
    do_action_ref_array( 'wp', array( &$this ) );
}
```

**`parse_request()` returning `false` skips the query entirely** — that is what the
`do_parse_request` filter is for, and how REST and admin-ajax requests avoid running the main query.

### Query variable classification 🟢

`WP` maintains two whitelists (`class-wp.php:18`, `28`):

**`$public_query_vars`** (48) — settable from the URL query string:
`m`, `p`, `posts`, `w`, `cat`, `withcomments`, `withoutcomments`, `s`, `search`, `exact`,
`sentence`, `calendar`, `page`, `paged`, `more`, `tb`, `pb`, `author`, `order`, `orderby`, `year`,
`monthnum`, `day`, `hour`, `minute`, `second`, `name`, `category_name`, `tag`, `feed`,
`author_name`, `pagename`, `page_id`, `error`, `attachment`, `attachment_id`, `subpost`,
`subpost_id`, `preview`, `robots`, `favicon`, `taxonomy`, `term`, `cpage`, `post_type`, `embed`

**`$private_query_vars`** (27) — settable only in PHP, **never** from the URL:
`offset`, `posts_per_page`, `posts_per_archive_page`, `showposts`, `nopaging`, `post_type`,
`post_status`, `category__in`, `category__not_in`, `category__and`, `tag__in`, `tag__not_in`,
`tag__and`, `tag_slug__in`, `tag_slug__and`, `tag_id`, `post_mime_type`, `perm`,
`comments_per_page`, `post__in`, `post__not_in`, `post_parent`, `post_parent__in`,
`post_parent__not_in`, `title`, `fields`

**This split is a security boundary.** If `post_status` were public, any visitor could append
`?post_status=draft` and read unpublished content. `add_query_var()` moves a variable into the public
list — which is why a careless `add_query_var('post_status')` is a real vulnerability class. 🟢

### Algorithms 🟢

#### `handle_404()` (`class-wp.php:724`) — when *not* to 404

The logic is a series of exemptions, and the default is to 404:

```
pre_handle_404 filter returns non-false      → return (fully overridden)
already is_404()                             → return
$set_404 = true
if is_admin() || is_robots() || is_favicon() → $set_404 = false
elseif ( $wp_query->posts non-empty ):
    $content_found = true
    if is_singular() and query_vars['page'] set:
        if post_content contains '<!--nextpage-->':
            $content_found = (int)$page <= substr_count(content,'<!--nextpage-->') + 1
        else:
            $content_found = false      ← ?page=2 on an unpaginated post is a 404
    if is_posts_page and query_vars['page'] set:
        $content_found = false          ← the posts page never supports <!--nextpage-->
    if $content_found → $set_404 = false
elseif ( ! is_paged() ):                ← paged queries with no posts ALWAYS 404
    $set_404 = false if:
        is_author() && numeric author > 0 && is_user_member_of_blog(author)
        || (is_tag()||is_category()||is_tax()||is_post_type_archive()) && get_queried_object()
        || is_home() || is_search() || is_feed()
if $set_404 → set_404(); status_header(404); nocache_headers()
```

Two rules worth stating explicitly:

- **An empty author/term/post-type archive is a 200, not a 404**, provided the object exists. An
  author with zero posts is a valid page.
- **An empty *paged* archive (`/page/5/`) is always a 404**, because there is no object-existence
  exemption on the `is_paged()` branch.

#### `WP_Query::get_posts()` — the SQL compiler

Nearly 1,800 lines. It assembles seven clause strings (`fields`, `join`, `where`, `groupby`,
`orderby`, `distinct`, `limits`) and exposes **every one of them to filters, twice**:

| Clause | Early filter | Late filter (`_request`) |
|--------|-------------|--------------------------|
| SELECT | `posts_fields` | `posts_fields_request` |
| JOIN | `posts_join`, `posts_join_paged` | `posts_join_request` |
| WHERE | `posts_where`, `posts_where_paged` | `posts_where_request` |
| GROUP BY | `posts_groupby` | `posts_groupby_request` |
| ORDER BY | `posts_orderby` | `posts_orderby_request` |
| DISTINCT | `posts_distinct` | `posts_distinct_request` |
| LIMIT | `post_limits` | `post_limits_request` |
| all at once | `posts_clauses` | `posts_clauses_request` |
| whole SQL | — | `posts_request` |

Plus `posts_pre_query` (bypass the query completely, return your own posts), `posts_results`
(mutate the raw rows), and `the_posts` (mutate the final array). **34 distinct filters** in this one
method.

The `_request` variants exist because the early filters run before the "is this a suppressed-filters
query" check; `suppress_filters => true` skips the early set but not the late set.

#### The split query (`class-wp-query.php:3380`)

```php
$is_unfiltered_query = $old_request === $this->request && "{$wpdb->posts}.*" === $fields;

$split_the_query = $is_unfiltered_query && (
    wp_using_ext_object_cache()
    || ( ! empty($limits) && $query_vars['posts_per_page'] < 500 )
);
$split_the_query = apply_filters( 'split_the_query', $split_the_query, $this, $old_request, $clauses );
```

When true, WordPress runs `SELECT ID FROM …` and then hydrates each post from the object cache
individually, instead of `SELECT wp_posts.* FROM …`. The trade: many small cacheable reads versus one
large uncacheable result set.

**It only applies to unfiltered queries** — if any plugin altered the SQL, `$old_request !== $this->request`
and the optimization is disabled, because the filtered SQL may no longer be a simple post selection.
The `posts_per_page < 500` bound prevents pathological hydration loops when there is no persistent
cache. 🟢

#### `set_found_posts()` (`class-wp-query.php:3692`)

```
if no_found_rows OR posts is an empty array → return (found_posts stays 0)
if limits non-empty:
    found_posts = (int) $wpdb->get_var( apply_filters('found_posts_query', 'SELECT FOUND_ROWS()') )
else:
    found_posts = count(posts) | 0 if null | 1 otherwise
found_posts = apply_filters('found_posts', found_posts)
if limits: max_num_pages = ceil( found_posts / posts_per_page )
```

`SELECT FOUND_ROWS()` requires `SQL_CALC_FOUND_ROWS` in the main query, which forces MySQL to count
the full result set — **the single most expensive thing `WP_Query` does**. `'no_found_rows' => true`
is the standard fix for queries that do not need pagination.

#### Search term parsing (`class-wp-query.php:1556`)

```
for each term:
    if the term is "quoted"  → trim quotes, KEEP surrounding spaces (exact-match intent)
    else                     → trim quotes and spaces
    skip if empty
    skip if a single a-z or '-' character
    skip if it is a stopword (locale-provided, filterable)
```

Terms surviving this become `LIKE '%term%'` conditions. **Every search is a leading-wildcard LIKE**,
which cannot use an index. There is no full-text search in core.

#### The Loop (`class-wp-query.php:3768`, `3844`)

`the_post()` performs a **lazy cache prime on first iteration only** (`if (! $this->in_the_loop)`):

- `fields => 'all'` — post objects already present, nothing to do.
- `fields => 'ids'` — the ids *are* the results.
- otherwise — reduce partial rows to ids, then `_prime_post_caches($ids, $update_post_term_cache, $update_post_meta_cache)`
  and re-hydrate via `array_map('get_post', $ids)`.
- always `update_post_author_caches($post_objects)`.

This is the N+1 defense at the loop level: one bulk meta query, one bulk term query, one bulk author
query, regardless of how many posts the loop touches.

`have_posts()` handles loop termination and **fires `loop_end` then auto-rewinds**, which is why a
second `while (have_posts())` over the same query works without an explicit `rewind_posts()`. When
the query returned nothing it fires `loop_no_results` instead.

### Business rules 🟢

| # | Rule | Location |

## B3. `taxonomy-and-terms`

**Purpose.** Classify objects. A three-table design (`wp_terms`, `wp_term_taxonomy`,
`wp_term_relationships`) that separates the *word* from the *classification* from the *assignment* —
the most normalized part of the WordPress schema, and the source of its most confusing API.

**Primary files:** `wp-includes/taxonomy.php` (~5,100 lines), `wp-includes/class-wp-taxonomy.php`,
`wp-includes/class-wp-term.php`, `wp-includes/class-wp-term-query.php`,
`wp-includes/class-wp-tax-query.php`, `wp-includes/category.php`

### The three-table design 🟢

| Table | Holds | Key |
|-------|-------|-----|
| `wp_terms` | `term_id`, `name`, `slug`, `term_group` | the *word* — "News" |
| `wp_term_taxonomy` | `term_taxonomy_id`, `term_id`, `taxonomy`, `description`, `parent`, `count` | the word *as a classification* — "News as a category" |
| `wp_term_relationships` | `object_id`, `term_taxonomy_id`, `term_order` | the *assignment* — "post 42 is in News-as-a-category" |

The consequence: **one term can exist in multiple taxonomies with one `term_id` but different
`term_taxonomy_id`s**, and it is `term_taxonomy_id` (`tt_id`), not `term_id`, that actually links to
objects. Nearly every taxonomy bug in the wild is a confusion between the two.

### The 8 built-in taxonomies 🟢

`create_initial_taxonomies()` (`taxonomy.php:25`) registers:

| Taxonomy | Hierarchical | Applies to |
|----------|-------------|------------|
| `category` | ✅ | `post` |
| `post_tag` | ❌ | `post` |
| `nav_menu` | ❌ | `nav_menu_item` |
| `link_category` | ❌ | `link` |
| `post_format` | ❌ | `post` |
| `wp_theme` | ❌ | `wp_template`, `wp_template_part`, `wp_global_styles` |
| `wp_template_part_area` | ❌ | `wp_template_part` |
| `wp_pattern_category` | ❌ | `wp_block` |

Note `post_format` and `wp_theme`: like post types, taxonomies get repurposed as generic tagging
infrastructure rather than being modeled as columns.

### Algorithms 🟢

#### `wp_insert_term()` (`taxonomy.php:2458`) — insert-then-detect-duplicate

The validation chain is long and every step returns a distinct `WP_Error`:

```
!taxonomy_exists            → 'invalid_taxonomy'
pre_insert_term filter (may return WP_Error)
is_int($term) && $term === 0 → 'invalid_term_id'
trim($term) === ''           → 'empty_term_name'
parent > 0 && !term_exists   → 'missing_parent'
description coerced to (string)   ← "to avoid database errors" on null
sanitize_term(…, 'db')
name = wp_unslash(...)
name === '' AFTER sanitization → 'invalid_term_name'   ← checked twice, deliberately
slug = provided ?: sanitize_title(name)
```

**Aliasing (`alias_of`)** uses `term_group`: if the alias target already has a group, join it;
otherwise `SELECT MAX(term_group) FROM wp_terms + 1` and move the target into that new group.
A synonym mechanism that predates term meta and is essentially unused today. 🟡

**Then the unusual part.** WordPress inserts the row *first*, then looks for a duplicate:

```
INSERT INTO wp_terms
$term_id = insert_id
SELECT tt.term_taxonomy_id ... WHERE tt.taxonomy = %s AND t.term_id = %d
   → if found, the term already existed in this taxonomy; return it
INSERT INTO wp_term_taxonomy
$tt_id = insert_id
SELECT ... WHERE t.slug = %s AND tt.parent = %d AND tt.taxonomy = %s
           AND t.term_id < %d AND tt.term_taxonomy_id != %d
   → duplicate found (an OLDER row with the same slug/parent/taxonomy):
        DELETE the rows just inserted
        return the pre-existing term_id / tt_id
```

The `t.term_id < %d` condition means **only an older row counts as the duplicate** — the row just
created always loses. This is a last-writer-loses reconciliation that makes concurrent identical
inserts converge on one term instead of erroring. Insert-then-check rather than check-then-insert,
because there is no unique constraint to rely on. 🟢

#### `wp_set_object_terms()` (`taxonomy.php:2851`)

```
!taxonomy_exists → WP_Error
normalize $terms to an array
if !$append: $old_tt_ids = current tt_ids   (for later diff/removal)
foreach term:
    trim === '' → skip
    $term_info = term_exists($term, $taxonomy)
    if !$term_info:
        if is_int($term) → skip        ← a numeric id that does not exist is IGNORED
        else → wp_insert_term($term, $taxonomy)     ← a STRING creates the term
    WP_Error → return it
    SELECT term_taxonomy_id FROM wp_term_relationships
        WHERE object_id = %d AND term_taxonomy_id = %d
    → already related, skip
    INSERT the relationship (fires add_term_relationship / added_term_relationship)
if $new_tt_ids: wp_update_term_count($new_tt_ids, $taxonomy)
[if !$append: delete relationships in $old_tt_ids but not in $tt_ids]
```

**A string creates a term; an integer does not.** `wp_set_object_terms($id, 'Nonexistent', 'category')`
creates the category. `wp_set_object_terms($id, 9999, 'category')` silently does nothing. This
asymmetry is a frequent source of silent data loss. 🟢

Note also **one existence query per term** — assigning 50 terms costs 50 queries before any insert.

#### Deferred term counting (`taxonomy.php:3587`)

```php
function wp_update_term_count( $terms, $taxonomy, $do_deferred = false ) {
    static $_deferred = array();
    if ( $do_deferred ) { flush every taxonomy's queue via wp_update_term_count_now(); }
    if ( wp_defer_term_counting() ) {
        $_deferred[$taxonomy] = array_unique( array_merge( $_deferred[$taxonomy], $terms ) );
        return true;
    }
    return wp_update_term_count_now( $terms, $taxonomy );
}
```

A static accumulator. `wp_defer_term_counting(true)` before a bulk import collapses thousands of
count recalculations into one pass. `wp_update_term_count_now()` honors the taxonomy's
`update_count_callback`, which is how `post_tag` and attachments count differently.

#### `_pad_term_counts()` (`taxonomy.php:4085`) — hierarchical count rollup

Hierarchical taxonomies display a parent's count **including its descendants**, but the stored
`count` column only holds direct assignments. Padding computes the rest at read time:

1. Bail unless the taxonomy is hierarchical and `_get_term_hierarchy()` is non-empty.
2. One query joining `wp_term_relationships` to `wp_posts`, filtered to the taxonomy's object types
   and `post_status = 'publish'`.
3. Build `$term_items[term_id][object_id] = touch_count`.
4. For each term, walk up the `parent` chain and copy each object id into every ancestor's bucket —
   **with a cycle guard**: `if ( in_array($parent, $ancestors, true) ) break;`.
5. Transfer the deduplicated bucket sizes onto the term objects (by reference).

Using an object-id-keyed map rather than a running sum is what prevents double-counting a post
assigned to both a child and its parent. The cycle guard is necessary because `parent` is a plain
column with no referential integrity — a corrupted hierarchy would otherwise hang the request. 🟢

**Note the hardcoded `post_status = 'publish'`.** Term counts reflect published content only, which
is why draft posts do not increment a category's count.

#### `wp_unique_term_slug()` (`taxonomy.php:3136`)

Appends `-2`, `-3`, … on collision, with a special case: in a hierarchical taxonomy, a term whose
parent differs may keep a colliding slug, because the full path disambiguates it.

### Business rules 🟢

| # | Rule | Location |
|---|------|----------|
| BR-TAX-01 | Objects are linked by `term_taxonomy_id`, never `term_id`. One `term_id` may serve several taxonomies. | schema |
| BR-TAX-02 | The term name is validated for emptiness **twice** — before and after sanitization. | `taxonomy.php:2470, 2495` |
| BR-TAX-03 | A `null` description is coerced to `''` to avoid a database error. | `taxonomy.php:2487` |
| BR-TAX-04 | A non-existent parent term id rejects the insert with `missing_parent`. | `taxonomy.php:2481` |
| BR-TAX-05 | Duplicate detection happens **after** insert; only a row with a *lower* `term_id` counts as the duplicate, and the newly inserted rows are deleted. | `taxonomy.php:2645` |
| BR-TAX-06 | In `wp_set_object_terms()`, a term passed as a **string** that does not exist is created; passed as an **integer**, it is silently skipped. | `taxonomy.php:2884` |
| BR-TAX-07 | Assigning a term already related to the object is a no-op (checked with one query per term). | `taxonomy.php:2893` |

### Findings

| # | Finding | Confidence |
|---|---------|-----------|
| F-TAX-01 | The `term_id` / `term_taxonomy_id` split is correct normalization that the API then obscures: most functions take `term_id` while the actual relationships use `tt_id`. This is the module's dominant defect source. | 🟢 |

## B4. `comments`

**Purpose.** Accept, moderate and display reader responses, plus trackbacks and pingbacks. The
moderation pipeline is the most rule-dense piece of business logic in WordPress core — a spam filter
expressed as a sequence of option-driven checks.

**Primary files:** `wp-includes/comment.php` (~4,000 lines), `wp-includes/class-wp-comment.php`,
`wp-includes/class-wp-comment-query.php`, `wp-includes/comment-template.php`, `wp-comments-post.php`

### The submission pipeline 🟢

```
wp-comments-post.php
  → wp_handle_comment_submission( $_POST )        validates post is open, builds commentdata
    → wp_new_comment( $commentdata )
      → wp_allow_comment( $commentdata )          ① duplicate ② flood ③ approval decision
        → wp_check_comment_data( $commentdata )
          → check_comment(...)                    moderation rules → 1 or 0
          → wp_check_comment_disallowed_list(...) → 'trash' or 'spam'
      → wp_insert_comment( $commentdata )
      → wp_update_comment_count( $post_id )
```

### Algorithms 🟢

#### ① Duplicate detection (`comment.php:752`)

A query built by concatenating three `prepare()` fragments:

```sql
SELECT comment_ID FROM wp_comments
WHERE comment_post_ID = %d
  AND comment_parent  = %s
  AND comment_approved != 'trash'
  AND ( comment_author = %s
        [AND comment_author_email = %s]   -- only when an email was supplied
      )
  AND comment_content = %s
LIMIT 1
```

A hit fires `comment_duplicate_trigger` and terminates with **HTTP 409** (`wp_die()`, or `die()` under
AJAX, or a `WP_Error` when `$wp_error` is set). Note that trashed comments are excluded, so
re-submitting a comment that was trashed is allowed. 🟢

#### ② Flood control (`comment.php:909`)

`wp_check_comment_flood()` is registered onto the `wp_is_comment_flood` filter by
`check_comment_flood_db()` — it is core's own opt-in callback, not hardwired.

```
if $is_flood already true                              → trust the earlier callback
if current_user_can('manage_options') or 'moderate_comments' → NOT throttled
$hour_ago = now - HOUR_IN_SECONDS
logged in ? check_column = user_id, user = current_user_id
          : check_column = comment_author_IP, user = ip
SELECT comment_date_gmt FROM wp_comments
  WHERE comment_date_gmt >= $hour_ago
    AND ( {check_column} = %s OR comment_author_email = %s )
  ORDER BY comment_date_gmt DESC LIMIT 1
if a previous comment exists in that hour:
    $flood_die = apply_filters( 'comment_flood_filter', FALSE, $last, $new )
    if $flood_die → 429
```

**The default is `false`.** Core finds the last comment within the hour and then asks a filter whether
that constitutes flooding — and nothing in core answers yes. Flood control is a *hook point with a
query attached*, not an enforced rate limit. Any actual throttling comes from a plugin. 🟢

#### ③ Approval decision (`wp_check_comment_data()`, `comment.php:1352`)

```
if user_id set:
    $post_author = SELECT post_author FROM wp_posts WHERE ID = %d
if user_id === post_author OR user->has_cap('moderate_comments'):
    $approved = 1                       ← "The author and the admins get respect"
else:
    $approved = check_comment(...) ? 1 : 0
    if wp_check_comment_disallowed_list(...):
        $approved = EMPTY_TRASH_DAYS ? 'trash' : 'spam'
return apply_filters( 'pre_comment_approved', $approved, $comment_data )
```

The disallowed-list check runs **after** the approval decision and overrides it — a comment can be
approved by every moderation rule and still be trashed by one disallowed word. And whether it lands
in `trash` or `spam` depends on `EMPTY_TRASH_DAYS`: with trash disabled, disallowed comments are
marked spam instead. 🟢

#### `check_comment()` (`comment.php:43`) — the moderation rules

Returns `true` = auto-approve, `false` = hold for moderation. Evaluated in order:

| # | Rule | Option |
|---|------|--------|
| 1 | Manual moderation on → **hold everything**, skip all further checks | `comment_moderation === '1'` |
| 2 | Link count: `preg_match_all('/<a [^>]*href/i', $comment)` ≥ max → hold | `comment_max_links` |
| 3 | For each keyword in the list, `#{preg_quote(word)}#iu` tested against **author, email, url, content, IP and user agent** → any match holds | `moderation_keys` |
| 4 | Previously-approved requirement: the commenter must have an earlier approved comment (matched by `user_id` when registered, otherwise by author name **and** email) → else hold | `comment_previously_approved === '1'` |

Two details worth flagging:

- The comment text passed to the keyword check has already been through `apply_filters('comment_text', …)`,
  so plugins altering comment rendering also alter what moderation sees. 🟢
- The keyword pattern is `#…#iu` — case-insensitive **and** Unicode. `preg_quote()` prevents a
  keyword from acting as a regex, but a substring match means the keyword `press` holds any comment
  containing "WordPress". 🟢

#### Length validation (`comment.php:1319`)

`wp_check_comment_data_max_lengths()` measures against the real column widths from
`wp_get_comment_fields_max_lengths()`. Note the measurement units differ:
`comment_author` and `comment_content` use `mb_strlen($v, '8bit')` (byte length, correct for a
column limit), while `comment_author_email` and `comment_author_url` use plain `strlen()`. Each
over-length field returns a distinct `WP_Error` with **HTTP 200**, not 400 — the submission form
re-renders rather than erroring. 🟢

#### Comment count deferral (`comment.php:3071`)

`wp_update_comment_count( $post_id, $do_deferred )` uses the same static-accumulator pattern as
term counting (BR-TAX-09), so bulk comment imports do not recount per row.

### Data structures 🟢

`wp_comments` — 15 columns: `comment_ID`, `comment_post_ID`, `comment_author`,
`comment_author_email`, `comment_author_url`, `comment_author_IP`, `comment_date`,
`comment_date_gmt`, `comment_content`, `comment_karma`, `comment_approved`, `comment_agent`,
`comment_type`, `comment_parent`, `user_id`.

**`comment_approved` is not a boolean.** It is a `varchar` holding `'1'`, `'0'`, `'spam'`, `'trash'`
or `'post-trashed'`. `comment_karma` is a legacy integer with no core consumer. 🟡

`comment_type` distinguishes `comment`, `pingback` and `trackback`; `separate_comments()`
(`comment.php:999`) splits a mixed list by type for templates that display pings separately.

### Business rules 🟢

| # | Rule | Location |
|---|------|----------|
| BR-CMT-01 | A duplicate (same post, parent, author, email and content, excluding trashed) is rejected with HTTP 409. | `comment.php:754` |
| BR-CMT-02 | Users with `manage_options` or `moderate_comments` are never flood-throttled. | `comment.php:917` |

## B5. `media-and-attachments`

**Purpose.** Upload handling, image resizing, responsive image markup and media metadata. The largest
body of pure algorithmic code in WordPress — geometry, aspect-ratio matching and `srcset` generation.

**Primary files:** `wp-includes/media.php` (231 KB), `wp-includes/media-template.php`,
`wp-includes/class-wp-image-editor.php` + `-gd.php` + `-imagick.php`,
`wp-includes/class-avif-info.php`, `wp-admin/includes/image.php`

### Image editor selection 🟢

```php
$implementations = apply_filters( 'wp_image_editors',
    array( 'WP_Image_Editor_Imagick', 'WP_Image_Editor_GD' ) );

$cache_key = md5( serialize( array( $args, $implementations ) ) );
// memoized in the 'image_editor' cache group (a GLOBAL group — see BR-CACHE-09 list)

foreach ( $implementations as $implementation ) {
    if ( ! $implementation::test( $args ) )                        continue;
    if ( isset($args['mime_type']) && ! $implementation::supports_mime_type(...) ) continue;
    if ( isset($args['methods']) && array_diff($args['methods'], get_class_methods($implementation)) ) continue;

```

A capability-negotiation loop, not a static choice: Imagick is preferred, GD is the fallback, and the
decision is made **per operation** based on the mime types and methods actually required. The result
is cached by an md5 of the arguments. 🟢

### Algorithms 🟢

#### `image_resize_dimensions()` (`media.php:555`) — crop geometry

Guards first:

```
orig_w <= 0 || orig_h <= 0                          → false
dest_w <= 0 && dest_h <= 0                          → false
image_resize_dimensions filter (may return early)
upscale prevention:
    only dest_w given:  orig_w < dest_w             → false
    only dest_h given:  orig_h < dest_h             → false
    both given:  orig_w < dest_w && orig_h < dest_h → false
```

**WordPress never upscales.** Requesting a size larger than the original returns `false` and the
original is used.

The crop branch:

```
aspect_ratio = orig_w / orig_h
new_w = min(dest_w, orig_w);  new_h = min(dest_h, orig_h)
if !new_w: new_w = round(new_h * aspect_ratio)
if !new_h: new_h = round(new_w / aspect_ratio)

size_ratio = MAX( new_w/orig_w, new_h/orig_h )      ← max, so the crop COVERS the target
crop_w = round(new_w / size_ratio)
crop_h = round(new_h / size_ratio)

$crop defaults to ['center','center'] when not a 2-element array
x: 'left'→0 | 'right'→orig_w - crop_w | else floor((orig_w - crop_w)/2)
y: 'top' →0 | 'bottom'→orig_h - crop_h | else floor((orig_h - crop_h)/2)
```

`max()` for `size_ratio` is the crux: it produces a source rectangle that *covers* the destination
box (like CSS `object-fit: cover`), which is then scaled down. Using `min()` would letterbox instead.

#### `wp_image_matches_ratio()` (`media.php:738`) — fuzzy aspect matching

```php
if ( $source_width > $target_width ) {
    $constrained_size = wp_constrain_dimensions( $source_width, $source_height, $target_width );
    $expected_size    = array( $target_width, $target_height );
} else {
    $constrained_size = wp_constrain_dimensions( $target_width, $target_height, $source_width );
    $expected_size    = array( $source_width, $source_height );
}
$matched = wp_fuzzy_number_match( $constrained_size[0], $expected_size[0] )
        && wp_fuzzy_number_match( $constrained_size[1], $expected_size[1] );
```

It always scales the **larger** image down to the smaller one's width, then compares. The comparison
is deliberately fuzzy — *"if the image dimensions are within 1px of the expected size, we consider it
a match"* — because integer rounding during resize means a 3:2 crop of one size will not be exactly
3:2 at another. Without the 1px tolerance, most `srcset` candidates would be rejected. 🟢

#### `wp_calculate_image_srcset()` (`media.php:1444`)

For each registered size of the attachment:

1. Skip sizes whose file is not in the same directory as the source (an uploads-directory guard).
2. Identify whether this candidate *is* the `src` image (`$is_src`).
3. **Skip candidates wider than `max_srcset_image_width` (default 2048)** — unless the candidate is
   the src itself, which is always included regardless of width.
4. Include only candidates where `wp_image_matches_ratio()` holds.

The 2048 default exists so that huge originals do not end up as `srcset` candidates a browser might
actually download. The `$is_src` exemption guarantees the srcset always contains the image the `src`
attribute names. 🟢

#### `wp_filter_content_tags()` (`media.php:1987`)

Post-processes rendered content to inject `srcset`, `sizes`, `loading="lazy"`,
`decoding="async"` and `fetchpriority` into `<img>` and `<iframe>` tags. Works on the **output**
HTML, not on the stored content — which is why responsive behavior improves for old posts when
WordPress is upgraded. `wp_get_loading_optimization_attributes()` (`media.php:6150`) decides
per-element whether an image is likely above the fold and therefore should be eager-loaded with high
fetch priority.

### Registered image sizes 🟢

`thumbnail`, `medium`, `medium_large`, `large`, plus the big-image thresholds `1536x1536` and
`2048x2048`. Each upload generates every registered subsize, so **one upload writes N files**.
`wp_get_registered_image_subsizes()` (`media.php:930`) is the canonical list.

## B6. `embeds-oembed`

**Purpose.** Turn a bare URL on its own line into rich embedded content, and expose WordPress's own
posts as oEmbed providers.

**Primary files:** `wp-includes/class-wp-oembed.php`, `wp-includes/class-wp-embed.php`,
`wp-includes/embed.php`, `wp-includes/embed-template.php`,
`wp-includes/class-wp-oembed-controller.php`

### Resolution chain 🟢

```
WP_Embed::shortcode()  /  autoembed
  → check the oembed_cache post type (cached HTML keyed by URL + args)
  → WP_oEmbed::get_html( $url, $args )
      → get_provider( $url )            ① match against 59 built-in provider patterns
          → if no match and discovery is enabled:
             discover( $url )           ② fetch the URL, parse <link rel="alternate"
                                          type="application/json+oembed">
      → fetch( $provider, $url, $args )  ③ _fetch_with_format('json') then 'xml'
      → data2html( $data, $url )         ④ render by response type
  → cache the result as an oembed_cache post
```

### Algorithms 🟢

**Provider registry** — 59 built-in providers as `pattern => [endpoint, is_regex]` pairs, matched by
`preg_match()` against the URL. `sanitize_provider()` (`class-wp-oembed.php:285`) validates each
entry before use. Providers are extensible via `wp_oembed_add_provider()` and the `oembed_providers`
filter.

**Discovery (`discover()`, line 493)** — the fallback when no registered provider matches. It
performs an HTTP GET on the target URL and scrapes `<link rel="alternate" type="application/json+oembed" href="…">`
(or the XML variant) from the response. This is a **server-side request to a user-supplied URL**, so
it is guarded by `wp_safe_remote_get()` semantics in the HTTP API (see the SSRF protections in the
`http-api` module).

**Format negotiation (`fetch()`, line 586)** — tries `json` first via `_fetch_with_format()`, falls
back to `xml`. `_parse_xml()` (line 672) is notably defensive: it disables external entity loading
before parsing, because oEmbed XML comes from a third party.

**Rendering (`data2html()`, line 750)** — dispatches on the response `type`:

| oEmbed type | Output |
|-------------|--------|
| `photo` | `<img src="…" width="…" height="…" />` with URL validation |
| `video` / `rich` | the provider's raw `html`, subject to filters |
| `link` | a plain anchor |

`_strip_newlines()` (line 812) removes newlines from the returned HTML so `wpautop()` does not insert
`<p>` tags inside a provider's markup.

**Caching** — successful embeds are stored as `oembed_cache` post-type rows (see B1), keyed by a hash
of URL and arguments. This is the clearest illustration of the "post type as generic storage" pattern.

### Business rules 🟢

| # | Rule | Location |
|---|------|----------|
| BR-EMB-01 | A URL alone on its own line is auto-embedded; a URL inline in a paragraph is not. | `class-wp-embed.php` |
| BR-EMB-02 | 59 providers are matched by regex before any network request is made. | `class-wp-oembed.php:54` |
| BR-EMB-03 | Discovery only runs when no registered provider matches **and** discovery is enabled for the request. | `class-wp-oembed.php:320` |
| BR-EMB-04 | JSON is attempted first, XML second. | `class-wp-oembed.php:586` |
| BR-EMB-05 | XML parsing disables external entity loading. | `class-wp-oembed.php:672` |
| BR-EMB-06 | Embed results are cached as `oembed_cache` posts keyed by URL + args. | `class-wp-embed.php` |
| BR-EMB-07 | Newlines are stripped from provider HTML so `wpautop()` cannot corrupt it. | `class-wp-oembed.php:812` |
| BR-EMB-08 | `photo`-type responses are rendered by WordPress as an `<img>`; `rich`/`video` responses inject the provider's own HTML. | `class-wp-oembed.php:750` |

| # | Finding | Confidence |
|---|---------|-----------|

| F-EMB-02 | `rich`/`video` responses inject third-party HTML into the page. The trust boundary is the provider allowlist — which is why the 59-entry registry, not sanitization, is the actual security control. | 🟢 |

# Tier C — Identity & access

## C1. `users-roles-capabilities`

**Purpose.** The authorization model. Roles are named bundles of capabilities; capabilities are
booleans; and a *meta capability* layer translates object-specific questions ("can this user edit
post 42?") into concrete capability checks. This is WordPress's entire access control.

**Primary files:** `wp-includes/capabilities.php`, `wp-includes/class-wp-user.php`,
`wp-includes/class-wp-roles.php`, `wp-includes/class-wp-role.php`,
`wp-includes/class-wp-user-query.php`, `wp-includes/user.php`,
`wp-admin/includes/schema.php` (`populate_roles()`)

### The model 🟢

Three layers, each with a distinct job:

| Layer | Question it answers | Where |
|-------|--------------------|-------|
| **Roles** | "What bundle does this user belong to?" | `wp_usermeta` key `{prefix}capabilities` |
| **Primitive capabilities** | "Does this user hold this boolean?" | `WP_User::$allcaps` |
| **Meta capabilities** | "Can this user do X *to this specific object*?" | `map_meta_cap()` |

The essential insight: **`current_user_can('edit_post', 42)` is never stored anywhere.**
`edit_post` is a meta capability that `map_meta_cap()` translates at call time into a list of
primitive capabilities (`edit_posts`, `edit_others_posts`, `edit_published_posts`, …) based on the
post's author, status and type.

### The 5 default roles 🟢

`populate_roles()` (`wp-admin/includes/schema.php:719`) builds them by incremental version functions
(`populate_roles_160()`, `_210()`, `_230()`, `_250()`, `_260()`, `_270()`, `_280()`, `_300()`) —
each historical WordPress version's additions layered on top, which is why the definition is
scattered across eight functions rather than one table.

| Role | Scope |
|------|-------|
| `administrator` | full site control including `manage_options`, `edit_users`, `activate_plugins`, `edit_plugins`, `edit_themes`, `install_plugins`, `update_core`, `unfiltered_html` |
| `editor` | all content by anyone: `edit_others_posts`, `delete_others_posts`, `manage_categories`, `moderate_comments`, `unfiltered_html` |
| `author` | own content, can publish: `publish_posts`, `edit_published_posts`, `delete_published_posts`, `upload_files` |
| `contributor` | own content, **cannot publish and cannot upload**: `edit_posts`, `delete_posts`, `read` |
| `subscriber` | `read` only |

**50 primitive capabilities** are defined across the role set (excluding the legacy `level_0`–`level_10`
pseudo-capabilities, which exist purely for backward compatibility with the pre-2.0 user-level system):

`activate_plugins`, `create_users`, `delete_others_pages`, `delete_others_posts`, `delete_pages`,
`delete_plugins`, `delete_posts`, `delete_private_pages`, `delete_private_posts`,
`delete_published_pages`, `delete_published_posts`, `delete_themes`, `delete_users`,
`edit_dashboard`, `edit_files`, `edit_others_pages`, `edit_others_posts`, `edit_pages`,
`edit_plugins`, `edit_posts`, `edit_private_pages`, `edit_private_posts`, `edit_published_pages`,
`edit_published_posts`, `edit_theme_options`, `edit_themes`, `edit_users`, `export`, `import`,
`install_plugins`, `install_themes`, `list_users`, `manage_categories`, `manage_links`,
`manage_options`, `moderate_comments`, `promote_users`, `publish_pages`, `publish_posts`, `read`,
`read_private_pages`, `read_private_posts`, `remove_users`, `switch_themes`, `unfiltered_html`,
`unfiltered_upload`, `update_core`, `update_plugins`, `update_themes`, `upload_files`

### Algorithms 🟢

#### `WP_User::has_cap()` (`class-wp-user.php:787`) — the actual gate

```php
if ( is_numeric( $cap ) ) {                       // legacy user levels
    _deprecated_argument(...);
    $cap = $this->translate_level_to_cap( $cap );
}

$caps = map_meta_cap( $cap, $this->ID, ...$args );   // ① meta → primitives

if ( is_multisite() && is_super_admin( $this->ID ) ) {
    if ( in_array( 'do_not_allow', $caps, true ) ) return false;
    return true;                                     // ② super admin bypass
}

$capabilities = apply_filters( 'user_has_cap', $this->allcaps, $caps, $args, $this );  // ③
$capabilities['exist'] = true;                       // everyone is allowed to exist
unset( $capabilities['do_not_allow'] );              // ④ nobody may do_not_allow

return array_all( (array) $caps, fn( $cap ) => ! empty( $capabilities[ $cap ] ) );  // ⑤ ALL, not ANY
```

Five load-bearing details:

1. **`map_meta_cap()` runs first**, always. Even a primitive capability passes through it (and comes
   back unchanged).
2. **Super admins bypass everything** except an explicit `do_not_allow` — the only capability that
   cannot be granted.
3. **The `user_has_cap` filter can rewrite the entire capability set** for this single check. It is
   the standard extension point and, equally, the standard privilege-escalation vector.
4. **`do_not_allow` is `unset()` from the capability array before the check**, so requiring it can
   never be satisfied. This is the deny primitive.
5. **All requested capabilities must be held**, not any. `map_meta_cap()` returning three
   capabilities means all three are required.

#### `map_meta_cap()` (`capabilities.php:45`) — a ~870-line switch

Each meta capability is a case that inspects the target object and emits a list of primitives.
Representative logic:

**`remove_user`** — a user may not remove themselves in multisite unless they are a super admin:
```
if ( $args[0] === $user_id && ! is_super_admin($user_id) ) → 'do_not_allow'
else → 'remove_users'
```

**`edit_user` / `edit_users`**
```
$user_id < 1                                    → 'do_not_allow'   (a non-user cannot edit anyone,
                                                                    "not even themselves")
'edit_user' && $args[0] === $user_id            → break with EMPTY $caps  ← self-edit always allowed
multisite && ( (! super_admin && editing a super_admin) || ! user_can('manage_network_users') )
                                                → 'do_not_allow'
else                                            → 'edit_users'
```

**Returning an empty `$caps` array means "allowed"** — `array_all()` over an empty array is `true`.
Self-editing is granted by emitting no requirement at all, which is subtle but consistent.

**`delete_post` / `delete_page`** — begins with a guard added in 6.1:
```
if ( ! isset($args[0]) ) {
    _doing_it_wrong( 'you must always check it against a specific post' );
    $caps[] = 'do_not_allow';       ← FAIL CLOSED
}
```

A capability check missing its object argument **denies** rather than allowing. That is the correct
default and was a deliberate hardening.

The post-related cases then branch on: post type existence, `map_meta_cap` flag on the post type,
whether the current user is the post author (`edit_posts` vs `edit_others_posts`), post status
(`edit_published_posts`, `edit_private_posts`), and whether the post is in the trash.

#### Dynamic capability grants

Three core callbacks hook `user_has_cap` to grant capabilities conditionally rather than storing them:

| Function | Grants |
|----------|--------|
| `wp_maybe_grant_install_languages_cap()` (line 1309) | `install_languages` when the filesystem permits |
| `wp_maybe_grant_resume_extensions_caps()` (line 1325) | `resume_plugin` / `resume_theme` in recovery mode |
| `wp_maybe_grant_site_health_caps()` (line 1356) | `view_site_health_checks` |

This is the sanctioned pattern for environment-dependent capabilities: compute, don't store.

#### Super admins (`capabilities.php:1163`)

`get_super_admins()` reads the `$super_admins` **global** if set, otherwise the `site_admins` network
option. `is_super_admin()` returns `true` for any user in that list under multisite, and for any user
with `delete_users` on single-site. `grant_super_admin()` / `revoke_super_admin()` both refuse to
operate during `wp_installing()`.

### Findings

| # | Finding | Confidence |
|---|---------|-----------|
| F-CAP-01 | The `user_has_cap` filter can rewrite the entire capability array on any check. Every authorization decision in WordPress is overridable by any plugin, in one line. | 🟢 |
| F-CAP-02 | `map_meta_cap()` is an ~870-line switch that is the sole source of truth for object-level permissions. It has no formal specification; the code *is* the policy. | 🟢 |

## C2. `authentication-and-sessions`

**Purpose.** Prove identity and maintain it across requests. Password hashing, cookie-based sessions,
session tokens, nonces and the pluggable-function override mechanism.

**Primary files:** `wp-includes/pluggable.php`, `wp-login.php`,
`wp-includes/class-wp-session-tokens.php`, `wp-includes/class-wp-user-meta-session-tokens.php`,
`wp-includes/class-wp-application-passwords.php`, `wp-includes/class-phpass.php`

### The pluggable mechanism 🟢

`pluggable.php` defines **35 functions**, each wrapped in `if ( ! function_exists( … ) ) :`. Because
it loads *after* all plugins (BR-BOOT-06), any plugin may define its own version first and core will
skip its definition entirely.

The overridable set includes the whole security core:
`wp_authenticate`, `wp_logout`, `wp_validate_auth_cookie`, `wp_generate_auth_cookie`,
`wp_parse_auth_cookie`, `wp_set_auth_cookie`, `wp_clear_auth_cookie`, `auth_redirect`,
`check_admin_referer`, `check_ajax_referer`, `wp_verify_nonce`, `wp_create_nonce`, `wp_nonce_tick`,
`wp_salt`, `wp_hash`, `wp_hash_password`, `wp_check_password`, `wp_password_needs_rehash`,
`wp_generate_password`, `wp_rand`, `wp_set_password`, `wp_redirect`, `wp_safe_redirect`,
`wp_validate_redirect`, `wp_mail`, `get_avatar`, and the notification functions.

**This is a total-replacement extension point with no interface enforcement.** A plugin that defines
`wp_check_password()` owns password verification for the entire site.

### Password hashing 🟢

`wp_hash_password()` (`pluggable.php:2753`) — note the `#[\SensitiveParameter]` attribute, which
keeps the plaintext out of stack traces:

```php
if ( ! empty( $wp_hasher ) ) {
    return $wp_hasher->HashPassword( trim( $password ) );   // legacy phpass override
}
if ( strlen( $password ) > 4096 ) {
    return '*';                       // ← a DoS guard: an unmatchable hash, not an error
}
$algorithm = apply_filters( 'wp_hash_password_algorithm', PASSWORD_BCRYPT );
$options   = apply_filters( 'wp_hash_password_options', array(), $algorithm );

if ( PASSWORD_BCRYPT !== $algorithm ) {
    return password_hash( $password, $algorithm, $options );
}

// bcrypt path: pre-hash to survive the 72-byte truncation
$password_to_hash = base64_encode( hash_hmac( 'sha384', trim($password), 'wp-sha384', true ) );
return '$wp' . password_hash( $password_to_hash, $algorithm, $options );
```

Three deliberate decisions:

1. **bcrypt truncates at 72 bytes.** WordPress pre-hashes with HMAC-SHA-384 so a 200-character
   passphrase keeps its entropy. The HMAC key `'wp-sha384'` provides domain separation, and
   base64-encoding avoids null bytes in the bcrypt input.
2. **The `$wp` prefix** distinguishes WordPress's pre-hashed bcrypt from vanilla bcrypt (`$2y$`),
   so verification knows whether to pre-hash the candidate.
3. **Passwords over 4096 bytes hash to `'*'`**, which no verification can match — a denial-of-service
   guard against expensive hashing of huge inputs, expressed as a permanently-failing hash rather
   than an error.

The hash-prefix set now in play: `$P$` (phpass, pre-6.8), `$2y$` (vanilla bcrypt), `$wp$2y$`
(WordPress pre-hashed bcrypt).

### Auth cookies 🟢

**Generation (`pluggable.php:951`):**

```php
$token = $manager->create( $expiration );        // a session token, if not supplied

// password fragment — the mechanism that invalidates cookies on password change
if ( str_starts_with($user->user_pass, '$P$') || str_starts_with($user->user_pass, '$2y$') ) {
    $pass_frag = substr( $user->user_pass, 8, 4 );   // legacy: 4 chars from offset 8
} else {
    $pass_frag = substr( $user->user_pass, -4 );     // modern: last 4 chars
}

$key  = wp_hash( "{$user_login}|{$pass_frag}|{$expiration}|{$token}", $scheme );
$hash = hash_hmac( 'sha256', "{$user_login}|{$expiration}|{$token}", $key );

$cookie = "{$user_login}|{$expiration}|{$token}|{$hash}";
```

A **two-stage HMAC**: the salt-derived `wp_hash()` produces a per-user key that includes the password
fragment, and that key then HMACs the cookie payload. The password fragment is never transmitted —
it only participates in key derivation. **Changing the password changes `$pass_frag`, which changes
the key, which invalidates every outstanding cookie.**

The offset difference (`substr(…, 8, 4)` vs `substr(…, -4)`) exists because modern hashes carry a
longer prefix; the comment says the tail is used *"to avoid dealing with potentially long hash
prefixes."*

**Validation (`pluggable.php:782`)** — in order:

```
parse the cookie into username | expiration | token | hmac
$expired = expiration
if wp_doing_ajax() or REQUEST_METHOD === 'POST':  $expired += HOUR_IN_SECONDS   ← grace period
if $expired < time()          → auth_cookie_expired,      return false
$user = get_user_by('login')  → auth_cookie_bad_username, return false
recompute $key and $hash
if ! hash_equals($hash, $hmac) → auth_cookie_bad_hash,    return false
if ! $manager->verify($token)  → auth_cookie_bad_session_token, return false
```

Two properties worth stating:

- **`hash_equals()`**, not `===` — constant-time comparison against timing attacks.
- **The one-hour POST/AJAX grace period** exists so a long-composed form submission does not fail
  because the cookie expired while the user was typing. It extends the effective session for
  state-changing requests specifically.

**Expirations (`pluggable.php:1071`):**

| Mode | `$expiration` (HMAC-bound) | `$expire` (browser cookie) |
|------|---------------------------|---------------------------|
| "Remember me" | 14 days | expiration + 12 hours |
| Normal | 2 days | `0` — session cookie |

The browser cookie outlives the HMAC expiration by 12 hours in remember-me mode, so the server can
recognize a just-expired cookie and redirect to login rather than treating the user as anonymous.

**Cookie naming** — `SECURE_AUTH_COOKIE` with scheme `secure_auth` when the request is SSL, else
`AUTH_COOKIE` with scheme `auth`. Separately, `LOGGED_IN_COOKIE` is always issued, and its secure
flag additionally requires the site's `home` URL to be HTTPS — because the front end may be served
over HTTP while the admin is HTTPS.

### Nonces 🟢

```php
function wp_nonce_tick( $action = -1 ) {
    $nonce_life = apply_filters( 'nonce_life', DAY_IN_SECONDS, $action );
    return ceil( time() / ( $nonce_life / 2 ) );      // half-life ticks
}

function wp_verify_nonce( $nonce, $action = -1 ) {
    $uid = (int) wp_get_current_user()->ID;
    if ( ! $uid ) $uid = apply_filters( 'nonce_user_logged_out', $uid, $action );
    $token = wp_get_session_token();
    $i = wp_nonce_tick( $action );

    $expected = substr( wp_hash( "$i|$action|$uid|$token", 'nonce' ), -12, 10 );
    if ( hash_equals( $expected, $nonce ) ) return 1;      // 0–12 hours old

    $expected = substr( wp_hash( ($i-1) . "|$action|$uid|$token", 'nonce' ), -12, 10 );
    if ( hash_equals( $expected, $nonce ) ) return 2;      // 12–24 hours old

    do_action( 'wp_verify_nonce_failed', … );
    return false;
}
```

The design points worth recording:

- **Nonces are not nonces.** They are time-windowed HMACs. The same action by the same user with the
  same session token produces the **same** value for 12 hours. They are replayable within the window
  — they defend against CSRF, not replay.
- **`wp_verify_nonce()` returns `1` or `2`, not `true`.** `2` means the nonce is in its second half
  of life. Code that treats the return as a boolean loses that signal; code that uses `===` against
  `true` breaks entirely.
- **10 characters from offset −12** of a SHA-256-derived hash. Only 10 hex characters (~40 bits) are
  compared.
- The nonce binds to the **session token**, so a nonce is invalidated by logout even if the time
  window is still open.
- Anonymous users have `$uid = 0` unless a plugin supplies an identity via `nonce_user_logged_out`,
  which means **all logged-out visitors share the same nonce for a given action** by default.

### Session tokens 🟢

`WP_Session_Tokens` is abstract; `WP_User_Meta_Session_Tokens` stores tokens in user meta
(`session_tokens`). Each login creates a token; `destroy_all_sessions()` invalidates every device.
The token is embedded in both the auth cookie and every nonce, which is how "log out everywhere"
simultaneously invalidates all cookies and all outstanding nonces.

## D1. `themes-and-templates`

**Purpose.** Choose which PHP (or HTML) file renders the current query, and manage theme
registration, parent/child inheritance and theme features.

**Primary files:** `wp-includes/template-loader.php`, `wp-includes/template.php`,

### The template hierarchy 🟢

`template-loader.php` is the shortest consequential file in WordPress. Its whole job:

```php
if ( wp_using_themes() ) do_action( 'template_redirect' );

if ( 'HEAD' === $_SERVER['REQUEST_METHOD'] && apply_filters('exit_on_http_head', true) ) exit;

// these run even when themes are disabled
if      ( is_robots() )    { do_action('do_robots');  return; }
elseif  ( is_favicon() )   { do_action('do_favicon'); return; }
elseif  ( is_feed() )      { do_feed();               return; }
elseif  ( is_trackback() ) { require 'wp-trackback.php'; return; }

$tag_templates = [ 17 conditional => getter pairs, IN PRIORITY ORDER ];
foreach ( $tag_templates as $tag => $getter ) {
    if ( call_user_func($tag) ) $template = call_user_func($getter);
    if ( $template ) {
        if ( 'is_attachment' === $tag ) remove_filter('the_content','prepend_attachment');
        break;
    }
}
if ( ! $template ) $template = get_index_template();
$template = apply_filters( 'template_include', $template );
```

**The 17 conditionals, in the order they are tested** — this order *is* the template hierarchy:

`is_embed` → `is_404` → `is_search` → `is_front_page` → `is_home` → `is_privacy_policy` →
`is_post_type_archive` → `is_tax` → `is_attachment` → `is_single` → `is_page` → `is_singular` →
`is_category` → `is_tag` → `is_author` → `is_date` → `is_archive` → *(fallback)* `index.php`

Note `is_404` is **second**, before `is_search` and everything else — a 404 short-circuits nearly the
whole hierarchy. And `is_singular` sits *after* `is_single`/`is_page`, so it only catches custom post
types that neither matched.

### Template file resolution 🟢

**`get_query_template()` (`template.php:23`)**

```php
$type = preg_replace( '|[^a-z0-9-]+|', '', $type );   // sanitize BEFORE building filenames
if ( empty($templates) ) $templates = array( "{$type}.php" );
$templates = apply_filters( "{$type}_template_hierarchy", $templates );
$template  = locate_template( $templates );
$template  = locate_block_template( $template, $type, $templates );   // block themes override
```

The `preg_replace` strips everything but `a-z0-9-` before the type becomes part of a filename — a
path-traversal guard applied at the type level.

**`locate_template()` (`template.php`)** — a strict three-step cascade per candidate filename:

```
1. $wp_stylesheet_path/$name        ← the active (child) theme
2. $wp_template_path/$name          ← the PARENT theme, only if is_child_theme()
3. ABSPATH/wp-includes/theme-compat/$name   ← core's last-resort fallbacks
```

**The first candidate filename that exists anywhere wins** — the loop breaks on the first hit, so
specificity of *filename* outranks proximity of *location*. A `single-product.php` in the parent
theme beats a `single.php` in the child theme.

**`get_single_template()`** builds its candidate list most-specific first:

```
1. the page-template slug from post meta (if validate_file() passes)
2. single-{post_type}-{urldecoded post_name}.php   ← only when decoding changed the string
3. single-{post_type}-{post_name}.php
4. single-{post_type}.php
5. single.php
```

`get_page_template()` is analogous: custom template slug → `page-{decoded pagename}.php` →
`page-{pagename}.php` → `page-{id}.php` → `page.php`.

The urldecoded variant is added **only when it differs** from the raw name, so non-ASCII slugs work
whether the theme's filename is percent-encoded or not — without doubling the candidate list for
ASCII slugs.

`validate_file()` gates the meta-supplied template slug: a stored `_wp_page_template` value
containing `../` is rejected. That check matters because the value comes from post meta, which is
user-writable.

### Template inclusion safety 🟢

After `template_include`, the resolved path is validated before use:

```php
$is_stringy = is_string($template) || (is_object($template) && method_exists($template,'__toString'));
$template   = $is_stringy ? realpath( (string) $template ) : null;

if ( is_string($template)
     && ( str_ends_with($template,'.php') || str_ends_with($template,'.html') )
     && is_file($template) && is_readable($template) ) {
    do_action( 'wp_before_include_template', $template );
    include $template;
}
```

Four checks after the filter: `realpath()` resolution, extension allowlist (`.php` / `.html` — the
latter for block templates), file existence and readability. The `template_include` filter can return
an arbitrary value, so this is the guard that stops it becoming a local file inclusion.

### Parent/child themes 🟢

`$wp_stylesheet_path` is the child (or only) theme; `$wp_template_path` is the parent. Both are set
by `wp_set_template_globals()` during boot (line 709 of `wp-settings.php`). Recall from BR-BOOT-08
that the **child's `functions.php` loads before the parent's** — the reverse of the template lookup
order, because functions must be *declarable first* while templates must be *overridable last*.

`WP_Theme` caches its parsed headers in the `themes` cache group, which is registered both global
(`class-wp-theme.php:259`) and non-persistent.

## D2. `rewrite-and-permalinks`

### The tag substitution tables 🟢

`WP_Rewrite` holds three **parallel arrays** that must stay index-aligned
(`class-wp-rewrite.php:281`–`341`):

| index | `$rewritecode` | `$rewritereplace` | `$queryreplace` |
|-------|---------------|------------------|-----------------|
| 0 | `%year%` | `([0-9]{4})` | `year=` |
| 1 | `%monthnum%` | `([0-9]{1,2})` | `monthnum=` |
| 2 | `%day%` | `([0-9]{1,2})` | `day=` |
| 3 | `%hour%` | `([0-9]{1,2})` | `hour=` |
| 4 | `%minute%` | `([0-9]{1,2})` | `minute=` |
| 5 | `%second%` | `([0-9]{1,2})` | `second=` |
| 6 | `%postname%` | `([^/]+)` | `name=` |
| 7 | `%post_id%` | `([0-9]+)` | `p=` |
| 8 | `%author%` | `([^/]+)` | `author_name=` |
| 9 | `%pagename%` | `([^/]+?)` | `pagename=` |
| 10 | `%search%` | `(.+)` | `s=` |

Compiling a permalink structure is: replace each `%tag%` with its regex to build the match pattern,
and with its query key to build the `index.php?…` target. Three arrays kept in lockstep by position
— fragile, but it is the entire compiler.

Note the deliberate regex differences: `%pagename%` is **non-greedy** `([^/]+?)` because pages are

`([^/]+)`. `%search%` is `(.+)` — it may contain slashes.

Built-in feed slugs: `feed`, `rdf`, `rss`, `rss2`, `atom`.

### Structural bases 🟢

`author_base = 'author'`, `search_base = 'search'`, `comments_base = 'comments'`,
`pagination_base = 'page'`, `comments_pagination_base = 'comment-page'`, `feed_base = 'feed'`,
`index = 'index.php'`.

`pagination_base = 'page'` is why a post slug of `page` or a bare number collides with pagination —
recall BR-POST-07, where `wp_unique_post_slug()` rejects `^(pagination_base)?\d+$` for hierarchical
types. The two modules are coupled through this property.

### Endpoint masks 🟢

14 bitmask constants let a rule attach to specific URL classes:

`EP_NONE = 0`, `EP_PERMALINK = 1`, `EP_ATTACHMENT = 2`, `EP_DATE = 4`, `EP_YEAR = 8`,
`EP_MONTH = 16`, `EP_DAY = 32`, `EP_ROOT = 64`, `EP_COMMENTS = 128`, `EP_SEARCH = 256`,
`EP_CATEGORIES = 512`, `EP_TAGS = 1024`, `EP_AUTHORS = 2048`, `EP_PAGES = 4096`
(plus `EP_ALL_ARCHIVES` and `EP_ALL` as combinations).

`add_endpoint('json', EP_PERMALINK | EP_PAGES)` attaches `/json/` to single posts and pages only.

### Rule caching 🟢

```php
public function wp_rewrite_rules() {
    $this->rules = get_option( 'rewrite_rules' );
    if ( empty( $this->rules ) ) {
        $this->refresh_rewrite_rules();
    }
    return $this->rules;
}

private function refresh_rewrite_rules() {
    $this->rules = '';
    $this->matches = 'matches';
    $this->rewrite_rules();                          // regenerate from permastructs
    if ( ! did_action( 'wp_loaded' ) ) {
        add_action( 'wp_loaded', array( $this, 'flush_rules' ) );   // defer
    } else {
        update_option( 'rewrite_rules', $this->rules );
    }
}
```

**The complete rule set lives in one option row.** It is read on every request that resolves a
permalink (`WP::parse_request()`), so it is almost always in `alloptions`. A site with many custom
post types and taxonomies can accumulate hundreds of rules in a single serialized option — a direct
tie back to F-OPT-01 and the 150 KB autoload threshold (BR-OPT-06).

### Flush deferral 🟢

```php
public function flush_rules( $hard = true ) {
    static $do_hard_later = null;

    if ( ! did_action( 'wp_loaded' ) ) {
        add_action( 'wp_loaded', array( $this, 'flush_rules' ) );
        $do_hard_later = isset($do_hard_later) ? ($do_hard_later || $hard) : $hard;
        return;                                    // ← deferred, NOT executed
    }
    if ( isset( $do_hard_later ) ) { $hard = $do_hard_later; unset( $do_hard_later ); }

    $this->refresh_rewrite_rules();

    if ( ! $hard || ! apply_filters( 'flush_rewrite_rules_hard', true ) ) return;

    if ( function_exists('save_mod_rewrite_rules') )    save_mod_rewrite_rules();      // .htaccess
    if ( function_exists('iis7_save_url_rewrite_rules') ) iis7_save_url_rewrite_rules(); // web.config
}
```

Three behaviors worth recording:

1. **Any flush before `wp_loaded` is deferred to `wp_loaded`** — with the explicit comment *"Prevent
   this action from running before everyone has registered their rewrites."* A plugin calling
   `flush_rewrite_rules()` on `init` does not flush then; it flushes later, once every post type and
   taxonomy exists.
2. **`$hard` accumulates across deferred calls via `||`.** If any caller asked for a hard flush, the
   eventual flush is hard. A static variable used as a sticky flag.
3. **A hard flush rewrites `.htaccess` or `web.config`** — the only place in this module that touches
   the filesystem, and it degrades silently to a soft flush when those functions are unavailable
   (they live in `wp-admin/includes/`, so a front-end flush is always soft).

### Verbose page rules 🟢

`$use_verbose_page_rules = true` by default. When a permalink structure begins with a variable tag
(e.g. `/%postname%/`), WordPress cannot tell `/about/` (a page) from `/my-post/` (a post) by pattern
alone, so it generates an explicit rule per page via `page_uri_index()` / `page_rewrite_rules()`.
**Rule count then grows linearly with the number of pages.**

## D3. `script-modules-and-assets`

**Purpose.** Register, resolve dependencies for, and emit scripts and stylesheets. Two generations
coexist: the classic `WP_Dependencies` handle system (jQuery era) and `WP_Script_Modules` (ES
modules with import maps).

**Primary files:** `wp-includes/class-wp-dependencies.php`, `wp-includes/class-wp-scripts.php`,
`wp-includes/class-wp-styles.php`, `wp-includes/script-loader.php` (the registry — every core
handle), `wp-includes/class-wp-script-modules.php`, `wp-includes/script-modules.php`

### Classic dependency system 🟢

`WP_Dependencies` keeps five parallel structures:

| Property | Meaning |
|----------|---------|
| `$registered` | `handle => _WP_Dependency{ handle, src, deps, ver, args, extra }` |
| `$queue` | handles explicitly enqueued |
| `$to_do` | resolved output order (built by `all_deps()`) |
| `$done` | already emitted |
| `$groups` | `handle => group`, where group `0` = header, `1` = footer |

#### `all_deps()` (`class-wp-dependencies.php:193`) — recursive topological resolution

```
for each $handle:
    strip a '?args' suffix
    $queued = handle already in to_do
    if handle in done                                   → continue
    $moved     = set_group( handle, recursion, group )
    $new_group = groups[handle]
    if $queued && ! $moved                              → continue   (right place already)

    $missing = registered[handle]->deps − array_keys(registered)
    if ! isset(registered[handle])                      → keep_going = false  (unknown handle)
    elseif count($missing) > 0:
        _doing_it_wrong( … )   ONCE per handle          → keep_going = false
    elseif deps && ! all_deps( deps, true, $new_group ) → keep_going = false  (recurse)

    if ! keep_going:
        if $recursion  → return false      ← abort the whole branch
        else           → continue          ← top level: skip this one, keep going
    if $queued → continue
    to_do[] = handle
```

Three properties this encodes:

1. **A missing dependency drops the dependent silently from output** — with a `_doing_it_wrong()`
   notice added in 6.9.1, emitted **once per handle** (tracked in
   `$dependencies_with_missing_dependencies`) so a repeated resolution does not spam the log.
2. **Failure propagates up but not out.** Inside recursion, a failure returns `false` and aborts that
   dependency branch; at the top level it merely skips that handle and continues with the rest.
3. **No cycle detection.** A circular dependency chain recurses until PHP's stack limit. The
   `$queued && ! $moved` early-continue mitigates re-entry for already-queued handles, but a genuine
   `a → b → a` cycle among unqueued handles has no explicit guard. 🟡

#### `set_group()` — the footer-to-header promotion rule

```php
public function set_group( $handle, $recursion, $group ) {
    $group = (int) $group;
    if ( isset( $this->groups[$handle] ) && $this->groups[$handle] <= $group ) {
        return false;                     // already in this group or an EARLIER one
    }
    $this->groups[$handle] = $group;
    return true;                          // moved
}
```

**A handle only ever moves to a *lower* group number.** Group `0` is the header, `1` the footer. If
a footer script depends on a script currently assigned to the footer, and something later needs that
dependency in the header, it is promoted to the header — never demoted. This is why enqueuing a
script in the header pulls all of its dependencies into the header with it, and why
`$in_footer = true` is a request, not a guarantee.

### Script modules 🟢

`WP_Script_Modules` is a parallel, more modern registry:

| Property | Purpose |
|----------|---------|
| `$registered` / `$queue` / `$done` | same three-phase lifecycle |
| `$dependents_map` | reverse dependency index — used to compute fetch priority |
| `$priorities` | fetch-priority bookkeeping |
| `$a11y_available` | whether `@wordpress/a11y` can be attached |
| `$modules_with_missing_dependencies` | the same once-per-handle warning pattern |

Distinct capabilities: `print_import_map()` emits a browser **import map** so bare specifiers resolve;
`print_script_module_preloads()` emits `<link rel="modulepreload">` for static dependencies;
`set_fetchpriority()` / `get_highest_fetchpriority()` compute a module's priority from its
*dependents* (via `$dependents_map`) rather than its own declaration; `set_translations()` and
`print_script_module_translations()` wire i18n into modules.

`add_hooks()` (line 433) registers the printing callbacks; `set_in_footer()` exists but, as with the
classic system, is a placement hint.

functions register every core handle with its dependencies and version — the versions extracted in

## D4. `widgets-and-nav-menus`

**Purpose.** Two legacy content-placement systems that predate blocks and remain load-bearing:
sidebar widgets and navigation menus.

**Primary files:** `wp-includes/widgets.php`, `wp-includes/class-wp-widget.php`,
`wp-includes/class-wp-widget-factory.php`, `wp-includes/default-widgets.php`,
`wp-includes/widgets/` (20 classes), `wp-includes/nav-menu.php`,
`wp-includes/nav-menu-template.php`, `wp-includes/class-walker-nav-menu.php`

### Widgets 🟢

`WP_Widget` is an abstract class with three methods a subclass implements —
`widget($args, $instance)` (render), `update($new, $old)` (sanitize on save), `form($instance)`
(admin UI) — and a parallel set of `*_callback` wrappers that core actually invokes.

**The multi-instance model is the unusual part.** One `WP_Widget` subclass serves *many* placed
widgets:

| Property | Role |
|----------|------|
| `$id_base` | the class-level identifier, e.g. `text` |
| `$number` | which instance, set by `_set($number)` |
| `$id` | `"{$id_base}-{$number}"` |
| `$option_name` | `"widget_{$id_base}"` — **all instances share one option row** |

`get_settings()` / `save_settings()` read and write that single option, keyed by instance number.
`_register()` inspects the stored settings and calls `_register_one($number)` for each existing
instance. `get_field_name()` / `get_field_id()` produce
`widget-{$id_base}[{$number}][{$field}]` so a single form submission can carry every instance.

The 20 core widgets: `archives`, `block`, `calendar`, `categories`, `custom-html`, `links`,
`media`, `media-audio`, `media-gallery`, `media-image`, `media-video`, `meta`, `nav-menu`, `pages`,
`recent-comments`, `recent-posts`, `rss`, `search`, `tag-cloud`, `text`.

`is_preview()` lets a widget know it is rendering inside the Customizer, so it can show unsaved state.

### Nav menus 🟢

A navigation menu is the `nav_menu` **taxonomy**; each menu item is a `nav_menu_item` **post**; and
the item's actual meaning lives entirely in **post meta**:

| Meta key | Meaning |
|----------|---------|
| `_menu_item_type` | `post_type`, `taxonomy`, `custom`, or `post_type_archive` |
| `_menu_item_object` | e.g. `page`, `category`, `custom` |
| `_menu_item_object_id` | the referenced post or term id |
| `_menu_item_menu_item_parent` | parent **menu item** id (not the referenced object's parent) |
| `_menu_item_url` | for `custom` items only |
| `_menu_item_target` | link target |
| `_menu_item_classes` | CSS classes |
| `_menu_item_xfn` | XFN relationship |
| `_menu_item_orphaned` | set when an item's referenced object no longer exists |

So a menu item is a post whose `post_title` may be empty (falling back to the referenced object's
title), whose ordering is `menu_order`, and whose hierarchy is a meta value rather than
`post_parent`. **Two parallel hierarchies exist on the same row** — `post_parent` (unused for menu
items) and `_menu_item_menu_item_parent` (the real one).

`_menu_item_orphaned` is the tombstone for referential integrity that the schema cannot provide: when
a page a menu item points to is deleted, the item is flagged rather than removed.

| # | Rule | Location |
|---|------|----------|

# Tier E — Block editor stack

## E1. `block-editor`

**Purpose.** Parse, register, and render the block-based content format. Post content is HTML with
block boundaries encoded as HTML comments; this module turns that string into a tree and back.

**Primary files:** `wp-includes/blocks.php`, `wp-includes/class-wp-block-parser.php`,
`wp-includes/class-wp-block.php`, `wp-includes/class-wp-block-type.php`,
`wp-includes/class-wp-block-type-registry.php`, `wp-includes/block-editor.php`,
`wp-includes/block-template.php`, `wp-includes/block-patterns.php`,
`wp-includes/block-bindings.php`

### The format 🟢

Block content is **valid HTML with metadata in comments** — it renders correctly even if WordPress
never parses it. The delimiter regex (`class-wp-block-parser.php:248`):

```
/<!--\s+(?P<closer>\/)?wp:(?P<namespace>[a-z][a-z0-9_-]*\/)?(?P<name>[a-z][a-z0-9_-]*)\s+
 (?P<attrs>{(?:(?:[^}]+|}+(?=})|(?!}\s+\/?-->).)*+)?}\s+)?(?P<void>\/)?-->/s
```

Three forms:

| Form | Example |
|------|---------|
| Open/close pair | `<!-- wp:paragraph -->…<!-- /wp:paragraph -->` |
| Void (self-closing) | `<!-- wp:spacer {"height":"20px"} /-->` |
| Freeform | anything outside a delimiter → `core/freeform` |

The namespace defaults to `core/`, so `wp:paragraph` means `core/paragraph`.

**The attribute sub-pattern is the interesting part.** `{(?:(?:[^}]+|}+(?=})|(?!}\s+\/?-->).)*+}`
uses a possessive quantifier (`*+`) and two lookaheads to match a JSON object that may itself contain
`}` characters, stopping only at the `}` immediately preceding the comment terminator. It is a
hand-rolled brace matcher expressed as a regex, and the possessive quantifier is what prevents
catastrophic backtracking on deeply-nested attributes.

### The parser 🟢

`WP_Block_Parser` is a **stack machine**, not a recursive-descent parser:

```
proceed():
    next_token() → (token_type, block_name, attrs, start_offset, token_length)
    leading_html_start = start_offset > offset ? offset : null   ← "HTML soup before the next block"

    switch token_type:
      'no-more-tokens':
          stack empty      → add_freeform(); return false
          stack depth 1    → add_block_from_stack(); return false      (implicit closer)
          deeper           → while stack: add_block_from_stack(); return false
      'void-block':        emit immediately, no stack push
      'block-opener':      push onto the stack
      'block-closer':      pop and attach to parent
```

**Unclosed blocks are recovered, not rejected.** `no-more-tokens` with a non-empty stack closes every
open block implicitly. The parser has no failure mode: malformed input becomes freeform content or an
implicitly-closed block. For a format edited by hand and by third-party tools, that is the correct
design choice.

`freeform()` / `add_freeform()` wrap any non-block text into a `core/freeform` block, which is how
pre-Gutenberg content survives.

### Round-tripping 🟢

`serialize_block()` (`blocks.php:1794`) is elegantly small:

```php
$block_content = '';
$index = 0;
foreach ( $block['innerContent'] as $chunk ) {
    $block_content .= is_string($chunk)
        ? $chunk                                            // literal HTML
        : serialize_block( $block['innerBlocks'][ $index++ ] );  // null marker → next inner block
}
return get_comment_delimited_block_content( $block['blockName'], $block['attrs'], $block_content );
```

`innerContent` is an array mixing **strings** (literal HTML) and **`null`s** (placeholders marking
where an inner block belongs). Serialization walks it, substituting each `null` with the next
serialized inner block. This separation of "my HTML" from "my children" is what makes
parse → serialize a faithful round trip: a block's own markup and its children's positions are
recorded independently.

### Block registration 🟢

`register_block_type_from_metadata()` (`blocks.php:520`) resolves metadata from three sources in
order:

1. `WP_Block_Metadata_Registry::get_metadata()` — a **pre-built manifest** (registered via
   `wp_register_block_metadata_collection()`), avoiding per-block file I/O.
2. `block.json` on disk, decoded with `wp_json_file_decode()`.
3. An empty array (metadata may then come entirely from `$args`).

Core blocks are detected by path prefix (`str_starts_with($file_or_folder, ABSPATH . WPINC)`) and get
`metadata_file_exists` assumed true without a `file_exists()` call — a deliberate I/O saving across
115 core blocks.

Core blocks also receive **implicit style handles**: `wp-block-{name}` for `style`,
`wp-block-{name}-editor` for `editorStyle`, plus `wp-block-{name}-theme` when the theme supports
`wp-block-styles` and separate core block assets are enabled.

The `$property_mappings` table converts `block.json`'s camelCase to PHP snake_case:
`apiVersion` → `api_version`, `providesContext` → `provides_context`, `usesContext` → `uses_context`,
and so on.

### Rendering 🟢

`do_blocks( $content )` (`blocks.php:2570`) is hooked onto `the_content`. It parses, then calls
`render_block()` (line 2410) per block, which:

- for a **static** block, returns the saved `innerHTML`;
- for a **dynamic** block (one with a `render_callback`), calls the callback with attributes,
  content and the `WP_Block` instance.

`get_dynamic_block_names()` (line 953) enumerates the blocks that have callbacks — the ones whose
output cannot be determined from stored content alone.

## E3. `block-supports`

**Purpose.** Cross-cutting block features. Instead of every block implementing its own colour or
spacing handling, a block declares `supports: { color: true }` in `block.json` and this module
injects the resulting classes and inline styles at render time.

**Primary files:** `wp-includes/class-wp-block-supports.php`, `wp-includes/block-supports/` (23 files)

### The 23 support modules 🟢

`align`, `anchor`, `aria-label`, `auto-register`, `background`, `block-style-variations`,
`block-visibility`, `border`, `colors`, `custom-classname`, `custom-css`, `dimensions`, `duotone`,
`elements`, `generated-classname`, `layout`, `position`, `settings`, `shadow`, `spacing`, `states`,
`typography`, `utils`

Each registers itself with `WP_Block_Supports::register( $name, [ 'register_attribute' => …, 'apply' => … ] )`.

### The application algorithm 🟢

`apply_block_supports()` (`class-wp-block-supports.php:114`):

```php
if ( ! is_array( self::$block_to_render ) ) return array();

$block_type = WP_Block_Type_Registry::get_instance()->get_registered( self::$block_to_render['blockName'] );
if ( ! $block_type ) return array();

$block_attributes = $block_type->prepare_attributes_for_render( self::$block_to_render['attrs'] );

$output = array();
foreach ( $this->block_supports as $config ) {
    if ( ! isset( $config['apply'] ) ) continue;
    $new_attributes = call_user_func( $config['apply'], $block_type, $block_attributes );

    foreach ( $new_attributes as $name => $value ) {
        if ( ! is_scalar($value) || is_bool($value) ) continue;      // ← skip non-scalars AND booleans
        $value = (string) $value;
        if ( ! array_key_exists($name,$output) || '' === $output[$name] ) {
            $output[$name] = $value;                                  // first writer sets
        } else {
            $output[$name] .= " $value";                              // subsequent APPEND, space-joined
        }
    }
}
```

Two rules do the real work:

1. **Attribute merging is space-concatenation, not replacement.** Multiple supports contributing to
   `class` produce `"support-a-class support-b-class"`. This is why `class` and `style` accumulate
   across supports correctly — and why a support cannot *remove* another's contribution.
2. **Booleans are explicitly skipped** despite being scalar. `is_scalar(true)` is `true`, so
   without the extra `is_bool()` check a boolean would stringify to `"1"` and be injected into the
   markup.

`$block_to_render` is a **public static** holding the block currently being rendered — global state
threading context through what is otherwise a stateless pipeline.

| # | Rule | Location |
|---|------|----------|
| BR-BSUP-01 | Supports apply only to blocks with a registered block type; unregistered blocks get nothing. | `class-wp-block-supports.php:120` |
| BR-BSUP-02 | Attributes contributed by multiple supports are **space-concatenated**, first writer wins the slot. | `class-wp-block-supports.php:148` |
| BR-BSUP-03 | Non-scalar values and booleans are skipped entirely. | `class-wp-block-supports.php:143` |

## E4. `global-styles-theme-json`

**Purpose.** A declarative styling system. `theme.json` describes settings (what the editor offers)
and styles (what is applied), merged across four origins and compiled to CSS.

**Primary files:** `wp-includes/class-wp-theme-json.php` (216 KB),
`wp-includes/class-wp-theme-json-resolver.php`, `wp-includes/class-wp-theme-json-schema.php`,
`wp-includes/class-wp-theme-json-data.php`, `wp-includes/global-styles-and-settings.php`,
`wp-includes/class-wp-duotone.php`

### The four origins 🟢

```php
const VALID_ORIGINS = array( 'default', 'blocks', 'theme', 'custom' );
```

`WP_Theme_JSON_Resolver::get_merged_data( $origin = 'custom' )` merges them in exactly that order,
with early returns:

```
$result = new WP_Theme_JSON();
$result->merge( get_core_data() );      // ① core's own theme.json
if ( 'default' === $origin ) return;
$result->merge( get_block_data() );     // ② per-block theme.json declarations
if ( 'blocks'  === $origin ) return;
$result->merge( get_theme_data() );     // ③ the active theme's theme.json (+ child)
if ( 'theme'   === $origin ) return;
$result->merge( get_user_data() );      // ④ user edits from the Site Editor
return $result;
```

**Later origins override earlier ones.** The `$origin` parameter lets a caller stop the cascade early
— for example, asking for `'theme'` data yields what the theme intends *before* user customization,
which is how the Site Editor shows a "reset to theme default" value.

User data lives in the `wp_global_styles` post type (see B1), one post per theme, resolved by
`get_user_data_from_wp_global_styles( $theme, $create_post = true )` — which creates the post on first
access. `$user_custom_post_type_id` memoizes the lookup in a static.

### Structural constants 🟢

| Constant | Purpose |
|----------|---------|
| `VALID_ORIGINS` | the four-layer cascade |
| `VALID_TOP_LEVEL_KEYS` | `version`, `settings`, `styles`, `customTemplates`, `templateParts`, `patterns`, … |
| `VALID_SETTINGS` | the settings schema — what a theme may declare |

| `PROPERTIES_METADATA` | style-path → CSS property mapping |
| `INDIRECT_PROPERTIES_METADATA` | properties computed rather than mapped directly |

| `ELEMENTS` | `link`, `heading`, `h1`–`h6`, `button`, `caption`, `cite` |

| `VALID_BLOCK_CUSTOM_STATES` | custom state selectors |

## E6. `html-api`

**Purpose.** Parse and modify HTML correctly, in PHP, without a DOM. Two layers: a streaming
tag-level editor and a full HTML5-spec-compliant parser.

**Primary files:** `wp-includes/html-api/` (14 files),
`class-wp-html-tag-processor.php` (175 KB), `class-wp-html-processor.php` (209 KB),
`html5-named-character-references.php`

### Why it exists 🟢

Before the HTML API, WordPress modified markup with regular expressions — `preg_replace` on
`<img ...>` to add attributes, string surgery to inject classes. The HTML API replaces that with two
correctly-specified tools. `wp_filter_content_tags()` (B5) and the Interactivity API (E7) are its
primary consumers.

### Layer 1 — `WP_HTML_Tag_Processor` 🟢

A **streaming, in-place editor**. It never builds a tree; it scans forward and records byte-level
replacements applied on `get_updated_html()`.

| Method | Purpose |
|--------|---------|
| `next_tag($query)` / `next_token()` | advance the cursor |
| `get_tag()` / `is_tag_closer()` | inspect the current element |
| `get_attribute($name)` / `get_attribute_names_with_prefix($prefix)` | read |
| `set_attribute()` / `remove_attribute()` | write |
| `add_class()` / `remove_class()` | class-list surgery |
| `get_modifiable_text()` | the text content between tags |
| `set_bookmark($name)` / `seek($name)` | save and restore a position |
| `get_updated_html()` | apply all queued modifications |

The bookmark/seek pair is what allows non-linear editing on a forward-only scanner — the caller marks
positions of interest, keeps scanning, then returns.

`get_attribute_names_with_prefix()` exists specifically for the Interactivity API, which needs every
`data-wp-*` attribute on an element without knowing their names in advance.

### Layer 2 — `WP_HTML_Processor` 🟢

An **HTML5 specification-compliant parser** implementing the real tree-construction algorithm:
insertion modes, the stack of open elements (`WP_HTML_Open_Elements`), the list of active formatting
elements (`WP_HTML_Active_Formatting_Elements`), and the adoption agency algorithm.

Two entry points:

- `create_fragment( $html, $context = '<body>', $encoding = 'UTF-8' )` — parse a fragment in a
  context, as `innerHTML` does.
- `create_full_parser( $html, $known_definite_encoding = 'UTF-8' )` — parse a full document.

`get_breadcrumbs()` returns the ancestor chain of the current node, and `matches_breadcrumbs()` tests
it — so a caller can ask "am I inside a `figure > figcaption`?" without a DOM or XPath.

`WP_HTML_Unsupported_Exception` signals constructs the parser deliberately does not handle, so
callers can detect and bail rather than receive wrong output — an explicit "I cannot do this"
rather than silent misparsing.

`html5-named-character-references.php` holds the full HTML5 named-entity table, and
`WP_HTML_Decoder` implements spec-correct entity decoding.

### Business rules 🟢

| # | Rule | Location |
|---|------|----------|
| BR-HTML-01 | `WP_HTML_Tag_Processor` never constructs a tree; modifications are byte-level and applied on `get_updated_html()`. | `class-wp-html-tag-processor.php:4913` |
| BR-HTML-02 | Scanning is forward-only; `set_bookmark()` / `seek()` are the only way to revisit a position. | `class-wp-html-tag-processor.php:1360, 2719` |
| BR-HTML-03 | `get_attribute_names_with_prefix()` enables attribute discovery by prefix. | `class-wp-html-tag-processor.php:2971` |
| BR-HTML-04 | `WP_HTML_Processor` implements HTML5 tree construction including the stack of open elements and active formatting elements. | `class-wp-html-processor.php` |
| BR-HTML-05 | Fragment parsing requires a context element, defaulting to `<body>`. | `class-wp-html-processor.php:300` |
| BR-HTML-06 | Unsupported constructs raise `WP_HTML_Unsupported_Exception` rather than producing incorrect output. | `class-wp-html-unsupported-exception.php` |
| BR-HTML-07 | `get_breadcrumbs()` / `matches_breadcrumbs()` provide ancestor querying without a DOM. | `class-wp-html-processor.php:1202, 931` |

### Findings

| # | Finding | Confidence |
|---|---------|-----------|
| F-HTML-01 | This is the most rigorous code in WordPress: a genuine HTML5 tree-construction implementation, 384 KB across two classes. It exists because regex-based HTML manipulation was the source of a long tail of correctness and security bugs. | 🟢 |
| F-HTML-02 | Failing loudly via `WP_HTML_Unsupported_Exception` is the opposite of the block parser's never-fail design (F-BLK-03). Two parsers in the same codebase with deliberately opposite error philosophies, each right for its input. | 🟢 |

## E7. `interactivity-api`

**Purpose.** Declarative client-side interactivity driven by `data-wp-*` HTML attributes, with
server-side pre-rendering of directives so the initial HTML is already correct.

**Primary files:** `wp-includes/interactivity-api/class-wp-interactivity-api.php`,
`class-wp-interactivity-api-directives-processor.php`, `interactivity-api.php`

### The model 🟢

State lives in **namespaced stores**. `state($namespace, $state)` reads or merges server state;
`config($namespace, $config)` does the same for configuration. Both are printed into the page by
`print_client_interactivity_data()` so the client hydrates from server truth.

`process_directives( $html )` (line 462) runs the server-side pass. Its private engine
`_process_directives()` (line 492) walks the HTML with the directives processor, and for each
recognized directive calls a dedicated handler:

| Directive | Handler |
|-----------|---------|
| `data-wp-interactive` | `data_wp_interactive_processor()` — enters a namespace |
| `data-wp-context` | `data_wp_context_processor()` — pushes a context frame |
| `data-wp-bind--{attr}` | `data_wp_bind_processor()` — sets an attribute from state |
| `data-wp-class--{name}` | `data_wp_class_processor()` — toggles a class |
| `data-wp-style--{prop}` | `data_wp_style_processor()` — sets a style property |
| `data-wp-text` | `data_wp_text_processor()` — sets element text |

Each handler is called twice — once entering the element and once leaving it (`$mode`) — which is how
context frames are pushed and popped correctly around nested elements.

### Algorithms 🟢

**Directive name parsing (`parse_directive_name()`, line 798)** splits
`data-wp-bind--aria-label` into its directive (`bind`) and suffix (`aria-label`), and
`extract_directive_value()` (line 893) parses the value, which may be a bare path or a
`namespace::path` reference — with a default namespace supplied by the enclosing
`data-wp-interactive`.

**`evaluate()` (line 663)** resolves a reference against the current state and context stack: it
walks the namespace, then the path, honouring the `!` negation prefix.

**`kebab_to_camel_case()` (line 997)** converts HTML's kebab-case attribute suffixes to the
camelCase keys used in the state object — the bridge between HTML naming and JS naming conventions.

**`merge_style_property()` (line 1354)** is a small but telling function: setting one style property
via `data-wp-style--color` must not destroy the element's other inline styles, so the existing
`style` attribute is parsed, the single property replaced, and the whole re-serialized.

**Client navigation** — `add_client_navigation_support_to_script_module()` (line 449) and
`add_load_on_client_navigation_attribute_to_script_modules()` (line 422) integrate with the script
modules registry (D3) so that a client-side navigation can load the right modules.

### Business rules 🟢

| # | Rule | Location |
|---|------|----------|
| BR-INT-01 | State and config are namespaced per store and serialized into the page for client hydration. | `class-wp-interactivity-api.php:166, 222` |
| BR-INT-02 | Directives are processed **server-side** so the initial HTML already reflects state. | `class-wp-interactivity-api.php:462` |
| BR-INT-03 | Each directive handler is invoked on both entering and leaving an element, enabling correct context push/pop. | `class-wp-interactivity-api.php:1020` |
| BR-INT-04 | A directive value may be `namespace::path`; without a namespace it resolves against the enclosing `data-wp-interactive`. | `class-wp-interactivity-api.php:893` |
| BR-INT-05 | Kebab-case attribute suffixes are converted to camelCase state keys. | `class-wp-interactivity-api.php:997` |
| BR-INT-06 | Setting one style property preserves all other inline styles on the element. | `class-wp-interactivity-api.php:1354` |
| BR-INT-07 | References support a `!` negation prefix, resolved in `evaluate()`. | `class-wp-interactivity-api.php:663` |

### Findings

| # | Finding | Confidence |
|---|---------|-----------|
| F-INT-01 | Server-side directive processing means an interactive block's *initial* render is correct without JavaScript — genuine progressive enhancement, and a marked contrast with the React-only editor. | 🟢 |
| F-INT-02 | The whole system rests on the HTML API's attribute-prefix discovery (BR-HTML-03). Without `get_attribute_names_with_prefix()` this would be regex-based again. | 🟢 |
| F-INT-03 | Directives are HTML attributes containing a small expression language (`namespace::path`, `!negation`). It is a template language embedded in attribute values, evaluated on both server and client — and the two evaluators must agree. | 🟢 |
| F-INT-04 | `merge_style_property()` reveals that directives compose with author-written inline styles rather than replacing them, which is required for correctness but easy to overlook when specifying behavior. | 🟡 |

## F1. `rest-api`

### The dispatch pipeline 🟢

`WP_REST_Server::dispatch( $request )` (`class-wp-rest-server.php:1062`):

```
dispatching_requests[] = $request                    ← a STACK: dispatch is reentrant
$result = apply_filters( 'rest_pre_dispatch', null, $this, $request )
if ! empty($result):
    rest_ensure_response(); WP_Error → error_to_response(); pop; RETURN   ← full bypass

$matched = match_request_to_handler( $request )
if WP_Error → error_to_response(); pop; RETURN

list($route, $handler) = $matched
if ! is_callable($handler['callback'])  → WP_Error 'rest_invalid_handler', 500

if no error:
    $check_required  = $request->has_valid_params()   ← ① VALIDATE
    if WP_Error → $error
    else:
        $check_sanitized = $request->sanitize_params() ← ② SANITIZE
        if WP_Error → $error

$response = respond_to_request( $request, $route, $handler, $error )
pop; return $response
```

**Validation precedes sanitization**, both derived from the route's `args` schema. A request is
rejected before any value is cleaned, so the callback receives data that has passed both stages.

`$dispatching_requests` being a stack (push at entry, pop at every exit) means a callback can
dispatch an internal REST request and the server tracks nesting correctly.

### The permission gate 🟢

`respond_to_request()` (`class-wp-rest-server.php:1250`):

```php
$response = apply_filters( 'rest_request_before_callbacks', $response, $handler, $request );

if ( ! is_wp_error($response) && ! empty( $handler['permission_callback'] ) ) {
    $permission = call_user_func( $handler['permission_callback'], $request );

    if ( is_wp_error( $permission ) ) {
        $response = $permission;
    } elseif ( false === $permission || null === $permission ) {
        $response = new WP_Error( 'rest_forbidden', …,
            array( 'status' => rest_authorization_required_code() ) );
    }
}
```

Three things to record precisely:

1. **`null` is treated as denial**, identically to `false`. A `permission_callback` that forgets to
   return is denied, not allowed — fail closed.
2. **The gate is `! empty( $handler['permission_callback'] )`.** If no callback is registered, the
   check is skipped entirely and the route is **public**. Since 5.5.0 `register_rest_route()` emits
   `_doing_it_wrong()` when the argument is missing, telling authors to pass `__return_true` for
   deliberately public routes — but it is a notice, not an enforcement. The route still works and
   still serves.
3. `rest_authorization_required_code()` returns **401** when no user is logged in and **403** when
   one is — so an anonymous request gets "authenticate" and a logged-in one gets "forbidden".

## F2. `http-api`

**Purpose.** Make outbound HTTP requests portably, with a safe variant that defends against
Server-Side Request Forgery. Underlies updates, oEmbed discovery, feeds, the block directory and
every plugin that calls a remote service.

**Primary files:** `wp-includes/http.php`, `wp-includes/class-wp-http.php`,
`wp-includes/class-wp-http-curl.php`, `class-wp-http-streams.php`,
`class-wp-http-requests-hooks.php`, `wp-includes/Requests/` (vendored), `class-wp-http-cookie.php`,
`class-wp-http-proxy.php`, `https-detection.php`, `https-migration.php`

### The two request families 🟢

| Family | Function | SSRF validated? |
|--------|----------|----------------|
| Unsafe | `wp_remote_get/post/head/request()` | ❌ |
| **Safe** | `wp_safe_remote_get/post/head/request()` | ✅ via `wp_http_validate_url()` |

The distinction is a naming convention with real consequences: a plugin fetching a user-supplied URL
with `wp_remote_get()` has an SSRF vulnerability; the same call with `wp_safe_remote_get()` does not.
The oEmbed discovery path (F-EMB-01) depends entirely on this.

### `wp_http_validate_url()` (`http.php:559`) — the SSRF guard 🟢

A precise, layered check. In order:

**1. Type and protocol**
```php
if ( ! is_string($url) || '' === $url || is_numeric($url) )      return false;
$url = wp_kses_bad_protocol( $url, array('http','https') );
if ( ! $url || strtolower($url) !== strtolower($original_url) )  return false;
```
The **round-trip equality check** is the important part: if `wp_kses_bad_protocol()` changed the URL
at all (stripping a `javascript:` prefix, decoding an obfuscated scheme), the URL is rejected rather
than used in its cleaned form. Sanitization is used as *detection*, not correction.

**2. Structural rejections**
```php
if ( ! $parsed_url || empty($parsed_url['host']) )               return false;
if ( isset($parsed_url['user']) || isset($parsed_url['pass']) )  return false;   // no userinfo
if ( false !== strpbrk($parsed_url['host'], ':#?[]') )           return false;   // no fragments,
                                                                                 // no IPv6 literals
```
Credentials in a URL (`http://user:pass@host/`) are rejected outright — they are a classic
parser-confusion vector. The `strpbrk` check rejects hosts containing `:#?[]`, which also means
**IPv6 literal addresses are not supported at all** by the safe path.

**3. Same-host exemption**
```php
$parsed_home = parse_url( get_option('home') );
$same_host   = strtolower($parsed_home['host']) === strtolower($parsed_url['host']);
```
Requests to the site's own host skip the IP checks entirely — necessary because a site on a private
network must still be able to call itself (loopback cron, REST self-requests).

**4. IP resolution and private-range blocking**

For non-same-host URLs, the host is resolved (`gethostbyname()`, unless it is already a dotted quad).
A `gethostbyname()` that returns the input unchanged means resolution failed → reject. The resulting
IPv4 address is then checked against **13 blocked ranges**:

| Range | Meaning |
|-------|---------|
| `0.0.0.0/8` | "this network" |
| `10.0.0.0/8` | private |
| `100.64.0.0/10` | CGNAT |
| `127.0.0.0/8` | loopback |
| `169.254.0.0/16` | link-local — **and cloud metadata endpoints** |
| `172.16.0.0/12` | private |
| `192.0.0.0/24` | IETF protocol assignments |
| `192.0.2.0/24` | TEST-NET-1 |
| `192.88.99.0/24` | 6to4 relay anycast |
| `192.168.0.0/16` | private |
| `198.18.0.0/15` | benchmarking |
| `198.51.100.0/24` | TEST-NET-2 |
| `203.0.113.0/24` | TEST-NET-3 |
| `224.0.0.0/4` | multicast |
| `240.0.0.0/4` | reserved, includes the broadcast address |

The inline comment on `169.254.0.0/16` explicitly names **cloud metadata** — this is a deliberate
defense against the AWS/GCP `169.254.169.254` credential-theft attack.

A blocked address can still be allowed by the `http_request_host_is_external` filter, which defaults
to `false` (blocked).

**5. Port allowlist**
```php
if ( empty($parsed_url['port']) ) return $url;                    // default port: fine
$allowed_ports = apply_filters( 'http_allowed_safe_ports', array(80, 443, 8080), $host, $url );
if ( in_array($port, $allowed_ports, true) ) return $url;
return false;
```
Only **80, 443 and 8080** are permitted when an explicit port is given. This blocks probing of
internal services on 3306, 6379, 11211 and so on.

### Transport negotiation 🟢

`WP_Http::_get_first_available_transport()` (`class-wp-http.php:547`) picks between
`WP_Http_Curl` and `WP_Http_Streams` based on availability and the request's requirements
(SSL, proxy support, streaming to file). `_dispatch_request()` (line 598) then executes it. The
vendored **Requests 2.0.17** library sits underneath, wired in by
`WP_HTTP_Requests_Hooks` which bridges Requests' own event system into WordPress filters.

`block_request()` (line 895) enforces `WP_HTTP_BLOCK_EXTERNAL` and `WP_ACCESSIBLE_HOSTS` — a
site-wide egress policy configurable in `wp-config.php`.

### Business rules 🟢

| # | Rule | Location |
|---|------|----------|
| BR-HTTP-01 | Only `wp_safe_remote_*` validates the URL; `wp_remote_*` does not. | `http.php:81` |
| BR-HTTP-02 | Only `http` and `https` schemes are accepted. | `http.php:564` |
| BR-HTTP-03 | If sanitization changes the URL in any way, it is rejected rather than corrected. | `http.php:565` |
| BR-HTTP-04 | URLs containing userinfo (`user:pass@`) are rejected. | `http.php:573` |
| BR-HTTP-05 | Hosts containing `:`, `#`, `?`, `[` or `]` are rejected, which excludes IPv6 literals. | `http.php:576` |
| BR-HTTP-06 | Requests to the site's own host bypass all IP-range checks. | `http.php:580` |
| BR-HTTP-07 | A hostname that fails DNS resolution is rejected. | `http.php:588` |
| BR-HTTP-08 | 13 IPv4 ranges are blocked, including `169.254.0.0/16` for cloud metadata. | `http.php:594` |

| BR-HTTP-10 | With an explicit port, only 80, 443 and 8080 are allowed (filterable). | `http.php:620` |

### Findings

| # | Finding | Confidence |
|---|---------|-----------|
| F-HTTP-01 | This is the most carefully written security function in WordPress. The range list is annotated with RFC intent, and the `169.254.0.0/16` comment names cloud metadata explicitly — evidence of threat-model-driven design rather than generic hardening. | 🟢 |
| F-HTTP-02 | The sanitize-then-compare pattern (reject if changed, rather than use the cleaned value) is the correct way to use a sanitizer as a validator, and is rare in the codebase. | 🟢 |
| F-HTTP-03 | **Validation is by resolved IP, but the request is made by hostname.** A DNS entry that resolves differently between the check and the request (DNS rebinding) defeats the guard. Nothing in this code pins the resolved address. | 🟡 |
| F-HTTP-04 | Only IPv4 is checked. IPv6 literals are rejected outright, but a hostname resolving to an IPv6 address is not range-checked — `gethostbyname()` returns IPv4 only. | 🟡 |
| F-HTTP-05 | Safety is opt-in by function name. Every `wp_remote_get()` on a user-supplied URL anywhere in the ecosystem is an SSRF, and the API makes the unsafe call the shorter, more obvious one. | 🟢 |
| F-HTTP-06 | The same-host exemption means a site whose `home` option points at an internal hostname can be used to reach that host — narrow, but a real edge. | 🟡 |

## F3. `xmlrpc`

**Purpose.** The legacy remote API — 78 methods across five protocol families, predating REST by a
decade. Still enabled by default.

**Primary files:** `xmlrpc.php`, `wp-includes/class-wp-xmlrpc-server.php` (211 KB),
`wp-includes/class-IXR.php`, `wp-includes/IXR/`

### The method surface 🟢

| Family | Methods | Purpose |
|--------|---------|---------|
| `wp.*` | 51 | WordPress-native API (posts, terms, users, media, options, comments) |
| `metaWeblog.*` | 8 | MetaWeblog API compatibility |
| `mt.*` | 8 | Movable Type API compatibility |
| `blogger.*` | 7 | Blogger API compatibility |
| `pingback.*` | 2 | `pingback.ping`, `pingback.extensions.getPingbacks` |
| `demo.*` | 2 | `demo.sayHello`, `demo.addTwoNumbers` |
| **Total** | **78** | |

Four of the six families exist purely for compatibility with blogging clients from the early 2000s.

### Enablement 🟢

```php
private function set_is_enabled() {
    $is_enabled = apply_filters( 'pre_option_enable_xmlrpc', false, 'enable_xmlrpc', false );
    if ( false === $is_enabled ) {
        $is_enabled = apply_filters( 'option_enable_xmlrpc', true, 'enable_xmlrpc' );
    }
    $this->is_enabled = apply_filters( 'xmlrpc_enabled', $is_enabled );
}
```

**XML-RPC is enabled by default.** The `enable_xmlrpc` option was deprecated in 3.5.0; the
`option_enable_xmlrpc` filter defaults to `true`, and the modern control is
`add_filter( 'xmlrpc_enabled', '__return_false' )`. The layered filter chain exists only to respect
old back-compat filters written against the removed option.

### The authentication model 🟢

**Every method call carries a username and password as XML-RPC parameters.** There is no session, no
token, no nonce. Each call independently authenticates, which means:

- credentials traverse the wire on **every** request;
- the endpoint is a password-guessing oracle with no built-in rate limit;
- `system.multicall` historically allowed many authentication attempts inside a single HTTP request
  (WordPress mitigated this specific amplification, but the per-call credential model remains).

`pingback.ping` additionally accepts a **remote URL and fetches it server-side**, making it an SSRF
and a reflection-amplification vector — the well-documented "pingback DDoS" surface.

| # | Rule | Location |
|---|------|----------|
| BR-XR-01 | XML-RPC is enabled by default; disabling requires the `xmlrpc_enabled` filter. | `class-wp-xmlrpc-server.php:195` |
| BR-XR-02 | The `enable_xmlrpc` option is deprecated since 3.5.0; its filters are consulted only for back-compat. | `class-wp-xmlrpc-server.php:191` |
| BR-XR-03 | Every method authenticates independently with a username and password parameter. | `class-wp-xmlrpc-server.php` |

### Findings

| # | Finding | Confidence |
|---|---------|-----------|
| F-XR-01 | A 211 KB always-on endpoint accepting credentials on every call is the largest legacy attack surface in WordPress. Four of its six method families serve clients that no longer exist. | 🟢 |
| F-XR-02 | Per-call credentials with no rate limiting make `xmlrpc.php` the canonical brute-force target. Core supplies no throttle here, exactly as with comment flooding (F-CMT-01). | 🟢 |

## F4. `feeds`

**Purpose.** Publish content as RSS 2.0, RSS 0.92, RDF and Atom, and consume external feeds via
SimplePie.

**Primary files:** `wp-includes/feed.php`, `feed-rss2.php`, `feed-rss.php`, `feed-rdf.php`,
`feed-atom.php`, `feed-rss2-comments.php`, `feed-atom-comments.php`,
`wp-includes/class-feed.php`, `wp-includes/rss.php`, `wp-includes/SimplePie/`

### Structure 🟢

**Publishing** is template-driven: `do_feed()` (called from `template-loader.php`, BR-TPL-03)
dispatches on the `feed` query var to `do_feed_rss2()`, `do_feed_atom()`, etc., each of which loads
the matching `feed-*.php` template. Those templates are plain PHP emitting XML, using the same
Loop as any theme template.

Registered feed slugs come from `WP_Rewrite::$feeds` — `feed`, `rdf`, `rss`, `rss2`, `atom`
(BR-RW-03) — and comment feeds have their own templates.

**Consuming** goes through SimplePie 1.9.0 (vendored), wrapped by `WP_Feed_Cache_Transient`
and `WP_SimplePie_File`/`WP_SimplePie_Sanitize_KSES`. The two wrapper classes are the interesting
part:

- `WP_SimplePie_File` routes SimplePie's HTTP through the WordPress HTTP API rather than its own,

### `WP_Ability` — the model 🟢

### The execution pipeline 🟢

`WP_Ability::execute()` (line 769) runs a strict five-stage sequence:

```
normalize_input()    (483)  → coerce input to the schema's shape
validate_input()     (519)  → JSON Schema validation; failure aborts
check_permissions()  (623)  → permission_callback; failure aborts
do_execute()         (671)  → invoke execute_callback
validate_output()    (712)  → JSON Schema validation of the RESULT
```

**Validating the output** is unusual and important: the ability's own return value is checked against
its declared schema before being handed back. An agent consuming an ability therefore receives data
that provably matches the contract it was given.

### Registration 🟢

`WP_Abilities_Registry::register()` (line 85) enforces:

```php
if ( ! preg_match( '/^[a-z0-9-]+\/[a-z0-9-]+$/', $name ) ) → _doing_it_wrong(); return null;
if ( $this->is_registered( $name ) )                       → _doing_it_wrong(); return null;
$args = apply_filters( 'wp_register_ability_args', $args, $name );
if ( isset($args['category']) && ! wp_has_ability_category($args['category']) )
                                                           → _doing_it_wrong(); return null;
```

A mandatory namespace, no silent overwrite of an existing ability, and a category that must already
be registered. Compare this to `register_post_type()` or `add_filter()`, both of which happily
overwrite.

`__wakeup()` / `__sleep()` are defined on both the registry and `WP_Ability` — deliberate
**unserialization guards**, because these objects hold callables.

# Tier G — Platform services

## G1. `cron`

**Purpose.** Schedule deferred and recurring work. WordPress has no daemon; "cron" is a queue in an
option, drained by piggybacking on incoming HTTP requests.

**Primary files:** `wp-includes/cron.php` (~1,400 lines), `wp-cron.php`

### The data model 🟢

The entire schedule lives in the **`cron` option**:

```
array(
    <timestamp> => array(
        <hook> => array(
            <md5(serialize($args))> => array( 'schedule' => …, 'args' => …, 'interval' => … )
        )
    ),
    'version' => 2
)
```

Keyed by timestamp, then hook, then an md5 of the serialized arguments. `_get_cron_array()` reads it,
migrating pre-v2 structures through `_upgrade_cron_array()`; `_set_cron_array()` writes it.

**One option row holds every scheduled event on the site**, and it is autoloaded — the same
single-row concentration as `rewrite_rules` (F-RW-02).

### The four built-in schedules 🟢

`hourly` (3600 s), `twicedaily` (43200 s), `daily` (86400 s), `weekly` (604800 s).
Additional schedules come from the `cron_schedules` filter.

### Duplicate prevention 🟢

`wp_schedule_single_event()` refuses an event that duplicates one already scheduled **within a
±10-minute window**, using an asymmetric window computation:

```php
$key = md5( serialize( $event->args ) );

if ( $event->timestamp < time() + 10 * MINUTE_IN_SECONDS ) {
    $min_timestamp = 0;                                   // near-future: ALL past events count
} else {
    $min_timestamp = $event->timestamp - 10 * MINUTE_IN_SECONDS;
}

if ( $event->timestamp < time() ) {
    $max_timestamp = time() + 10 * MINUTE_IN_SECONDS;     // past event: window from NOW
} else {
    $max_timestamp = $event->timestamp + 10 * MINUTE_IN_SECONDS;
}
```

The asymmetry is deliberate. For an event scheduled in the near future (or the past), the lower bound
becomes `0`, so **every past identical event counts as a duplicate** — otherwise a hook that keeps
failing to run would accumulate copies. For an event far in the future, the window is symmetric
around its own timestamp.

Identity is `hook + md5(serialize(args))`, so two events differing only in argument *order* are
distinct events.

### Spawning 🟢

`spawn_cron()` (`cron.php:899`) — the lock and dispatch logic:

```
if DOING_CRON defined or $_GET['doing_wp_cron'] set    → return false   (already inside cron)

$lock = (float) get_transient('doing_cron')
if $lock > $gmt_time + 600                             → $lock = 0      (clock skew / stale)
if $lock + WP_CRON_LOCK_TIMEOUT > $gmt_time            → return false   (another run in flight,
                                                                        or <60 s since the last)
$crons = wp_get_ready_cron_jobs()
if empty                                               → return false
if first timestamp > $gmt_time                         → return false   (nothing due yet)

if ALTERNATE_WP_CRON:
    require GET, not AJAX, not XML-RPC
    set_transient('doing_cron', $gmt_time)
    redirect to the same URI with ?doing_wp_cron=…, flush output, then require wp-cron.php
else:
    set_transient('doing_cron', $gmt_time)
    non-blocking HTTP request to site_url('wp-cron.php') with ?doing_wp_cron=…
```

Three properties:

1. **The lock is a transient**, so with a persistent object cache it is shared across processes, and
   without one it is a row in `wp_options`. Locking semantics therefore depend on the caching setup.
2. **A lock more than 10 minutes in the future is treated as invalid** — self-healing against clock
   skew or a corrupt value, the same shape as the maintenance-mode stale check (BR-BOOT-02).
3. **`WP_CRON_LOCK_TIMEOUT` (60 s by default) doubles as a rate limit.** Cron cannot spawn more than
   once a minute regardless of how many events are due.

`ALTERNATE_WP_CRON` exists for hosts where the loopback HTTP request fails: instead of calling
itself, WordPress redirects the *visitor's own browser* back to the same URL with a marker, and runs
cron during that second request. The visitor pays the latency.

### Business rules 🟢

| # | Rule | Location |
|---|------|----------|
| BR-CRON-01 | All scheduled events live in the single autoloaded `cron` option. | `cron.php:1261` |
| BR-CRON-02 | Event identity is `timestamp → hook → md5(serialize(args))`. | `cron.php:132` |
| BR-CRON-03 | Built-in schedules are `hourly`, `twicedaily`, `daily`, `weekly`. | `cron.php:1133` |
| BR-CRON-04 | A single event duplicating another within ±10 minutes is rejected. | `cron.php:135` |
| BR-CRON-05 | For an event due within 10 minutes or already past, **all** past identical events count as duplicates. | `cron.php:136` |
| BR-CRON-06 | Cron cannot spawn while `DOING_CRON` is defined or `doing_wp_cron` is present. | `cron.php:903` |
| BR-CRON-07 | A `doing_cron` lock more than 10 minutes in the future is discarded as invalid. | `cron.php:917` |
| BR-CRON-08 | `WP_CRON_LOCK_TIMEOUT` (60 s) prevents spawning more than once a minute. | `cron.php:921` |

### Findings

This is the defining characteristic of WP-Cron and the reason `DISABLE_WP_CRON` + a real crontab is the standard production configuration. | 🟢 |
| F-CRON-02 | The lock is a transient, so its cross-process correctness depends on whether a persistent object cache exists. Without one it is a database row with no atomic compare-and-set — two concurrent requests can both acquire it. | 🟢 |
| F-CRON-03 | All events in one autoloaded option means every request loads the full schedule, and a site with many events pays for it on every page view. | 🟢 |
| F-CRON-04 | The asymmetric duplicate window is subtle but correct: it prevents unbounded accumulation of a repeatedly-failing event while still allowing legitimate future scheduling. | 🟢 |
| F-CRON-05 | `ALTERNATE_WP_CRON` makes a visitor's browser the scheduler, adding a redirect to their request. A workaround for broken loopback that trades user latency for reliability. | 🟢 |
| F-CRON-06 | Argument identity is `md5(serialize($args))`, so argument order and type changes silently create distinct events. | 🟡 |

## G2. `internationalization`

**Purpose.** Translate strings, resolve the active locale, and switch locale mid-request.

**Primary files:** `wp-includes/l10n.php`, `wp-includes/locale.php`,
`wp-includes/class-wp-locale.php`, `wp-includes/class-wp-locale-switcher.php`,
`wp-includes/class-wp-textdomain-registry.php`, `wp-includes/l10n/` (5 classes),
`wp-includes/pomo/` (vendored gettext readers)

### The translation functions 🟢

| Function | Purpose |
|----------|---------|
| `__($text, $domain)` | translate, return |
| `_e($text, $domain)` | translate, echo |
| `_x($text, $context, $domain)` | translate with disambiguating context |
| `_n($single, $plural, $number, $domain)` | plural forms |
| `_nx($single, $plural, $number, $context, $domain)` | plural + context |
| `_n_noop($singular, $plural, $domain)` | register a plural pair for later translation |
| `esc_html__`, `esc_attr__`, `esc_html_e`, … | translate + escape |

Context (`_x`) exists because a source string is the lookup key: "Post" as a noun and "Post" as a verb
need different translations, and the context string disambiguates them.

### Locale determination 🟢

`determine_locale()` (`l10n.php:124`) is a precedence chain, and the order is security-relevant:

```
① apply_filters('pre_determine_locale', null)          → if a non-empty string, RETURN
② on wp-login.php with $_GET['wp_lang'] or $_COOKIE['wp_lang']
        → sanitize_locale_name( … )                     ← the ONLY user-supplied source
③ is_admin(), or a JSON request with ?_locale=user
        → get_user_locale()
④ during installation, $_REQUEST['language'] or $GLOBALS['wp_local_package']
        → sanitize_locale_name( … )
⑤ otherwise get_locale()                                ← the site option
→ apply_filters('determine_locale', $determined_locale)
```

**Only the login screen honours a request-supplied locale**, and only via `wp_lang` — because the
login form must be translatable before a user (and therefore a user locale) exists. Every
user-supplied value passes `sanitize_locale_name()` before use, since the locale becomes part of a
`.mo` filesystem path.

### Locale switching 🟢

`switch_to_locale()` / `restore_previous_locale()` (`l10n.php:1899`, `1940`) manage a **stack** in
`WP_Locale_Switcher`, initialized during boot (`wp-settings.php:737`). Switching reloads every loaded
textdomain in the new locale. This is what lets a single request send an email to one user in their
language and another in theirs.

### Translation loading 🟢

`WP_Textdomain_Registry` tracks which domains have been loaded and from where.
`load_textdomain()` (line 726) reads a `.mo` via the POMO library, or a `.l10n.php` file via
`WP_Translation_File_PHP` — the newer PHP-array format loaded at boot
(`wp-settings.php:123`–`127`), which is faster than parsing `.mo` binaries because opcache can hold
it.

`load_script_textdomain()` (line 1143) bridges to JavaScript: it locates the translation file for a
registered script handle and injects it as inline JS for `@wordpress/i18n`.

### Business rules 🟢

| # | Rule | Location |
|---|------|----------|
| BR-I18N-01 | `pre_determine_locale` returning a non-empty string overrides all other locale sources. | `l10n.php:125` |
| BR-I18N-02 | A request-supplied locale is honoured **only** on `wp-login.php`, via `wp_lang` in `$_GET` or `$_COOKIE`. | `l10n.php:130` |
| BR-I18N-03 | All user-supplied locale values pass `sanitize_locale_name()` before use. | `l10n.php:134` |
| BR-I18N-04 | The admin and `?_locale=user` JSON requests use the **user's** locale; the front end uses the site locale. | `l10n.php:140` |
| BR-I18N-05 | During installation, `$_REQUEST['language']` or `$wp_local_package` supplies the locale. | `l10n.php:146` |
| BR-I18N-06 | `switch_to_locale()` maintains a stack; `restore_previous_locale()` pops it. | `l10n.php:1899` |
| BR-I18N-07 | Switching locale reloads every already-loaded textdomain. | `class-wp-locale-switcher.php` |
| BR-I18N-08 | Translations load from `.mo` (POMO) or `.l10n.php` (PHP array). | `wp-settings.php:123` |
| BR-I18N-09 | The source English string **is** the lookup key; `_x()` adds a context prefix to disambiguate. | `l10n.php:409` |

### Findings

| # | Finding | Confidence |
|---|---------|-----------|
| F-I18N-01 | The login-screen locale is the only user-controlled locale input, and it becomes part of a filesystem path. `sanitize_locale_name()` is therefore a path-traversal boundary, not a formatting nicety. | 🟢 |
| F-I18N-02 | Using the English source string as the key means changing a typo in an English string orphans every translation of it. | 🟢 |
| F-I18N-03 | The `.l10n.php` format is a performance answer to `.mo` parsing: a PHP array that opcache can retain across requests. | 🟢 |
| F-I18N-04 | Locale switching is stack-based and reloads all textdomains, so switching in a loop is expensive — a per-recipient email loop pays a full reload per iteration. | 🟡 |

## G3. `formatting-and-sanitization`

**Purpose.** Text transformation on the way in and out. At 350 KB, `formatting.php` is the single
largest file in WordPress.

**Primary files:** `wp-includes/formatting.php` (350 KB), `wp-includes/utf8.php`,
`wp-includes/compat-utf8.php`, `wp-includes/class-wp-token-map.php`

### What lives here 🟢

Four categories mixed in one file:

| Category | Representative functions |
|----------|-------------------------|
| Escaping | `esc_html()`, `esc_attr()`, `esc_url()`, `esc_url_raw()`, `esc_js()`, `esc_textarea()`, `esc_xml()` |
| Sanitizing | `sanitize_text_field()`, `sanitize_title()`, `sanitize_key()`, `sanitize_file_name()`, `sanitize_email()`, `sanitize_html_class()`, `sanitize_option()`, `sanitize_locale_name()` |
| Transforming | `wpautop()`, `wptexturize()`, `convert_smilies()`, `convert_chars()`, `shortcode_unautop()`, `make_clickable()` |
| Slashing | `wp_slash()`, `wp_unslash()`, `addslashes_gpc()`, `stripslashes_deep()` |

### The escaping contract 🟢

Escaping is **context-specific and applied at output**, never at storage:

| Output context | Function |
|----------------|----------|
| HTML text | `esc_html()` |
| HTML attribute | `esc_attr()` |
| URL in HTML | `esc_url()` |
| URL for storage/redirect | `esc_url_raw()` |
| Inline JavaScript | `esc_js()` |
| `<textarea>` content | `esc_textarea()` |
| XML | `esc_xml()` |

`esc_url()` vs `esc_url_raw()` is the distinction most often confused: `esc_url()` additionally
HTML-encodes `&` to `&amp;`, which is correct in markup and wrong in a `Location:` header or a
database column.

### `wpautop()` and `wptexturize()` 🟢

`wpautop()` converts double newlines to `<p>` and single newlines to `<br>`, while preserving a list
of block-level tags it must not wrap. `wptexturize()` converts straight quotes to curly, `--` to en
dash, `...` to ellipsis, and similar. Both operate on **rendered output** via `the_content`, not on
stored content — which is why the database holds plain newlines and the page shows paragraphs.

Both maintain internal lists of tags to skip (`<pre>`, `<code>`, `<script>`, shortcodes), and both are
long-standing sources of edge-case bugs precisely because they are regex transformations over
arbitrary HTML — the problem the HTML API (E6) was built to end.

`WP_Token_Map` (loaded at boot, `wp-settings.php:113`) is a newer data structure for efficient
large-scale string substitution, used for HTML entity handling.

### Slashing 🟢

Recall BR-BOOT-05 / F-BOOT-05: `wp_magic_quotes()` re-slashes all superglobals during boot, so
**every value read from `$_GET`, `$_POST`, `$_COOKIE` or `$_REQUEST` is slashed**. `wp_unslash()`
must be called before use, and `wp_slash()` before passing data to functions that expect slashed
input (`wp_insert_post()` does). This inverted convention is the most persistent source of
double-escaping bugs in the ecosystem.

### Business rules 🟢

| # | Rule | Location |
|---|------|----------|
| BR-FMT-01 | Escaping is applied at output and chosen by context; there is no single universal escaper. | `formatting.php` |
| BR-FMT-02 | `esc_url()` encodes `&` to `&amp;`; `esc_url_raw()` does not. | `formatting.php` |

## G4. `kses-security`

**Purpose.** "KSES Strips Evil Scripts" — an HTML allowlist filter. The last line of defense for
untrusted markup.

**Primary files:** `wp-includes/kses.php` (~3,200 lines)

### The model 🟢

KSES is an **allowlist**, not a blocklist: anything not explicitly permitted is removed.

`wp_kses( $content, $allowed_html, $allowed_protocols )` is the entry point.
`wp_kses_allowed_html( $context )` supplies context-specific allowlists — `post`, `strip`, `data`,
`entities`, `user_description`, `pre_user_description` — and `wp_kses_post()` is the common wrapper
for post-content rules.

### Allowed protocols 🟢

`wp_allowed_protocols()` (`functions.php:7352`) returns **22 protocols**:

`http`, `https`, `ftp`, `ftps`, `mailto`, `news`, `irc`, `irc6`, `ircs`, `gopher`, `nntp`, `feed`,
`telnet`, `mms`, `rtsp`, `sms`, `svn`, `tel`, `fax`, `xmpp`, `webcal`, `urn`

Memoized in a static, and **filterable only before `wp_loaded`**:

```php
if ( ! did_action( 'wp_loaded' ) ) {
    $protocols = array_unique( (array) apply_filters( 'kses_allowed_protocols', $protocols ) );
}
```

Freezing the list after boot means a late-loading plugin cannot widen the protocol allowlist for
content that has already been filtered — a deliberate temporal boundary on a security-critical list.

### Protocol checking — the obfuscation defenses 🟢

`wp_kses_bad_protocol_once()` (`kses.php:2099`) is where the real work happens:

```php
// ① repair truncated colon entities so they are recognized
$content = preg_replace( '/(&#0*58(?![;0-9])|&#x0*3a(?![;a-f0-9]))/i', '$1;', $content );

// ② split on a colon in ANY of its encodings
$content2 = preg_split( '/:|&#0*58;|&#x0*3a;|&colon;/i', $content, 2 );

if ( isset($content2[1]) && ! preg_match('%/\?%', $content2[0]) ) {
    $protocol = wp_kses_bad_protocol_once2( $content2[0], $allowed_protocols );

    if ( 'feed:' === $protocol ) {
        if ( $count > 2 ) return '';                                     // ③ recursion cap
        $content = wp_kses_bad_protocol_once( $content, $allowed_protocols, ++$count );
        if ( empty($content) ) return $content;
    }
    $content = $protocol . $content;
}
```

And the scheme normalizer:

```php
function wp_kses_bad_protocol_once2( $scheme, $allowed_protocols ) {
    $scheme = wp_kses_decode_entities( $scheme );      // &#106;avascript → javascript
    $scheme = preg_replace( '/\s/', '', $scheme );      // java\nscript   → javascript
    $scheme = wp_kses_no_null( $scheme );               // java\0script   → javascript
    $scheme = strtolower( $scheme );                    // JaVaScRiPt     → javascript
    return in_allowlist ? "$scheme:" : '';
}
```

Four normalizations before comparison — entity decoding, whitespace stripping, null-byte removal and
lowercasing — each corresponding to a historical bypass technique. The colon regex recognizing
`&#58;`, `&#x3a;` and `&colon;` covers the encoded-colon evasion.

**The `feed:` recursion** exists because `feed:javascript:alert(1)` is a real nested-scheme attack:
`feed:` is allowed, so KSES must re-examine what follows it. The `$count > 2` cap bounds the
recursion — `feed:feed:feed:…` terminates rather than exhausting the stack.

`wp_kses_normalize_entities()` (line 2168) disarms entities by converting every `&` to `&amp;` and
then selectively re-permitting valid named and numeric entities.

## G5. `error-handling-and-recovery-mode`

**Purpose.** Survive a fatal PHP error. Catch it, identify which plugin or theme caused it, pause
that extension, and email the administrator a link to a mode where the site loads without it.

**Primary files:** `wp-includes/class-wp-error.php`, `wp-includes/class-wp-exception.php`,
`wp-includes/error-protection.php`, `wp-includes/class-wp-fatal-error-handler.php`,
`wp-includes/class-wp-recovery-mode.php` + four service classes,
`wp-includes/class-wp-paused-extensions-storage.php`

### `WP_Error` 🟢

WordPress's error type, present since 2.1 and used everywhere in preference to exceptions. It holds
**multiple codes, each with multiple messages and one data payload**, which is why
`$error->get_error_message()` returns only the first. `is_wp_error()` is the universal check.

`WP_Exception` (newer) coexists with it — core is midway through a slow migration and both are in
active use.

### The fatal error handler 🟢

Registered at `wp-settings.php:69`, **before the database connects** (BR-BOOT-10), and running via
`register_shutdown_function`.

`should_handle_error()` (`class-wp-fatal-error-handler.php:100`) handles exactly five error types:

`E_ERROR`, `E_PARSE`, `E_USER_ERROR`, `E_COMPILE_ERROR`, `E_RECOVERABLE_ERROR`

Anything else is ignored unless `wp_should_handle_php_error` returns true. Warnings and notices do
not trigger recovery — only genuinely fatal conditions.

`display_error_template()` looks for `wp-content/fatal-error-handler.php` (a fifth drop-in, alongside
the four in F-BOOT-03) before falling back to the built-in white-screen replacement.

### Recovery mode 🟢

`WP_Recovery_Mode::handle_error()` (`class-wp-recovery-mode.php:168`):

```
get_extension_for_error( $error )        ← map the error's file path to a plugin or theme
store_error( $error )                    ← record in paused-extensions storage
send the recovery email with a signed link
```

Four collaborating services:

| Service | Responsibility |
|---------|---------------|
| `WP_Recovery_Mode_Key_Service` | generate, store and validate one-time keys |
| `WP_Recovery_Mode_Link_Service` | build and verify the emailed link |
| `WP_Recovery_Mode_Cookie_Service` | set/validate/clear the `RECOVERY_MODE_COOKIE` |
| `WP_Recovery_Mode_Email_Service` | compose and rate-limit the email |

**Rate limiting and TTL:**

```php
protected function get_email_rate_limit() {
    return apply_filters( 'recovery_mode_email_rate_limit', DAY_IN_SECONDS );
}

protected function get_link_ttl() {
    $rate_limit = $this->get_email_rate_limit();
    $valid_for  = apply_filters( 'recovery_mode_email_link_ttl', $rate_limit );
    return max( $valid_for, $rate_limit );          // ← link TTL can never be SHORTER than the
                                                    //   rate limit
}
```

The `max()` is the careful part: if the link expired before the next email could be sent, an
administrator would be locked out with no way to get a fresh link. The constraint makes that
impossible regardless of how the filters are set.

The recovery cookie is set with `httponly = true` and `secure = is_ssl()`, on both `COOKIEPATH` and
`SITECOOKIEPATH`, and is cleared by setting it to expire a year in the past.

**Paused extensions** are recorded via `WP_Paused_Extensions_Storage`, which is what
`wp_skip_paused_plugins()` / `wp_skip_paused_themes()` read at boot (BR-BOOT-05). The loop closes:
fatal → identify → pause → skip on next request → site loads.

| # | Rule | Location |

## H2. `filesystem-api`

**Purpose.** Write files portably, including on hosts where PHP cannot write directly and must go
through FTP or SSH.

**Primary files:** `wp-admin/includes/file.php`, `wp-admin/includes/class-wp-filesystem-base.php`,
`-direct.php`, `-ftpext.php`, `-ftpsockets.php`, `-ssh2.php`,
`wp-admin/includes/class-pclzip.php`

### Method detection 🟢

`get_filesystem_method()` (`wp-admin/includes/file.php`) is a capability probe, and the ownership
test is its centre:

```php
$method = defined('FS_METHOD') ? FS_METHOD : false;

if ( ! $method ) {
    $temp_file_name = $context . 'temp-write-test-' . str_replace('.', '-', uniqid('', true));
    $temp_handle    = @fopen( $temp_file_name, 'w' );

    if ( $temp_handle ) {
        $wp_file_owner   = @fileowner( __FILE__ );          // who owns WordPress's files
        $temp_file_owner = @fileowner( $temp_file_name );   // who owns files PHP creates

        if ( false !== $wp_file_owner && $wp_file_owner === $temp_file_owner ) {
            $method = 'direct';   $GLOBALS['_wp_filesystem_direct_method'] = 'file_owner';
        } elseif ( $allow_relaxed_file_ownership ) {
            $method = 'direct';   $GLOBALS['_wp_filesystem_direct_method'] = 'relaxed_ownership';
        }
        fclose( $temp_handle ); @unlink( $temp_file_name );
    }
}
if ( ! $method && $args['connection_type'] === 'ssh' && extension_loaded('ssh2') ) $method = 'ssh2';
if ( ! $method && extension_loaded('ftp') )                                        $method = 'ftpext';
…else 'ftpsockets'
```

**Writability alone is not enough.** WordPress writes a temp file, then compares its owner to the
owner of WordPress's own files. If they differ, direct writing is refused even though it succeeded —
because on a shared host, files created by the web server user but owned differently can become
unreadable, unwritable or a privilege-escalation vector between accounts.

`$allow_relaxed_file_ownership` opts out of the check for contexts where the risk is acceptable, and
the chosen rationale is recorded in a global for diagnostics.

Special case: `WP_LANG_DIR` may not exist yet, so the check runs against its parent.

Fallback order: **direct → ssh2 → ftpext → ftpsockets**, with `FS_METHOD` overriding everything.

### Update package verification 🟢

`verify_file_signature()` (`file.php:1410`) — Ed25519 signatures over update packages:

```
if ! sodium_crypto_sign_verify_detached() OR no sha384
      → WP_Error 'signature_verification_unsupported'     ← unsupported, NOT failed
if sodium extension absent AND ! ParagonIE_Sodium_Compat::polyfill_is_fast()
      → run runtime_speed_test(100, 10); if too slow, WP_Error
$trusted_keys = wp_trusted_keys();
$file_hash    = hash_file( 'sha384', $filename, true );
mbstring_binary_safe_encoding();
foreach signatures:
    $signature_raw = base64_decode($signature)
    if strlen !== SODIUM_CRYPTO_SIGN_BYTES → skip (count it)
    foreach trusted key:
        sodium_crypto_sign_verify_detached( $signature_raw, $file_hash, $key_raw ) → success
```

Three deliberate details:

1. **Missing crypto is "unsupported", not "invalid".** The distinction matters: an old PHP without
   sodium must still be able to update, so verification degrades rather than blocking.
2. **A runtime speed test.** Pure-PHP Ed25519 is slow enough that verifying a large package could
   exhaust `max_execution_time`. WordPress measures the polyfill first and refuses rather than
   hanging.
3. **Signature length is validated before use**, and skipped signatures are counted so the error can
   distinguish "no valid signature" from "no signature at all".

| BR-FS-11 | `PclZip` is the pure-PHP fallback when `ZipArchive` is unavailable. | `class-pclzip.php` |

### Findings

| # | Finding | Confidence |
|---|---------|-----------|
| F-FS-01 | The ownership check is a genuinely thoughtful piece of shared-hosting security: "can write" and "should write" are different questions, and WordPress asks the second. | 🟢 |
| F-FS-02 | Signature verification degrading to "unsupported" means a host without sodium installs updates unverified. Availability was chosen over integrity, deliberately. | 🟢 |
| F-FS-03 | The polyfill speed test is a rare case of runtime performance measurement gating a security operation. | 🟢 |

## H3. `updates-and-upgrader`

**Purpose.** Check for, download, verify and install core, plugin, theme and translation updates;
and migrate the database schema between versions.

**Primary files:** `wp-includes/update.php`, `wp-admin/includes/class-wp-upgrader.php`,
`wp-admin/includes/update.php`, `wp-admin/includes/update-core.php`,
`wp-admin/includes/schema.php`, `wp-admin/includes/upgrade.php`, `wp-admin/upgrade.php`

### Update checks 🟢

`wp_version_check()`, `wp_update_plugins()` and `wp_update_themes()` POST the site's inventory to
api.wordpress.org and cache the response in the `update_core` / `update_plugins` / `update_themes`
site transients.

**Adaptive timeouts** (`update.php:383`–`393`, mirrored at 670–680):

| Condition | Timeout |
|-----------|---------|
| Currently doing cron | 1 minute |
| A recent request/failure | 1 hour |
| Intermediate | 2 hours |
| Steady state | 12 hours |

`wp_get_update_data()` and the admin UI additionally suppress a re-check within 12 hours of
`last_checked` (line 1033). The escalating backoff means a site that just checked does not check
again, and a site with a failing connection backs off rather than retrying every request.

### `WP_Upgrader` 🟢

The install pipeline, shared by `Plugin_Upgrader`, `Theme_Upgrader`, `Core_Upgrader`,
`Language_Pack_Upgrader`:

```
init() → setup the skin (UI feedback)
download_package()      → to a temp file, then verify_file_signature()
unpack_package()        → ZipArchive or PclZip
install_package()       → clear destination, copy files, run hooks
  → maintenance mode ON for the duration
```

`Core_Upgrader` additionally routes through `update-core.php`, which knows the file manifests of
prior versions so it can delete files that no longer exist.

### Database migration 🟢

`wp-admin/includes/upgrade.php` holds version-gated functions:

```php
if ( $wp_current_db_version < 25824 ) upgrade_400();
if ( $wp_current_db_version < 36686 ) upgrade_460();
…
```

each applying the schema deltas of that release, run in sequence from whatever version the site is
on. `dbDelta()` compares `wp_get_db_schema()`'s `CREATE TABLE` statements to the live schema and
emits the `ALTER` statements needed — a diffing migrator rather than a migration log.

`$wp_db_version` (61833 in this build) is the sole version marker.

### Business rules 🟢

| # | Rule | Location |
|---|------|----------|
| BR-UPD-01 | Update data is cached in the `update_core`, `update_plugins` and `update_themes` site transients. | `update.php` |
| BR-UPD-02 | The check timeout escalates: 1 minute during cron, 1 hour after a recent attempt, 2 hours, then 12 hours. | `update.php:383` |
| BR-UPD-03 | A re-check is suppressed within 12 hours of `last_checked`. | `update.php:1033` |
| BR-UPD-04 | Packages are signature-verified after download and before extraction. | `class-wp-upgrader.php` |
| BR-UPD-05 | The site enters maintenance mode for the duration of `install_package()`. | `class-wp-upgrader.php` |
| BR-UPD-06 | Core updates use `update-core.php`, which carries per-version file manifests to remove obsolete files. | `update-core.php` |
| BR-UPD-07 | Schema migrations are version-gated `upgrade_NNN()` functions applied in sequence. | `upgrade.php` |
| BR-UPD-08 | `dbDelta()` diffs the declared schema against the live one and emits the necessary `ALTER` statements. | `upgrade.php` |
| BR-UPD-09 | `$wp_db_version` is the single schema version marker. | `version.php` |

### Findings

| # | Finding | Confidence |
|---|---------|-----------|
| F-UPD-01 | The escalating timeout is a well-judged backoff: a failing update endpoint costs a site one slow request per hour rather than one per page view. | 🟢 |
| F-UPD-02 | `dbDelta()` infers migrations by diffing rather than recording them. It cannot express data migrations, only schema shape, which is why `upgrade_NNN()` functions exist alongside it. | 🟢 |
| F-UPD-03 | Auto-updates plus maintenance mode plus paused extensions plus recovery mode compose into a genuinely resilient update story — each mechanism covers a different failure mode of the others. | 🟢 |
| F-UPD-04 | Core knows the file manifest of every prior version in order to clean up. That list is hand-maintained in `update-core.php`. | 🟢 |

## H4. `site-health`

**Purpose.** Run diagnostic tests and surface configuration problems, with a debug-data collector for
support.

**Primary files:** `wp-admin/site-health.php`, `wp-admin/includes/class-wp-site-health.php`,
`class-wp-site-health-auto-updates.php`, `class-wp-debug-data.php`, plus the
`site-health` REST controller

### Structure 🟢

Tests are split into **direct** (run synchronously during the page load) and **async** (fetched by
JavaScript afterwards), so a slow test — such as a loopback HTTP request — does not block the page.

Each test returns a structured result: `label`, `status` (`good` / `recommended` / `critical`),
`badge` (label + colour), `description`, `actions`, `test`.

Coverage includes PHP version, database version, HTTPS status, REST availability, **loopback
requests** (which is how a site discovers that WP-Cron cannot spawn — F-CRON-01), scheduled events,
plugin/theme currency, file permissions, and available PHP extensions.

`WP_Site_Health` is instantiated during boot (`wp-settings.php:760`) specifically **so its cron
events can fire** — a class loaded on every request to keep a scheduled hook alive.

`WP_Debug_Data` collects the environment report shown on the Info tab and copied into support
requests.

| BR-SH-02 | Statuses are `good`, `recommended` and `critical`. | `class-wp-site-health.php` |
| BR-SH-03 | `WP_Site_Health` is instantiated during boot so its cron events can fire. | `wp-settings.php:760` |

### Findings

## H5. `multisite`

**Purpose.** Run many sites from one installation, sharing users and a codebase while separating
content.

**Primary files:** `wp-includes/ms-blogs.php`, `ms-functions.php`, `ms-load.php`, `ms-network.php`,
`ms-site.php`, `ms-settings.php`, `ms-files.php`, `ms-default-constants.php`,
`ms-default-filters.php`, `class-wp-network.php`, `class-wp-site.php`,
`class-wp-network-query.php`, `class-wp-site-query.php`, `wp-admin/network/` (30 screens),
`wp-signup.php`, `wp-activate.php`

### The model 🟢

| Concept | Storage |
|---------|---------|
| Network | `wp_site` + `wp_sitemeta` |
| Site (blog) | `wp_blogs` + `wp_blogmeta` |
| Site content | `wp_{$blog_id}_posts`, `_postmeta`, `_comments`, … — **one table set per site** |
| Users | `wp_users` + `wp_usermeta` — **shared network-wide** |
| Signups | `wp_signups` |

`$wpdb->set_blog_id()` (BR-DB-13) recomputes the blog-scoped table names; global and ms-global tables
are untouched. `switch_to_blog()` / `restore_current_blog()` maintain a stack, changing
`$wpdb`'s prefix, the object cache's `blog_prefix` (BR-CACHE-02) and various globals.

**Role membership is per site.** Because roles are stored in `wp_usermeta` under
`{$prefix}capabilities` (BR-CAP-13), a user has a `wp_capabilities` key for site 1 and a
`wp_3_capabilities` key for site 3 — one user row, many role assignments.

**Super admins** sit above the role system entirely and bypass `has_cap()` (BR-CAP-03).

`sunrise.php` is the fifth drop-in (F-BOOT-03), loaded before the network is resolved, used for
domain mapping.

### Business rules 🟢

| # | Rule | Location |
|---|------|----------|
| BR-MS-01 | Each site gets its own prefixed table set; users and usermeta are shared network-wide. | `class-wpdb.php:291` |
| BR-MS-02 | `switch_to_blog()` maintains a stack and must be paired with `restore_current_blog()`. | `ms-blogs.php` |
| BR-MS-03 | Switching a blog changes `$wpdb`'s prefix and the object cache's blog prefix together. | `class-wpdb.php:1043`, `cache.php:385` |
| BR-MS-04 | Role membership is per site, stored as `{$prefix}capabilities` user meta. | `class-wp-user.php` |
| BR-MS-05 | Super admins bypass every capability check except `do_not_allow`. | `class-wp-user.php:795` |
| BR-MS-06 | `sunrise.php` loads before network resolution, enabling domain mapping. | `ms-settings.php` |
| BR-MS-07 | Network-activated plugins load before `muplugins_loaded`. | `wp-settings.php:523` |
| BR-MS-08 | Site and network options live in `wp_blogmeta` and `wp_sitemeta`. | `option.php:2001` |

### Findings

| # | Finding | Confidence |
|---|---------|-----------|
| F-MS-01 | Table-per-site means a 1,000-site network has ~11,000 tables. Schema migrations must run per site, and `dbDelta()` is invoked once per blog. | 🟢 |
| F-MS-02 | `switch_to_blog()` changes global state and must be unwound manually; an unbalanced switch corrupts every subsequent query in the request. | 🟢 |
| F-MS-03 | Multisite is not a layer on top of WordPress — it is `if ( is_multisite() )` branches threaded through the kernel: `wpdb`, the object cache, capabilities, options and boot all behave differently. | 🟢 |
| F-MS-04 | Shared users with per-site roles is the right model, but it means user meta grows linearly with the number of sites a user belongs to. | 🟡 |

# Tier I — Compatibility

## I1. `deprecated-compat`

**Purpose.** Keep code written for WordPress 1.5 working on WordPress 7.2.

**Primary files:** `wp-includes/deprecated.php` (6,534 lines),
`wp-admin/includes/deprecated.php` (1,602), `wp-includes/ms-deprecated.php` (755),
`wp-includes/pluggable-deprecated.php` (221), `wp-includes/compat.php`,
`wp-includes/php-compat/`, `wp-includes/registration.php`, `registration-functions.php`,
`rss-functions.php`, `class-snoopy.php`, `wp-db.php`, `class.wp-scripts.php`,
`class.wp-styles.php`, `class.wp-dependencies.php`

### Scale 🟢

**9,112 lines** exist solely for backward compatibility — about **1.4%** of the PHP codebase.

Two distinct mechanisms:

1. **Deprecated functions** — retained, functional, and calling `_deprecated_function()`,
   `_deprecated_argument()`, `_deprecated_file()` or `_deprecated_hook()`, which emit a notice only
   when `WP_DEBUG` is on. The old function still does its job.
2. **Compatibility shims** — `compat.php` and `php-compat/` polyfill PHP functions missing on older
   supported versions (`str_contains`, `str_starts_with`, `array_is_list`, `mb_*` fallbacks), so core
   can use modern syntax while supporting PHP 7.4.

**Filename aliases** are a third category: `class.wp-scripts.php` and `class-wp-scripts.php` both
exist because plugins `require`d the old filename directly. Even *file paths* are part of the
compatibility contract.

`apply_filters_deprecated()` / `do_action_deprecated()` (BR-HOOK-11) extend the same treatment to
hooks: a removed hook still fires, and only warns if someone is listening.

### Business rules 🟢

| # | Rule | Location |
|---|------|----------|
| BR-DEP-01 | Deprecated functions remain fully functional; only a debug-time notice is added. | `deprecated.php` |
| BR-DEP-02 | Deprecation notices appear only when `WP_DEBUG` is enabled. | `functions.php` |
| BR-DEP-03 | Deprecated hooks still fire, warning only if a callback is registered. | `plugin.php:723` |
| BR-DEP-04 | Old file paths are preserved as aliases because plugins require them directly. | `class.wp-scripts.php` |
| BR-DEP-05 | `compat.php` polyfills newer PHP functions so core can use them on PHP 7.4. | `compat.php` |
| BR-DEP-06 | Nothing in the deprecated layer has a removal date. | — |

### Findings

| # | Finding | Confidence |
|---|---------|-----------|
| F-DEP-01 | 9,112 lines of compatibility code is not technical debt — it is the product decision that made WordPress ubiquitous. A site from 2008 still upgrades. | 🟢 |
| F-DEP-02 | Preserving *filenames* as public API is the strongest statement of the compatibility commitment in the codebase. | 🟢 |
| F-DEP-03 | Nothing is ever removed and nothing has a sunset date, so the compatibility surface only grows. Every deprecated function is also a permanently supported one. | 🟢 |
| F-DEP-04 | Deprecation notices are invisible in production, so a plugin can rely on deprecated APIs indefinitely without its users ever seeing a warning. | 🟢 |
