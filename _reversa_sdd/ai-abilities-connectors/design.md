## Main Flow

1. **five-stage ability execution** — normalize_input, validate_input against JSON Schema, check_permissions, do_execute, then validate_output against JSON Schema. Output validation is unique in core.
   Source: `wp-includes/abilities-api/class-wp-ability.php:769` 🟢
2. **strict registration** — Mandatory namespace pattern, no overwrite of an existing name, and a category that must already exist; all three fail with _doing_it_wrong() and a null return.
   Source: `wp-includes/abilities-api/class-wp-abilities-registry.php:85` 🟢
3. **ability to AI function bridge** — The ability-function resolver turns a registered ability's schemas into an LLM tool definition, so one declaration becomes both a REST endpoint and a model-callable function.
   Source: `wp-includes/ai-client/class-wp-ai-client-ability-function-resolver.php` 🟢

## Alternative Flows

## Risks and Gaps

- 🟢 **F-AI-01** — The strictest contracts in WordPress: mandatory namespaces, no overwrite, schema-validated input and output, private-by-default visibility. It reads as if written by people who catalogued core's defaults and chose the opposite each time.
- 🟢 **F-AI-02** — Output validation is unique in core; nothing else verifies that a callback returned what it promised.
- 🟡 **F-AI-03** — Checking permissions after input validation lets an unauthorized caller learn whether their input was well-formed; the reverse order would be more conservative.
- 🟢 **F-AI-04** — The ability-to-AI-function bridge means every registered ability is potentially reachable by an LLM, with permission_callback as the only gate, in a context its author may not have anticipated.
- 🟢 **F-AI-05** — 156 PHP files of AI infrastructure ship in core with no counterpart in existing WordPress documentation; any specification written before this release is now incomplete.
- 🟢 **F-AI-06** — Explicit __wakeup()/__sleep() guards show awareness of PHP object-injection risk, a defense core does not apply to most other registries.
