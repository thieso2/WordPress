## Main Flow

1. **multi-instance single-option storage** — One WP_Widget subclass serves many placed widgets; all instance settings live in one option row keyed by number, with _register() iterating stored numbers to call _register_one().
   Source: `wp-includes/class-wp-widget.php:253` 🟢
2. **meta-driven menu item model** — A menu item's type, target object, parent and presentation all live in nine post meta rows; the post row itself carries only ordering and an optional title override.
   Source: `wp-includes/nav-menu.php` 🟢
3. **orphan tombstoning** — _menu_item_orphaned flags items whose referenced object was deleted, standing in for a foreign key the schema lacks.
   Source: `wp-includes/nav-menu.php` 🟢

## Risks and Gaps

- 🟢 **F-WIDG-01** — The one-option-per-widget-class model means every instance is loaded whenever any one is read, and a corrupt entry affects all instances.
- 🟢 **F-WIDG-02** — Sanitization is delegated to third-party update() implementations, making widget input the least uniformly-validated data path in core.
- 🟢 **F-MENU-01** — Menu items store their meaning in nine meta rows each; a 50-item menu is 50 posts and roughly 450 meta rows, which is why menus are a documented performance concern.
- 🟢 **F-MENU-02** — Two parallel parent columns exist on the same row and only one is used; any tool reasoning about post_parent for menu items is wrong.
- 🟡 **F-MENU-03** — _menu_item_orphaned is a manual tombstone standing in for the foreign key the schema lacks, the same pattern as the taxonomy cycle guard.
