## Main Flow

1. **four-step scheme normalization** — Decode entities, strip whitespace, remove null bytes, lowercase; each step answers a specific historical XSS bypass technique before the allowlist comparison.
   Source: `wp-includes/kses.php:2118` 🟢
2. **multi-encoding colon detection** — preg_split on ':' plus its numeric, hex and named entity encodings, with a prior repair pass for truncated colon entities.
   Source: `wp-includes/kses.php:2099` 🟢
3. **depth-capped nested scheme recursion** — feed: is allowed, so what follows it is re-examined recursively with a hard cap of 2 levels, defeating feed:javascript: while keeping feed: support.
   Source: `wp-includes/kses.php:2107` 🟢

## Risks and Gaps

- 🟢 **F-KSES-01** — The four-step scheme normalization is a catalogue of two decades of XSS bypass attempts, each line answering a specific historical technique; the most attack-informed code in WordPress after wp_http_validate_url().
- 🟢 **F-KSES-02** — The feed: recursion with a hard depth cap shows the nested-scheme attack was found in the wild and fixed without removing feed: support.
- 🟢 **F-KSES-03** — Freezing the protocol allowlist at wp_loaded is a rare temporal security boundary: the same filter behaves differently depending on when it runs.
- 🟢 **F-KSES-04** — KSES only applies where it is called; content saved by a user with unfiltered_html bypasses it entirely, making it a capability-gated defense rather than a universal one.
- 🟡 **F-KSES-05** — KSES parses HTML with regular expressions while the HTML API exists in the same codebase; it has not been migrated and is the higher-risk of the two.
