## 1. The model

Three layers, each answering a different question (see `domain.md` §2):

```
current_user_can( 'edit_post', 42 )
        │
        ├─ META CAPABILITY ─── object-specific, NEVER stored
        │       map_meta_cap() inspects post 42's author, status and type
        │       ↓
        ├─ PRIMITIVE CAPABILITIES ─── e.g. ['edit_posts', 'edit_others_posts',
        │                                   'edit_published_posts']
        │       ↓  ALL must be held (BR-CAP-01)
        └─ ROLE ─── wp_usermeta key {$prefix}capabilities
```

**A capability check is a runtime computation, not a lookup.** There is no table of
"who may edit post 42".

### Reading the matrix 🟢

- **Administrator holds every one of the 50 primitives.** There is no capability an admin lacks on
  single-site; the role *is* the full set.
- **Editor is "all content by anyone"** — the full posts and pages surface including others' and
  private content, plus `moderate_comments`, `manage_categories`, `manage_links` and
  `unfiltered_html`. It holds **no** site, plugin, theme or user capability.
- **Author is "own content, publishable"** — 7 capabilities. Note the absence of
  `edit_others_posts` and of every `*_pages` capability: authors cannot touch pages at all.
- **Contributor is "own content, not publishable"** — 3 capabilities. **No `upload_files`**, which
  is why contributors cannot add images (BR-CAP-15).
- **Subscriber holds exactly one capability: `read`.**

The drop from Editor (26) to Author (7) is the sharpest boundary in the system: it is the line
between "trusted with the site's content" and "trusted with your own".

## 3. Capabilities held by nobody 🟢

Two capabilities in the primitive list are granted to **no default role**:

| Capability | Who holds it |
|------------|-------------|
| `edit_files` | Administrator only, and only when `DISALLOW_FILE_EDIT` is not defined |
| `unfiltered_upload` | Administrator on single-site; **removed on multisite** and grantable only via a constant |

And several exist only through dynamic grants (BR-CAP-12), never stored in any role:

| Capability | Granted by | Condition |
|------------|-----------|-----------|
| `install_languages` | `wp_maybe_grant_install_languages_cap()` | the filesystem permits writing |
| `resume_plugin`, `resume_theme` | `wp_maybe_grant_resume_extensions_caps()` | recovery mode is active |
| `view_site_health_checks` | `wp_maybe_grant_site_health_caps()` | — |
| `exist` | `WP_User::has_cap()` | **always** — every user holds it (BR-CAP-04) |

## 4. Meta capabilities 🟢

`map_meta_cap()` translates these at call time. The important ones:

| Meta capability | Resolves to (depending on the object) |
|-----------------|---------------------------------------|
| `edit_post` / `edit_page` | `edit_posts` → `edit_others_posts` (if not the author) → `edit_published_posts` (if published) → `edit_private_posts` (if private) |
| `delete_post` / `delete_page` | mirror of the above with `delete_*`. **No object argument → `do_not_allow`** (BR-CAP-10) |
| `read_post` / `read_page` | `read` → `read_private_posts` (if private and not the author) |
| `publish_post` | `publish_posts` |
| `edit_user` | empty caps if editing **yourself** (BR-CAP-07); otherwise `edit_users`; `do_not_allow` if `$user_id < 1` |
| `remove_user` | `remove_users`; `do_not_allow` if removing **yourself** on multisite without super-admin (BR-CAP-09) |
| `promote_user` / `add_users` | `promote_users` |
| `edit_comment` | the parent post's `edit_post` |
| `edit_term` / `delete_term` / `assign_term` | the taxonomy's declared capabilities |

**The critical asymmetry (BR-CAP-05):** `map_meta_cap()` returning an **empty array** means
*allowed*, because `array_all()` over an empty array is `true`. A case that falls through without
emitting a capability grants access silently (F-CAP-03).

## 5. Legacy user levels 🟢

`level_0` through `level_10` are pseudo-capabilities retained since the pre-2.0 numeric user-level
system:

| Role | Levels held |
|------|-------------|
| Administrator | `level_0` … `level_10` |
| Editor | `level_0` … `level_7` |
| Author | `level_0` … `level_2` |
| Contributor | `level_0` … `level_1` |
| Subscriber | `level_0` |

`WP_User::has_cap()` still accepts a numeric argument and translates it via
`translate_level_to_cap()`, emitting `_deprecated_argument()` (BR-CAP-11). Deprecated for two
decades and still shipped in every role, because plugins test for them (F-CAP-05).

## 6. Multisite 🟢

| Concept | Behavior |
|---------|----------|
| **Role scope** | Per site. A user has `wp_capabilities` for site 1, `wp_3_capabilities` for site 3 (BR-CAP-13, BR-MS-04). |
| **Super Admin** | Bypasses `has_cap()` entirely unless the mapped list contains `do_not_allow` (BR-CAP-03). |
| **Source of truth** | `get_super_admins()` prefers the **`$super_admins` PHP global** over the `site_admins` network option (BR-CAP-14). |
| **Network capabilities** | `manage_network`, `manage_sites`, `manage_network_users`, `manage_network_themes`, `manage_network_plugins`, `manage_network_options` — held only by super admins. |
| **Self-removal** | A user cannot remove themselves unless they are a super admin (BR-CAP-09). |
| **`unfiltered_html`** | Removed from Editor and Administrator on multisite; only super admins retain it. 🟡 |

## 7. Authorization surfaces beyond roles 🟢

Roles are one of **six** places authorization is decided, and they do not agree on defaults
(`domain.md` DR-10):

| # | Surface | Gate | Default when unspecified |
|---|---------|------|-------------------------|
| 1 | `current_user_can()` | `map_meta_cap()` → primitives | **empty caps ⇒ ALLOWED** |
| 2 | REST route | `permission_callback` | **absent ⇒ PUBLIC** |
| 3 | REST callback return | `false` or `null` | **`null` ⇒ DENIED** |
| 4 | Admin screen | `auth_redirect()` + per-screen `current_user_can()` | authenticated, then per-screen |
| 5 | Admin-Ajax | `wp_ajax_nopriv_*` registration | **`nopriv` ⇒ PUBLIC, no gate** |
| 6 | Ability | `permission_callback` + `DEFAULT_PUBLIC = false` | **PRIVATE, not in REST** |
| 7 | Customizer setting | per-setting `capability` | `edit_theme_options` |

### The house style — decided 2026-08-21 🟢

**Answer to Q4: deny by default. The Abilities API is the reference implementation.**

| Surface | Current default | Conforms? |
|---------|----------------|:---------:|
| Ability with no explicit opt-in | private, not in REST | ✅ **reference** |
| REST `permission_callback` returning `null` | denied | ✅ |
| `delete_post` with no object argument | denied | ✅ |
| REST route with **no** `permission_callback` | **public** | ❌ deviation |
| `map_meta_cap()` emitting an empty array | **allowed** | ❌ deviation |
| Admin-Ajax `wp_ajax_nopriv_*` | **public, ungated** | ❌ no mechanism exists |

The three deviations are recorded as technical debt in `architecture.md` §6 (TD-01, TD-02) and as
gap `G-03`… correction: gap **G-02** in `gaps.md`. Admin-Ajax is the hardest of the three, because
unlike REST it has **no declarative authorization mechanism at all** to fix (F-ADM-01).

### The override 🟢

Every one of these can be short-circuited:

```php
$capabilities = apply_filters( 'user_has_cap', $this->allcaps, $caps, $args, $this );
```

Any plugin may rewrite the entire capability set on any check, in one line (F-CAP-01).

## 8. Findings

| # | Finding | Confidence |
|---|---------|-----------|
| F-PERM-01 | The role definition is spread across eight version-named functions. There is no single authoritative statement of what an Editor can do — this matrix had to be reconstructed by simulating `add_cap`/`remove_cap` in historical order. | 🟢 |
| F-PERM-02 | "Empty capability list means allowed" is the wrong default for a permission system, and it sits at the centre of the primary authorization path. | 🟢 |
| F-PERM-03 | Six authorization surfaces with five different defaults means the safe pattern depends entirely on which surface an author is writing against. | 🟢 |
| F-PERM-04 | Roles are user meta with no referential integrity: deleting a role leaves users holding a name that resolves to nothing (F-CAP-06). | 🟢 |
| F-PERM-05 | `$super_admins` as a PHP global outranking the database means a compromised `wp-config.php` or any early plugin grants total network control (F-CAP-08). | 🟢 |
| F-PERM-06 | The Contributor role's lack of `upload_files` is the most user-visible consequence of the capability model and a frequent support question. | 🟡 |
| F-PERM-07 | Admin-Ajax is the only surface with **no** declarative authorization mechanism at all, and it is the most common source of privilege-escalation CVEs (F-ADM-01). | 🟢 |
