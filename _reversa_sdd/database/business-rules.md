# Business rules in the database — WordPress

> Generated by the **Data Master** (Reversa)

## 1. What the database enforces

**Nothing.**

A search of every DDL statement in the tree returns zero of each:

| Construct | Count | Verified by |
|-----------|:-----:|-------------|
| `CREATE TRIGGER` | **0** | grep over `wp-admin/`, `wp-includes/` |
| `CREATE PROCEDURE` | **0** | ″ |
| `CREATE FUNCTION` | **0** | ″ |
| `CREATE VIEW` | **0** | ″ |
| `CHECK (...)` constraints | **0** | ″ |
| `FOREIGN KEY` / `REFERENCES` | **0** | ″ |

The only DDL in WordPress core is `wp_get_db_schema()` in `wp-admin/includes/schema.php`:
19 `CREATE TABLE` statements, columns, primary keys and indexes. Nothing else.

🟢 One vendored library, SimplePie (`wp-includes/SimplePie/src/Cache/MySQL.php`), carries two
`CREATE TABLE` statements of its own for an optional feed cache backend. WordPress does not use it —
`WP_Feed_Cache_Transient` supplies the cache instead (BR-FEED-06).

## 2. The three constraints that do exist

Only three declarative guarantees are expressed in the schema at all:

| Constraint | Table | What it guarantees |
|------------|-------|--------------------|
| `UNIQUE KEY option_name` | `options` | An option name appears once. The only unique constraint the system genuinely relies on. |
| `UNIQUE KEY term_id_taxonomy (term_id, taxonomy)` | `term_taxonomy` | A term appears once per taxonomy. **Does not cover** `(slug, parent, taxonomy)`, which is the case `wp_insert_term()` actually needs — hence its insert-then-detect-duplicate logic (F-TAX-02, F-DD-05). |
| `PRIMARY KEY (object_id, term_taxonomy_id)` | `term_relationships` | An object is related to a term once. |

Everything else — including `user_login`, which is semantically unique — is an **ordinary index**,
not a constraint. 🟢

## 3. Where the rules actually live

All 431 business rules in this extraction are enforced in PHP. The consequences are visible
throughout the codebase:

| Missing DB guarantee | PHP compensation | Rule |
|----------------------|------------------|------|
| No unique index on `(post_id, meta_key)` | `add_metadata()` runs `SELECT COUNT(*)` then `INSERT` — a race with no constraint behind it | BR-META-03 |
| No unique index on `post_name` | `wp_unique_post_slug()` loops, one query per attempt | BR-POST-06 |
| No unique index on `(slug, parent, taxonomy)` | `wp_insert_term()` inserts, detects a duplicate, then **deletes its own rows** | BR-TAX-05 |
| No FK from `term_relationships` to `posts` | Deleting a post deletes its relationships in PHP | — |
| No FK on `term_taxonomy.parent` | `_pad_term_counts()` carries an explicit **cycle guard** against corrupted hierarchies | BR-TAX-13 |
| No FK from menu items to their target | `_menu_item_orphaned` tombstone meta | BR-MENU-05 |
| No `CHECK` on `post_status` | 11 valid values enforced only by `register_post_status()` and PHP | BR-POST-01 |
| No `CHECK` on `comment_approved` | 5 valid strings enforced only in PHP | BR-CMT-12 |
| No transactions | Compensating logic everywhere (`../domain.md` DR-07) | F-DB-06 |

## 4. Rules the database is *configured* not to enforce

`wpdb::set_sql_mode()` **removes** six strict modes on every connection (BR-DB-10):

```
NO_ZERO_DATE · ONLY_FULL_GROUP_BY · STRICT_TRANS_TABLES · STRICT_ALL_TABLES · TRADITIONAL · ANSI
```

🟢 This is deliberate. `NO_ZERO_DATE` would reject `0000-00-00 00:00:00`, which is the
`post_date_gmt` of **every draft** (BR-POST-04). See [ADR-007](../adrs/007-permissive-mysql-sql-mode.md).

Because strict mode is off, MySQL will not reject over-length or mis-encoded values — so `wpdb`
implements that check **in PHP** instead, rejecting rather than truncating (BR-DB-06). The database's
own guard was removed and replaced with an application-level one.

## 5. Schema evolution

There is no migration log. Two mechanisms cooperate:

| Mechanism | Purpose | Limitation |
|-----------|---------|-----------|
| `dbDelta()` | Diffs the declared `CREATE TABLE` statements against the live schema and emits `ALTER` statements | Can only express **schema shape**, never data transformation |
| `upgrade_NNN()` functions | **43 version-gated functions** in `wp-admin/includes/upgrade.php`, run in sequence from the site's current `db_version` | Hand-maintained; contains 79 direct query/dbDelta calls |

The most recent are `upgrade_590`, `upgrade_600`, `upgrade_630`, `upgrade_640`, `upgrade_650`,
`upgrade_670`, `upgrade_682`, `upgrade_700`. 🟢

`$wp_db_version` (**61833**) is the sole version marker.

## 6. Findings

| # | Finding | Confidence |
|---|---------|-----------|
| F-DBR-01 | **The database holds no logic at all** — zero triggers, procedures, functions, views, check constraints and foreign keys. It is pure storage. | 🟢 |
| F-DBR-02 | Only three declarative constraints exist in 18 tables, and one of them (`term_id_taxonomy`) does not cover the case its own module needs. | 🟢 |
| F-DBR-03 | WordPress actively **weakens** its database configuration on every connection, then re-implements the removed guarantees in PHP. | 🟢 |
| F-DBR-04 | Portability is the reason: MySQL 3.23 had no foreign keys in MyISAM, no triggers and no procedures. Every choice here follows from running anywhere (ADR-003). | 🟡 |
| F-DBR-05 | The cost is that **every integrity guarantee is advisory**, and a direct SQL write — by a plugin, a migration script or a developer — can leave the database in a state no PHP path would produce. | 🟢 |
