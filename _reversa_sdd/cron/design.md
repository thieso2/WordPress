## Main Flow

1. **asymmetric duplicate window** — For events due within 10 minutes or already past, min_timestamp becomes 0 so all past identical events count as duplicates; for far-future events the window is symmetric around the event's own timestamp.
   Source: `wp-includes/cron.php:135` 🟢
2. **transient-based spawn lock** — A doing_cron transient holds a microtime float; locks more than 10 minutes ahead are discarded, and WP_CRON_LOCK_TIMEOUT doubles as a one-per-minute rate limit.
   Source: `wp-includes/cron.php:899` 🟢
3. **visitor-redirect fallback** — ALTERNATE_WP_CRON redirects the visitor's browser back to the same URI with a marker and runs cron during that second request, trading user latency for reliability on hosts where loopback fails.
   Source: `wp-includes/cron.php:936` 🟢

## Alternative Flows

- **BR-CRON-09:** Spawning aborts when no events are ready or the earliest ready timestamp is in the future. 🟢
- **BR-CRON-11:** The default path issues a non-blocking loopback HTTP request to wp-cron.php. 🟢

## Risks and Gaps

- 🟢 **F-CRON-01** — Cron only runs when someone visits the site; a site with no traffic executes no scheduled work, which is why DISABLE_WP_CRON plus a real crontab is the standard production configuration.
- 🟢 **F-CRON-02** — The lock is a transient, so cross-process correctness depends on a persistent object cache; without one it is a database row with no atomic compare-and-set and two concurrent requests can both acquire it.
- 🟢 **F-CRON-03** — All events in one autoloaded option means every request loads the full schedule.
- 🟢 **F-CRON-04** — The asymmetric duplicate window is subtle but correct: it prevents unbounded accumulation of a repeatedly-failing event while still allowing legitimate future scheduling.
- 🟢 **F-CRON-05** — ALTERNATE_WP_CRON makes a visitor's browser the scheduler, adding a redirect to their request.
- 🟡 **F-CRON-06** — Argument identity is md5(serialize($args)), so argument order and type changes silently create distinct events.
