## Main Flow

1. **streaming byte-level editing** — Forward-only scan recording queued replacements applied on get_updated_html(); memory proportional to the document, not to a node graph.
   Source: `wp-includes/html-api/class-wp-html-tag-processor.php` 🟢
2. **bookmark and seek** — Named positions saved during a forward scan allow non-linear editing on a forward-only cursor.
   Source: `wp-includes/html-api/class-wp-html-tag-processor.php:1360` 🟢
3. **HTML5 tree construction** — Insertion modes, stack of open elements, list of active formatting elements and the adoption agency algorithm, per the HTML5 specification.
   Source: `wp-includes/html-api/class-wp-html-processor.php` 🟢

## Alternative Flows

- **BR-HTML-01:** WP_HTML_Tag_Processor never constructs a tree; modifications are byte-level and applied on get_updated_html(). 🟢
- **BR-HTML-02:** Scanning is forward-only; set_bookmark() and seek() are the only way to revisit a position. 🟢

## Risks and Gaps

- 🟢 **F-HTML-01** — The most rigorous code in WordPress: a genuine HTML5 tree-construction implementation totalling 384 KB, written because regex-based HTML manipulation caused a long tail of correctness and security bugs.
- 🟢 **F-HTML-02** — Failing loudly via WP_HTML_Unsupported_Exception is the opposite of the block parser's never-fail design: two parsers in one codebase with deliberately opposite error philosophies, each right for its input.
- 🟢 **F-HTML-03** — The streaming tree-free design keeps memory proportional to the document, necessary for wp_filter_content_tags() running on every post.
- 🟡 **F-HTML-04** — Neither processor is exposed as a simple 'modify this HTML' helper; callers must drive the cursor, which keeps it fast and makes it easy to misuse.
