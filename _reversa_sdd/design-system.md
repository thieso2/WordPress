## 1. How WordPress's design system actually works

WordPress has **two entirely separate design systems**, and they share no tokens:

| System | Scope | Source of truth | Delivery |
|--------|-------|-----------------|----------|
| **theme.json** | the front end and the block editor | `wp-includes/theme.json` (v3), merged across 4 origins | CSS custom properties + utility classes, generated at runtime by `WP_Style_Engine` |
| **Admin colour schemes** | `/wp-admin/` only | 8 SCSS files under `wp-admin/css/colors/` | compiled CSS, chosen per user |

🟢 The block editor uses the first; the admin chrome around it uses the second. A colour defined in
`theme.json` has no effect on the admin menu, and vice versa.

### The four-origin cascade 🟢

Every token below is a **default**, not a fixed value. `WP_Theme_JSON_Resolver::get_merged_data()`
merges four origins in order (BR-GS-01):

```
default (wp-includes/theme.json)  →  blocks  →  theme  →  custom (user, via the Site Editor)
```

Later wins. `PROTECTED_PROPERTIES` are the only values a user cannot override (BR-GS-05).

### Token delivery 🟢

Each preset generates **two** artifacts (BR-GS-07):

| Artifact | Example |
|----------|---------|
| A CSS custom property on `:root` | `--wp--preset--color--vivid-red: #cf2e2e` |
| A utility class | `.has-vivid-red-color`, `.has-vivid-red-background-color` |

The root custom-property selector is `:root`; the root block selector is `body` (BR-GS-06).

### Spacing 🟢

`settings.spacing` — WordPress generates its spacing scale **algorithmically** rather than listing it:

```json
"spacingScale": { "operator": "*", "increment": 1.5, "mediumStep": 1.5, "steps": 7, "unit": "rem" }
```

Seven steps, multiplied by 1.5 from a 1.5 rem medium step — so the emitted presets are approximately
`0.44rem · 0.67rem · 1rem · 1.5rem · 2.25rem · 3.38rem · 5.06rem`, exposed as
`--wp--preset--spacing--{n}`. 🟡 (the values are computed at runtime; the generator is confirmed)

**Accepted units:** `px`, `em`, `rem`, `vh`, `vw`, `%`

**Default applied style:** `blockGap: 24px`, root padding `0px` on all sides.

### Borders 🟢

```json
"border": { "color": false, "radius": false, "style": false, "width": false }
```

**All four border controls are disabled by default.** A theme must opt in via its own `theme.json`.
There is no core border-radius scale — 🔴 a notable absence for a design system.

### Feature flags 🟢

| Setting | Default | Effect |
|---------|:-------:|--------|
| `appearanceTools` | `true` | enables the full appearance UI |
| `useRootPaddingAwareAlignments` | `true` | full-width blocks escape root padding correctly |
| `typography.dropCap` | enabled | drop-cap control on paragraphs |
| `typography.fluid` | **absent** | 🟢 core ships **no** fluid typography by default; themes opt in |
| `dimensions.defaultAspectRatios` | `true` | the 7 ratios above are offered |

`core/button`, `core/image`, `core/icon`, `core/pullquote`.

## 5. The style engine 🟢

`WP_Style_Engine` converts style objects into CSS. Its four-class model
(`../style-engine/design.md`) is the cleanest boundary in core (F-SE-01):

| Class | Responsibility |
|-------|---------------|
| `WP_Style_Engine_CSS_Declarations` | `property: value` pairs, **sanitized on add** (BR-SE-01) |
| `WP_Style_Engine_CSS_Rule` | a selector plus its declarations |
| `WP_Style_Engine_CSS_Rules_Store` | a named collection; several coexist independently (BR-SE-02) |
| `WP_Style_Engine_Processor` | combines, deduplicates and renders (BR-SE-03) |

🟢 The engine can return **either** a preset utility class **or** an inline style for the same input
(BR-SE-04) — which is what lets block supports choose between a token and a custom value.

**No component inventory can be produced from this checkout.**

## 7. Findings

| # | Finding | Confidence |
|---|---------|-----------|
| F-DS-01 | **WordPress has two design systems that share no tokens.** `theme.json` governs content; SCSS colour schemes govern the admin. A brand colour must be defined twice. | 🟢 |
| F-DS-02 | Every token is a **default in a four-origin cascade**, so no token value is fixed. A theme or a user can replace any of them (BR-GS-01). | 🟢 |
| F-DS-03 | The spacing scale is **generated from a formula**, not enumerated — unusual and compact, but it means the concrete values are not visible in the token file. | 🟢 |
| F-DS-04 | **All four border controls are disabled by default** and there is no core radius scale. For a system this mature, that is a conspicuous omission. | 🟢 |
| F-DS-05 | Core ships **no fluid typography**; only four font sizes (13 / 20 / 36 / 42 px) with no fluid clamping. Themes must supply their own scale. | 🟢 |
| F-DS-06 | Presets emit both a custom property and a utility class, so the same token is addressable from CSS and from block markup. | 🟢 |
| F-DS-07 | The component library is unrecoverable from this checkout; only block schemas can be specified. | 🔴 |
