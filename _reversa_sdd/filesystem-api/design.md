## Main Flow

1. **ownership-based method detection** — Write a temp file, compare fileowner() of that file with fileowner() of a WordPress file; only if they match is direct writing used. 'Can write' and 'should write' are treated as different questions.
   Source: `wp-admin/includes/file.php` 🟢
2. **degradable signature verification** — Missing crypto yields 'unsupported' rather than 'invalid' so old hosts can still update; the pure-PHP polyfill is speed-tested first to avoid exhausting max_execution_time.
   Source: `wp-admin/includes/file.php:1410` 🟢

## Alternative Flows

- **BR-FS-05:** Fallback order is direct, then ssh2, then ftpext, then ftpsockets. 🟢
- **BR-FS-08:** When the sodium extension is absent, the pure-PHP polyfill is speed-tested via runtime_speed_test(100, 10) and rejected if too slow. 🟢
- **BR-FS-11:** PclZip is the pure-PHP fallback when ZipArchive is unavailable. 🟢

## Risks and Gaps

- 🟢 **F-FS-01** — The ownership check is thoughtful shared-hosting security: 'can write' and 'should write' are different questions and WordPress asks the second.
- 🟢 **F-FS-02** — Signature verification degrading to 'unsupported' means a host without sodium installs updates unverified; availability was deliberately chosen over integrity.
- 🟢 **F-FS-03** — The polyfill speed test is a rare case of runtime performance measurement gating a security operation.
- 🟡 **F-FS-04** — Four filesystem backends means every update-path file operation is written against an abstraction whose FTP implementations are exercised on a small fraction of installs.
