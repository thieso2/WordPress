## Main Flow

1. **functional deprecation** — The deprecated function keeps working and merely calls _deprecated_function(), which emits a notice only under WP_DEBUG.
   Source: `wp-includes/deprecated.php` 🟢
2. **listener-gated hook deprecation** — apply_filters_deprecated()/do_action_deprecated() emit their notice only when a callback is registered, so unused deprecated hooks stay silent.
   Source: `wp-includes/plugin.php:723` 🟢

## Alternative Flows

- **BR-DEP-01:** Deprecated functions remain fully functional; only a debug-time notice is added. 🟢
- **BR-DEP-02:** Deprecation notices appear only when WP_DEBUG is enabled, so they are invisible in production. 🟢
- **BR-DEP-03:** Deprecated hooks still fire, warning only if a callback is actually registered. 🟢

## Risks and Gaps

- 🟢 **F-DEP-01** — 9112 lines of compatibility code is not technical debt but the product decision that made WordPress ubiquitous: a site from 2008 still upgrades.
- 🟢 **F-DEP-02** — Preserving filenames as public API is the strongest statement of the compatibility commitment in the codebase.
- 🟢 **F-DEP-03** — Nothing is ever removed and nothing has a sunset date, so the compatibility surface only grows; every deprecated function is also a permanently supported one.
- 🟢 **F-DEP-04** — Deprecation notices are invisible in production, so a plugin can rely on deprecated APIs indefinitely without its users ever seeing a warning.
