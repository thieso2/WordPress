Evidence:

- No root `package.json`, `composer.json`, `Gruntfile.js` or `webpack.config.js`.
- No `src/` directory; `wp-includes/js/dist/` already contains **compiled** `@wordpress/*` packages.

## 10. Spec organization suggestion

**Suggested granularity: `module`**

WordPress presents two competing organizational signals:

1. **Domain-named module boundaries** — both as folders (`rest-api/`, `html-api/`, `block-supports/`, `sitemaps/`, `customize/`, `interactivity-api/`, `style-engine/`, `l10n/`, `abilities-api/`, `block-bindings/`, `widgets/`) and as the ~220 domain-named flat files in `wp-includes/` (`post.php`, `taxonomy.php`, `user.php`, `comment.php`, `option.php`, `cron.php`, `rewrite.php`…).
2. **Centralized routing** — `rest-api.php` plus 49 `WP_REST_*_Controller` classes registering routes across 45 files.

The routing signal is real but **scoped to a single subsystem**. WordPress's primary request routing is not a routes table at all: it is `wp-settings.php` → `WP::main()` → `WP_Query` → `template-loader.php`. The module signal, by contrast, spans the entire 670k-line codebase and matches how WordPress documents itself.

`module` is therefore the dominant signal, with the REST surface recorded as a secondary signal to be captured as a module in its own right.
