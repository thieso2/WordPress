## Main Flow

1. **server-side directive processing** — Walk the HTML with the directives processor, dispatching each recognized data-wp-* attribute to a handler called on both element entry and exit so context frames push and pop correctly.
   Source: `wp-includes/interactivity-api/class-wp-interactivity-api.php:492` 🟢
2. **namespaced reference resolution** — parse_directive_name splits directive from suffix; extract_directive_value parses namespace::path with a default namespace; evaluate() walks namespace then path honouring a ! negation prefix.
   Source: `wp-includes/interactivity-api/class-wp-interactivity-api.php:663` 🟢
3. **non-destructive style merging** — merge_style_property parses the existing style attribute, replaces one property and re-serializes, so directives compose with author-written inline styles.
   Source: `wp-includes/interactivity-api/class-wp-interactivity-api.php:1354` 🟢

## Risks and Gaps

- 🟢 **F-INT-01** — Server-side directive processing means an interactive block's initial render is correct without JavaScript: genuine progressive enhancement, in marked contrast with the React-only editor.
- 🟢 **F-INT-02** — The whole system rests on the HTML API's attribute-prefix discovery; without get_attribute_names_with_prefix() this would be regex-based again.
- 🟢 **F-INT-03** — Directives are HTML attributes containing a small expression language evaluated on both server and client, and the two evaluators must agree.
- 🟡 **F-INT-04** — merge_style_property() reveals that directives compose with author-written inline styles rather than replacing them, required for correctness but easy to overlook when specifying behavior.
